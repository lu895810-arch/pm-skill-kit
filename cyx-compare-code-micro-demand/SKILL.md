# 竞品代码级对比微需求（cyx-compare-code-micro-demand）

> 本 skill 原名 `cyx-compare-micro-demand`，2026-09-29 更名为 `cyx-compare-code-micro-demand`；能力、骨架与产出不变。

## Purpose（目的）

把「A、B 两个产品谁在哪块更强」这件事，变成一份**可以直接拿去排期、照着做**的需求文档。

和常见的「对比一下就完事」的竞品分析不同，这份交付物的落点是**需求**：对比只是手段，目的是把 A 里那些确实更好用的功能，抽象成一条条**任何同类工具都能照做的通用需求**，每条配可勾选的验收标准。B 反超 A 的部分单独列一份清单，作为后续演进的参考。

它来自一次真实跑通的交付（火宝 huobao-drama × 爱创梦工厂 manju 功能对比与优势需求文档，22 项优势功能 + 反向差距清单）。那次做对的三件事，也是本 skill 的交付标准：

1. **事实可回溯**——每条论断都能指到源码文件 / 接口 / 具体界面，不靠印象；找不到出处的判断直接删，不保留模糊措辞。
2. **优势要落成需求**——不满足于「A 有这个功能」，而要写成「系统必须做到 X，验收时看到 Y」的通用要求，编号管理。
3. **语言干净**——去 AI 味、不用套话与行业缩语、不口语；判据是「这句话放进给客户的正式材料，是严谨专业还是聊天口气」。

## When to use（何时触发）

**触发**：

- 用户手里有**两个产品 / 工具**，要一份功能横向对比，且明确要把「某一方好用的点」整理成需求或改进项。
- 用户说「对比一下 XX 和 YY」「把 XX 里好用的功能整理成需求」「写一份优势需求文档」「列出对方领先我们的地方」。
- 用户要求「每项给需求点 + 验收标准」「要能直接排期」「带反向差距清单」。
- 交付对象是产品 / 研发团队，要能照着做，而不是只看结论。

**不触发**：

- 只做整盘产品规划（架构 / 模块 / MVP / 路线图）→ `cyx-strcuture-need`。
- 单产品轻量需求 brief → `cyx-summary-need`；给一批需求排优先级 → `cyx-priority-need`。
- 要做市场规模测算 / 数据溯源型行业报告 → `cyx-research-report`。
- 只对比不落需求、纯文字综述 → 不触发，直接答。

## 交付物结构（固定骨架）

单文件 HTML，左侧三级目录 + 右侧正文。章节顺序固定如下，可按需增删附录但**主链不变**：

```
Hero（H1 标题 + 导语 + meta 行）
  导语讲三件事：对比对象是谁、结论从哪来、这份文档产出什么
  meta：版本 vX.Y · 日期 · 对比对象（A × B）· 依据（如"两项目全量代码探索"）

1. 核心摘要
   ① 一段定位差异（A 侧重什么、B 侧重什么、各自适合谁）——不用"一句话"类标签，用「两者定位：」
   ② 双方长项卡片（verdict）：A 的长项 N 条 / B 的长项 N 条，条目写具体功能名

2. 项目概览对比
   一张表：维度 | A 的实现 | B 的现状（目标用户、技术栈、部署形态、协作能力等 8~12 个维度）

3. 全景功能对比矩阵
   逐模块一行：功能 | A 实现 | B 现状 | 谁更优
   判优口径统一为三档：A 更优 / B 更优 / 各有千秋；只列有实质差异的模块

4. 优势功能详解（主体）
   按分组排列（A 组资产与风格、B 组生成与一致性、C 组设置与可定制、D 组剧本与导出、E 组服务接入…）
   每组若干张微需求卡（模板见下节）

附录 A. 反向差距清单（B 反超 A）：功能 | B 实现 | A 现状 | 借鉴价值
附录 B. 全量能力对照（完整矩阵，含小项）
页脚：文档名 · vX.Y · 日期 · 一句维护提示
```

**目录纪律**：三级层次必须一眼能数出来——一级（章）/ 二级（分组标题，缩进一档 + 加粗 + 正文色）/ 三级（功能条目，再缩进一档 + 字号小半档 + 浅色 + 短横引导线）。只靠缩进还不够，要叠加字重与颜色。锚点改名时目录与正文一起改。

## 微需求卡模板（核心）

每项优势功能一张卡，内部顺序固定，缺一不可：

```
【卡片标题】分组字母 + 序号 + 功能名，右侧挂优先级标记（P0/P1/P2）
  · P0 = 决定性体验优势，直接决定成片质量 / 一致性 / 可控性
  · P1 = 明显提高效率，降低操作成本或提高可靠性
  · P2 = 差异化的额外亮点

▍B 现状与痛点
    B 现在怎么做、卡在哪。只写事实，一句一个点，不夸张。

▍A 方案
    A 怎么做的，带实现出处（源码文件、接口、参数）。技术细节要能回查，
    文件路径用 .file 样式，接口用 <code>。

▍需求点（编号可执行）
    写成「任何同类工具都能照做」的通用要求，编号形如 R-<组><序号>-<两位>，如 R-A2-01。
    一条只讲一件事，动词开头（"系统在…时，必须…"）。

▍验收标准（可勾选）
    每条都是可观察、可判定的动作或结果，供 QA 打勾，不写"体验良好"这类空话。
```

**需求点的写法**：从 A 的具体实现里抽出通用机制，而不是照抄 A 的技术细节。例：A 用某张表存风格预设 → 需求点写成「系统须内置不少于 N 套风格预设，每套含正向描述与负面清单」，而不是「须建 style_presets 表」——表名是 A 的实现，通用要求是能力。

## 对比矩阵规则

- **只列有实质差异的**模块；两边一样的常识项（都要登录、都有账号）不进矩阵。
- **判优要克制**：能判"更优"才判，功能面各有胜负的写"各有千秋"，并在括号里点明各自强在哪（如"各有千秋（A 易用 / B 深度）"）。
- **矩阵不写长句**：单元格用"顿号串联的短语 + 关键项加粗"，把细节留给第 4 章的需求卡。
- **优势标记不靠图标**：用文字（A 更优 / B 更优 / 各有千秋）+ 配色区分，不堆 emoji。

## 工作流（步骤）

1. **对齐立场**：确认对比对象、以及"哪一方是要借鉴的对象"（即优势方）。立场不同，需求卡的朝向就不同。
2. **收事实**：逐模块收集两边的功能清单与实现出处（文件、接口、界面）。**每条事实必须可回溯**；查不到出处的论断直接删，不改成模糊话保留。
3. **建矩阵**：按模块逐行判优，产出一张全景矩阵。
4. **提炼微需求**：把优势方的每一项优势抽象成通用需求点 + 验收标准，按分组编号。
5. **搭 HTML**：套本 skill 的骨架与 `cyx-html-style` 的组件类；目录做三级层级；对比矩阵用表格组件。
6. **两轮去味回扫**：第一轮清套话与行业缩语，第二轮专扫「读法标签（一句话…）+ 轻度口语词」。详见 `references/language-guard.md`。
7. **机检 + 自查**：跑 `python scripts/check-language.py <交付HTML>`，再走一遍下面的自查清单。

## 语言纪律（去 AI 味，强制）

**通用规则以 `cyx-html-style` 一.1 与 `~/.workbuddy/MEMORY.md`「语言总纲」为准**；本 skill 补充对比文档场景的高频违规：

- **不用读法标签**：不写「一句话说清 / 一句话结论 / 解读 / 小结」；提示框引导语用内容名（「两者定位：」「优先级说明：」），不用教读者"怎么读"的动词。
- **不用行业缩语**：耦合、粒度、跑通、运维、兜底、语义、系统性、可插拔、全量、交付、排障、空烧、打补丁、数据主权、可视化、透视、降级、快照语义、生产节拍、链路、幂等、细粒度、对齐比对、治理 → 一律换中性白话（对照表见 `references/language-guard.md`）。
- **不用套话**：赋能、闭环、生态化、沉淀、护城河、镜像式互补、底座、开箱即用、抓手、组合拳、落地、颗粒度 → 换成具体动作与结果。
- **不口语**：很麻烦 / 很烦 / 就能用 / 白白消耗 / 活儿 / 东西 / 手感 / 挑片 / 抽卡 / 把功夫花在 / 底子 / 搞定 / 说白了 / 咱们 → 改成书面表述。
- **技术事实保留原样**：接口路径、源码文件名、模型名、数字、验收标准一律不动，去味只动措辞，不动事实。

**两轮回扫**（关键）：去 AI 味不是一次到位。第一轮按「套话 + 缩语」清，交付前**再从全文视角扫第二轮**，专查「读法标签 + 轻度口语词」——这两类最容易在第一轮漏掉。

## 交付前自查清单

- [ ] 每条论断都能指到具体出处（文件 / 接口 / 界面），没有悬空判断
- [ ] 微需求卡四段齐全（现状痛点 / 方案 / 需求点 / 验收标准）
- [ ] 需求点是通用能力，不是照抄优势方的技术实现
- [ ] 需求点编号连续无跳号，验收标准可勾选
- [ ] 对比矩阵只列有实质差异项，判优克制、口径统一
- [ ] 目录三级层级一眼可辨（缩进 + 字重 + 颜色三重区分），锚点与正文一致
- [ ] 全文无「一句话」类读法标签、无套话、无行业缩语、无口语词（机检 + 人工各一遍）
- [ ] 无 emoji 装点
- [ ] 页脚版本号与 meta 一致
- [ ] 反向差距清单（B 反超 A）已列

## 自我进化机制

用户每提一次修改意见，先判定**是否具备跨文档通用性**：

- **通用**（如"不要一句话标签""去行业缩语""目录要看出层级"）→ 回写到对应位置：
  - 语言禁词新增 → `references/language-guard.md`，并同步 `cyx-html-style` 一.1 禁词表；
  - 新增机检词 → `scripts/check-language.py` 对应词表；
  - 骨架 / 模板 / 矩阵规则变了 → 本 SKILL.md 对应小节。
- **个案**（只跟这一篇的具体内容有关）→ 只改当期产物，不写进 skill。

**不要只在当期产物上改完就结束。** 改动在共享账本 `~/.workbuddy/skills/cyx-research-report/references/feedback-log.md` 留痕（含「归属 skill」列）。
