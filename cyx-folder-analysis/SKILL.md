# 本地项目分析 · 产品 × 技术双视角（cyx-folder-analysis）

## Purpose（目的）

把「分析一个本地文件夹」从随手聊变成可复现的方法论：先勘察再动笔、每个判断有文件证据、
宣传与实现分开核、图只画承载结构的图，产出一份能直接点开看的单文件暗色 HTML 报告。
首例是 Agnes AI Studio v18.0 桌面分发版分析，方法论与具体项目无关，任何本地工程可套。

> 与 `cyx-github-analysis` 的关系：它是 GitHub 仓库版（先 clone 再读），本技能是**本地文件夹版**
> （不假设有 git，直接读磁盘）。分析框架、交付物规格、语言红线、进化机制三处对齐，避免各写一套。
> 两者都不管「把项目跑起来」（→ 各自的 deploy 技能）。

---

## How to use（如何使用）

1. 拿到**文件夹路径**后，先按「一、取材」勘察，再按「二、七步分析法」走完全程，禁止凭空下结论。
2. 交付物按「四、交付物规格」排版；骨架与组件直接 `assets/report-template.html` 起手，改内容不改骨架。
3. 图的精绘按「五、图怎么画得精美」，统一视觉语言后再往报告里放。
4. 语言遵循 `~/.workbuddy/MEMORY.md` 的**语言总纲**（通俗 + 严谨 + 逻辑闭环 + 去 AI 味 + 不口语化）
   与 `cyx-html-style` 的禁词纪律。
5. 交付前逐项走「六、交付前自查清单」；渲染用 `assets/verify_render.py` 截图自验。
6. 交付后按「七、自我进化机制」回扫本轮反馈，可复用的写回本文件并记账。

## 一、取材：怎么读一个本地文件夹（动笔前读什么）

本地文件夹没有统一入口，且**目录可能极大**（上万文件），直接 `Glob` 全树会超时。先收口再深挖。

| 优先级 | 读什么 | 回答什么 |
|---|---|---|
| 0 | 顶层 `ls`（用 Bash，禁用无 depth 限制的 `Glob`/`find`） | 区分「这是工程源码」还是「这是已打包的分发物（exe/解压包）」 |
| 1 | 使用说明 / README / 启动脚本（`.txt`/`.ps1`/`.bat`/`start-*.sh`） | 产品对自己的定位与承诺——**这是宣传口径，不是事实** |
| 2 | `docs/`、`prompts/`、`*.md` 等文档目录 | 模块清单、用法、能力边界的自述 |
| 3 | 配置与清单：`package.json` / `inkos.json` / `*.config.*` / `.env.example` | 技术栈、依赖、端口、启动参数——**实现口径** |
| 4 | 源码顶层 + 1-2 个核心子系统（挑最有含金量的） | 真实模块分布、分层、关键机制取舍 |
| 5 | 网关 / 反向代理 / 入口文件（`gateway.js` / `server.js` / `app.py`） | 多进程如何对外、端口如何分配、单点在哪 |
| 6 | 资源目录（`assets/`、`public/`、`models/`）与构建产物 | 规模、是否有内置二进制（FFmpeg 等） |

**勘察纪律（踩过的坑）：**
- **大目录先 `ls` 顶层，再定点 `Read`**，不要一上来 `Glob **/*`。万级文件会让 Glob 超时、拿不到结果。
- **宣传 ≠ 实现**：说明文档里宣称的每项能力（对接了哪些模型/平台、有哪些功能）必须到源码/配置里数一遍再写；
  对不上的差距**单列一节**，不消化掉、不替作者圆场。
- **找真入口**：桌面分发物常是 `xxx.exe` + 内嵌源码；源码里真正的服务入口往往是 `launchers/`、`gateway`、`server`。
- **Windows 本机 Bash 坑**：`ls`/`dirname` 在某些 Git Bash 环境缺 coreutils；文件读改用 `Read`/`Write`/`Edit`/`Glob`/`Grep`，
  拷贝用 PowerShell `Copy-Item -LiteralPath`（中文/带括号路径必须 `-LiteralPath`）。

## 二、七步分析法

### 1. 核心定位
- 句式：**「不做 X，只做 Y」+ 一个生活化类比**（例：大模型是摄像机，它是剧组管理系统）。
- 判断项目站在赛道哪一层（模型层 / 编排层 / 应用层），并写清这一定位的两面：换来什么、代价是什么。
- 标题用「核心定位」，不用「一句话定位」（名词短语，不带论述腔）。

### 2. 产品全景（谁来用 · 解决什么）
- 把「用户给什么输入 → 产出什么」讲清；用户画像（非技术创作者 / 工程师 / 运维）决定正文口径。
- 一句话说清「它解决的是哪个具体环节的问题」，不泛泛谈「提升效率」。

### 3. 能力地图（模块怎么排）
- 按**生产流程先后**排成三栏（上游/中游/下游）或管线，不按字母或目录顺序平铺。
- 标出哪块是枢纽（高频被调用、串联前后）。纯功能清单不下判断。

### 4. 技术架构（几个进程 · 一个网关）
- 画**架构分层图**：前端/后端/基础设施 + 关键数据流箭头，每块标技术选型与端口。
- 多进程系统要标出**单点**（哪个进程一旦停，全系统断）、进程间如何通信（反代/消息/共享文件）。
- 核心机制深挖：挑全项目最有含金量的一个子系统画链路图、讲透取舍。

### 5. 供应链依赖（外部 API / 模型）
- 本机只做编排时，实际算力来自外部：把「本机模块 → 外部引擎」一一对应画出来。
- 标出**最大单点依赖**（哪个外部厂商一旦抽薪，功能即刻失效）；号池/轮询等成本策略单列。

### 6. 强项 vs 隐患
- 固定两栏：**强项 / 隐患**，每条带证据（源码路径 / 配置项 / 文档句），禁无锚点猜测
  （「可能存在性能问题」→ 改成「`X` 模块在 `Y` 下会阻塞，见 `path:line`」）。
- 隐患要落到具体机制，不说「未来可能不稳」这类空话。

### 7. 行业位置（给市场/竞品研究用）
- 把项目摆进同类坐标系：它在哪一层、与你在研究的模型层/应用层厂商是供需还是竞品。
- 结论落到「研究时要把 X 类与 Y 类分开算账」，给后续调研可直接引用的判断。

**来源索引**：报告末尾列全部依据文件路径 + 判断依据（如「基于静态阅读源码与文档，未实跑程序」），读者可回查。

## 三、证据与语言红线

1. **每个结论锚定文件路径**，写成 `来源：路径` 跟在图/表后面；报告末尾来源索引收口。
2. **未实现的能力不得写成已有**；「宣称」与「实现」两个词分开用。
3. **图必有信息量，不为图而图**：流程、架构、核心链路才配 SVG；对照关系、风险清单用表；
   成熟度用色条。纯装饰插图一张都不要。
4. **一句话原则**：能用一句说完不用两句；每节一个核心判断，先判断后展开。
5. **去 AI 味 ≠ 口语化**（2026-09-28 反馈定，最高优先级）：语言要**通俗易懂 + 专业严谨同时成立**。
   - 去 AI 味：不写「生态」「闭环」「赋能」「体现了…的诚实」这类空词与论述腔；
     「链路没闭环」改「生产链路到 X 这段断了」。
   - **反面同样成立**：不滑向口语/大白话/方言腔。「变砖→功能即刻失效」「捏成→编排成」
     「塞一个→注入一个」「躲限流→规避限流」「卡准→精准切入」「强绑→高度依赖」「卖铲子挖矿→售卖配套服务」。
   - 判据：**这句话放进要交给客户的正式材料里，合适吗？** 不合适就改（不是改回文言/官腔，是改中性书面语）。
6. **术语白话定义**：第一次出现必须给「是什么 + 为什么叫这个名」（例：分镜=把剧本拆成镜头并写清运镜；
   号池=一批共享账号轮换使用以分摊费用、规避限流）。外行能用自己的话复述才算讲清。
7. 叙述主体用「我们」/「本次分析」，不写「本报告」「本文将」。

## 四、交付物规格（单文件暗色 HTML）

| 项 | 规格 |
|---|---|
| 布局 | **左侧通栏目录**：贴左、贴顶、整条到底（`grid-template-columns:196px minmax(0,1fr)`；去掉 layout 的 `max-width`/`margin:auto`，否则整页变成居中浮岛）；`.toc` 用 `position:sticky;top:0;height:100vh`，右一条 `border` 分隔；滚动时用原生 JS 高亮当前节（不依赖库） |
| 目录标题 | 「目录」前加主色竖条（`::before` 4×16px 圆角块）；条目**带章节序号**（「一、核心定位」），序号与正文 `h2` **一字不差**——改一处同步另一处 |
| 激活项 | 主色文字 + 左侧 3px 主色竖线 + 10% 主色透明底，**直角左、圆角右**；缩略图看不清就放大核对，别凭印象 |
| 版心 | 正文 `padding:26px 36px 90px 28px`，`.main > *{max-width:1280px}`；正文**占满剩余空间、紧贴侧栏起排**，不居中留大块空档 |
| 窄屏 | `≤820px`：`.toc` 转 `position:static`、横排，正文单列 |
| 图 | 内联 SVG，`viewBox` 宽约 680；箭头用全局 `marker`（见模板 `<defs>`），深色底上每个形状显式填色；精致度见「五」 |
| 目录命名 | 章节标题用名词短语、无 AI 味：「核心定位」「产品全景」「能力地图」「技术架构」「供应链依赖」「强项与隐患」「行业位置」 |
| 禁用 | emoji、说明性文字（口径声明、方法论自述、审阅免责语）、单字双字空标签、页脚免责 |

CSS 变量、组件类（`.layout`/`.toc`/`.hero`/`.fig`/`.col`/`.pill`/表格）与 SVG `defs` 直接从
`assets/report-template.html` 抄，改内容不改骨架。

## 五、图怎么画得精美（diagram polish）

复用 `buddy-diagram-design` 的通用规则，并固化本会话沉淀的精绘基线。原则：**精致靠几何与层级，不靠堆阴影发光**。

1. **箭头统一**：在报告顶部 `<defs>` 定义 4 色 `marker`（dim/purple/cyan/green），各图按语义引用，不再用无头裸线。
2. **连线走圆角直角**：跨轴连接一律正交圆角（`M x y H … V …` 配 `stroke-linejoin:round`），标签背后垫**不透明遮罩矩形**再压字，不压线。
3. **字级分档**：正文 / 副标 / 说明 / 端口 / 栏头分成 5-6 档，全图字体阶梯一致；端口、路径、模型名这类才用等宽（`Consolas`/`monospace`）。
4. **强调节点加渐变 + 一层极淡光晕**：焦点容器用纵向 `linearGradient` 抬高，配 `radialGradient` 光晕（opacity ≤ 0.18）；**不加投影**、不滥用发光，避免「技术感堆砌」。
5. **分层/分区用主色竖条 + 分隔线**：多列容器左侧 3-4px 主色竖条标类别，列头用加粗小字 + 一条 `line` 分隔，不用重边框。
6. **同类图共用一套视觉语言**：同一份报告里架构图/依赖图/层级图的渐变、marker、箭头样式保持一致，渐变与 marker 的 `id` 每张图独立前缀防冲突。
7. **图下配 `cap` 说明**：「图 N ｜ 一句话讲清这张图承载的结构」，让图不被误读为装饰。

- [ ] 每个结论后面有 `来源：路径`？末尾来源索引齐吗？

## 七、自我进化机制（遵循 cyx-skill-evolution 通用条款）

**本技能不是一次写死的。** 用户使用本技能时提的修改意见，按 `cyx-skill-evolution` 的三步判定处理：
**通用**（换个项目仍成立）→ 回写本文件对应章节；**个案**（只对这一份产物成立）→ 只改当期产物。

| 反馈类型 | 典型原话 | 改本文件哪一节 |
|---|---|---|
| 勘察/取材 | 「这个目录别用 Glob 全扫」「先读说明文档」 | 一（取材清单） |
| 分析框架 | 「这块该多讲讲 X」「视角缺了」 | 二（七步分析法） |
| 证据与口径 | 「这个结论哪来的」「宣传和实际不符」 | 一 / 三（红线） |
| 遣词命名 | 「换个词」「标题别这么说」 | 三（红线）/ 四（目录命名） |
| 排版视觉 | 「加目录」「间距小点」「图多点/少点」 | 四（交付物规格）/ 五（图） |
| 流程命令 | 「这步顺序不对」 | 一（取材清单） |

**沉淀三步（每次反馈后必做）：**
1. 规则与「六、交付前自查清单」两处同步；
2. 在 `references/feedback-log.md` 追加一行（编号 `#N`、日期、用户原话节选、类别、落点、处置：新增/强化/修订/推翻、是否高频）；
3. 一句话告知用户「这条记进本技能了」。

**高频升级规则**：同一类别反馈出现 **2 次以上**，在对应章节把该条从「建议」升级为「强约束」，
并在 feedback-log 标注「高频」。个案（只对这一份报告成立的结论、数字）不入账本。
规则回退、落盘纪律（三不写）、分权处理、账本格式见 `cyx-skill-evolution`。

> 本会话已把首项经验种子写入 `references/feedback-log.md`（#1–#7），后续反馈在此连续编号。

## 边界

- 本技能只管「分析并产出报告」。要部署运行项目 → `cyx-folder-deploy`；
  要市场规模、竞品格局、商业模式调研 → `cyx-research-report`；
  GitHub 开源项目分析 → `cyx-github-analysis`。
- 分析过程中发现的可部署性、启动坑，不属于本技能产出；用户需要时转交对应 deploy 技能。
