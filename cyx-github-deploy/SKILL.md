description: 把一个 GitHub 仓库从零部署成本地可用的服务，并验证到「核心业务动作真能跑通」（clone → 读部署配置 → 选路径 → 装依赖 → 起服务 → 验证 → 固化）。当用户发来 GitHub 链接说「帮我把这个项目部署一下」「把这个仓库跑起来」「装一个/deploy 这个项目」，或问「这个项目怎么部署」时使用。入口先做分流判定：只要分析不要运行的走 cyx-github-analysis，静态页面直接打包预览，公网发布走发布类技能。核心方法：以仓库自带的 compose/Dockerfile/.env.example 为部署事实来源，区分「启动必需」和「用了才需要」的外部依赖，无 Docker 时用 SQLite 等零依赖默认值走本地开发态。部署后必须做核心业务动作冒烟（真实跑一次写操作/触发一次任务并等到终态），只验证服务活着不算通过；功能点了没反应时，按「后端日志 → 落库痕迹 → 端口监听 → 用户配置」顺序取证排查，未取证不得归因于用户配置。与 cyx-folder-deploy 的分工：那边管「本地已有文件夹跑不起来怎么排查」，这边管「从仓库链接到第一次跑通」；验证失败自动转入那边的排查链路。

# cyx-github-deploy：把 GitHub 项目部署成本地服务

## 第 0 步：先分流（进本技能先判这个，不满足立即离开）

用户发来 GitHub 链接，**先判断要不要部署**，以下三种不走本技能：

| 情况 | 判定信号 | 去处 |
| --- | --- | --- |
| ❌ 只要分析/调研，不要求运行 | 用户说「分析一下」「评估」「看看这个项目怎么样」，全程没提跑起来 | `cyx-github-analysis`（产品×技术分析报告）或 `cyx-github-search`（生态调研） |
| ❌ 纯静态页面/单文件 | 仓库只有 HTML/CSS/JS，无 package.json、无后端目录 | 直接打包/打开预览，不走部署流程 |
| ❌ 要公网上线/分享链接 | 用户说「上线」「发布」「给我一个能分享的网址」 | 发布类技能（sites） |

✅ **适用**：用户要的是"本地能打开用的服务"（前后端工作台、API 服务），关键词：部署、跑起来、起服务、本地能用。

分流通过后，走八步：**摸环境 → 读仓库 → 定路径 → 判依赖 → 装依赖 → 起服务 → 验证 → 固化**。
每步先执行「动作」；*斜体备注是原理说明，帮助理解，不执行、不对外输出*。

---

## 第 1 步：摸环境

动作——跑一遍并记录结论：

```bash
git --version
docker --version; docker info >/dev/null 2>&1 && echo "docker daemon: OK" || echo "docker daemon: NOT RUNNING"
node -v; python --version
which uv pnpm 2>/dev/null
```

动作——按结论分支：daemon OK → 第 3 步走路径 A；无 Docker 或 daemon 没跑 → 路径 B。缺的工具链到第 5 步再补，不预装。

_备注：`docker --version` 有输出不代表能用，必须 `docker info` 确认 daemon 活着。_

---

## 第 2 步：读仓库

动作——按序读 5 类文件，边读边记录：

1. README 的 "Docker Compose" / "Local Development" / "Start" 段落（官方推荐路径）；
2. deploy/ 目录或根下 docker-compose.yml（服务清单、端口、depends_on 启动顺序）；
3. compose/.env.example（端口和密钥的语义，哪个必填哪个可选）；
4. 后端 .env.example 和 config/settings 源码的**默认值**（第 4 步判定的输入）；
5. 各组件 Dockerfile（语言版本要求、包管理器及版本）。

**通过标准**：能用一句话说清——几个服务、各监听哪个端口、哪些外部服务是 compose 专供、前端从哪读后端地址。说不出就继续读，不许跳到第 3 步。

---

## 第 3 步：定路径

动作——二选一执行：

**路径 A（daemon OK）**：

```bash
git clone --depth 1 <url> && cd <repo>
cp deploy/compose/.env.example deploy/compose/.env   # 路径按仓库实际
docker compose --env-file deploy/compose/.env -f deploy/compose/docker-compose.yml up --build
```

起完直接跳第 7 步验证。

**路径 B（无 Docker）**：先做第 4 步判定，再继续第 5 步。

_备注：compose 里的 init 容器（建表/灌 SQL）通常是 `restart: "no"` 的一次性任务，排查时单看它的日志。_

---

## 第 4 步：判依赖（路径 B 必做，路径 A 跳过）

动作——对每个外部依赖（数据库/Redis/对象存储），按 4 条规则逐条判定并记录结论：

1. 看配置**默认值**：有默认值（如 `sqlite+aiosqlite:///...`）→ 不是硬依赖；必填无默认 → 启动必需；
2. 看启动钩子（FastAPI `lifespan`/`startup`）：启动时没连接它 → 不是启动必需；
3. 看客户端构造时机：函数调用时才 build（惰性）→ 用了才需要；import 时就连接 → 启动必需；
4. 看 broker 调用位置：`.delay()`/`apply_async` 在请求处理时才发生 → 缺了只影响异步任务功能。

动作——把结论写进 `.env` 注释，格式：`# X：启动必需 / 用了才需要（影响 N 功能）`。

动作——凡是判为"用了才需要"**且本机没有**的依赖，逐条登记受影响的功能名，写进第 7 步冒烟清单的"已知不可用"项（例：缺 Redis → 所有走队列的生成/提取功能点了不会响应）。

_备注：这步的结论是第 7 步"交代边界"的唯一依据，没做判定不许说"某些功能不可用"。另注意——缺 broker 这类依赖**不会让服务起不来**，只会让对应功能点了没反应，最隐蔽，必须靠第 7 步冒烟暴露，不能只靠读配置猜。_

---

## 第 5 步：装依赖

动作——Python（uv 项目）：

```bash
cd <repo>/backend
uv sync
uv run python init_db.py   # 仓库有 init 脚本就跑，确认 SQLite 文件生成
```

动作——Node（pnpm 项目）：

```bash
corepack enable
corepack prepare pnpm@<版本> --activate   # 版本取 package.json 的 packageManager 字段
pnpm install
```

动作——esbuild postinstall 报 EBUSY（Windows 稳定复现，重试无效）时：

```bash
pnpm install --ignore-scripts
find node_modules/.pnpm -name "esbuild.exe"   # 确认平台包二进制在，且能执行 --version
```

_备注：esbuild 真正的二进制来自 `@esbuild/win32-x64` 平台包，postinstall 只是校验，跳过不影响 vite。npm 项目的同款问题见 cyx-folder-deploy 坑 1/坑 2。_

---

## 第 6 步：起服务

动作——用后台任务机制（`run_in_background`，即把整条命令托管为常驻后台进程的运行方式）分别拉起服务，**命令里不得再套 `&`**：

```bash
# 后台任务 1：后端
cd <repo>/backend && uv run uvicorn app.main:app --host 0.0.0.0 --port 8000

# 后台任务 2：前端
cd <repo>/front && pnpm dev --host
```

动作——起服务前逐项过「串联三件事」，缺哪件补哪件：

1. 前端知道后端地址（dev 模式的 `VITE_*` 环境变量或代码默认值；构建态是 `/env.js`）；
2. 后端 CORS 放行前端 origin（`.env` 的 `CORS_ORIGINS`，localhost 和 127.0.0.1 两种形式都放）；
3. 数据库连接串指向实际用的库（SQLite 相对路径基于进程工作目录，确认 `cd` 位置）。

_备注：`&` 套进后台命令会随外层 bash 结束被连带杀掉，表现为任务"已完成"、日志为空、端口拒绝连接。后端 `--host 0.0.0.0`、前端 `--host` 分别解决外部访问和 Vite 只绑 IPv6 回环的问题。_

动作——服务起来后，**在仓库根留一个双击就能重启的启动脚本**（Windows 用 `.bat`：文件名只用 ASCII、内容不写中文注释，先把 `uv`/`pnpm` 所在目录补进 `PATH`，用 `start` 各开一个窗口；启动前先用 `netstat` 判端口，已在监听就跳过，避免重复起）。

_备注：Agent 拉起的服务是**会话托管的临时进程**，会话结束或长时间空闲会被回收。用户下次打开必然遇到"又打不开了"，这不是故障、是机制。不留下可自助重启的东西，同一个问题会被反复追问。汇报时要把"为什么停"和"怎么自己重启"一起说清。_

---

## 第 7 步：验证（含失败分支）

动作——按清单逐项验证，全部加 `--noproxy '*'`：

1. 后端健康检查（/health 或 /api/v1/health）返回 200；
2. /docs、/openapi.json 能打开，paths 数量符合第 2 步预期；
3. 从 openapi.json 挑 2-3 个业务 GET 接口，返回业务结构而非 500/404；
4. CORS：带 `Origin: <前端地址>` 头，响应含正确的 `access-control-allow-origin`；
5. 前端页面 200（localhost 和 127.0.0.1 各测一次）；
6. 有条件让用户开浏览器确认页面真的请求到后端；
7. **核心业务动作冒烟**：挑一个真实**写操作**接口（触发任务/生成/提交类，不是 GET 列表）实跑一次，轮询到任务终态（succeeded/failed），并直接查库确认产出真的写入。**只看 GET 200 不算通过——服务活着不等于业务能跑通。**

**失败分支（任一项不过就触发）**：健康检查失败、接口 500/404、页面不通——停止推进，**转入 `cyx-folder-deploy` 的排查链路**定位问题（先查进程存活/端口监听/启动日志，不要重装依赖、不要重 build）；修复后回本清单**从头复验**，不许跳项。

**静默失败分支（最易漏）**：服务全绿、GET 接口全 200，但第 7 项冒烟里业务动作点了没反应、任务状态不流转——按下一节「排障顺序」逐级取证，多半是第 4 步漏判的"用了才需要"依赖（典型：缺 Redis/Celery）在作祟，解法见坑 7。

---

## 排障：功能点了没反应 / 任务不流转（顺序硬约束）

适用：服务全绿、页面能开、接口 200，但某个业务动作（生成、提取、提交）点了没反应，任务永远停在初始状态。

**按顺序取证，不许跳步、不许先入为主**：

| 顺序 | 查什么 | 怎么查 | 判据（命中即锁定方向） |
| --- | --- | --- | --- |
| 1 | 后端日志异常 | 读后端进程日志 | 有 traceback / `OperationalError` / `ConnectionRefused` / `kombu` / `Exception in ASGI application` → 直奔该依赖 |
| 2 | 落库痕迹 | 直接读 SQLite/DB，看任务表与业务表 | 任务建了但 `executor_type`/`executor_task_id`/`started_at` 全空 = 从没被派发出去 |
| 3 | 端口监听 | `netstat -ano \| grep -E ":6379\|:8000"` | 依赖端口（broker/DB）没有 LISTEN = 服务压根没跑 |
| 4 | 用户配置 | 只读探针：拿库里存的 key 调供应商 `/models` 或发最小请求 | 配置对不对要**主动验**，不是让用户重填一遍 |

**三条铁律**：① 拿到第 1–3 步证据之前，禁止让用户重填/重新授权配置——大多数"没反应"不是用户填错，而是后端某个依赖没起；② 结论要落到可复现的链路：日志报什么 → 哪个依赖没起 → 补哪个（装依赖或走坑 7 的零内存兜底）；③ **应用把错误吞成笼统提示时（如 `xxx returned no result`），绕过应用层、用同样参数直接打供应商 API / 依赖端口，拿原始错误码与响应原文**——别在应用日志里绕，直接复现调用是最快的定位路径。

若是"配置项填了、但下拉为空 / 保存被拒 / 选项识别不出来"（不是点了没反应），见坑 9——那通常不是部署故障，是应用内置的能力白名单。

## 第 8 步：固化

动作——把启动命令（两条）、重启方式、本次新踩的坑写进当天工作日志 `.workbuddy/memory/YYYY-MM-DD.md`。

_备注：WorkBuddy 后台进程不跨会话存活，下次恢复照日志拉起即可（见 cyx-folder-deploy 坑 6）。_

## 坑位清单（内部参考，禁止输出给用户）

### 坑 1：后台命令里套 `&`，服务假死
现象：后台任务状态"已完成"、日志为空、端口无人监听。解法见第 6 步动作。

### 坑 2：代理劫持 localhost 请求
有 http_proxy 时 `curl localhost` 返回 502/"upstream connect failed"/000，全是假象。诊断一律 `curl --noproxy '*'`。（cyx-folder-deploy 坑 5 是同源的 502 变体。）

### 坑 3：esbuild postinstall EBUSY
Windows 下重试无效，`--ignore-scripts` 绕开 + 验证平台包二进制，见第 5 步。

### 坑 4：Vite 只绑 IPv6 回环
现象：`curl 127.0.0.1:7788` 000、`curl localhost:7788` 200。加 `--host`。

### 坑 5：把 compose 里的外部服务当成"必须装"
compose 全家桶需要 MySQL/Redis/对象存储 ≠ 本地开发态需要。判定看第 4 步，别给 Windows 装 Redis。

### 坑 6：pnpm 版本不对齐
corepack 按项目 `packageManager` 字段激活对应版本，别随手装最新版。

### 坑 7：异步任务型项目（Celery/broker）在本机无 Redis 时的零内存兜底
现象：UI 配好模型后点「生成/提取」毫无反应，后端日志刷 `kombu OperationalError: 10061 connecting to localhost:6379` + `Exception in ASGI application`；任务表里任务建了但 `executor_type`/`started_at` 全空。
判定：项目用 Celery 且派发点是 `.delay()`（见第 4 步第 4 条）时必现。
解法（省内存优先，不装 Redis、不起 worker）：在派发函数加 inline 分支——`threading.Thread(daemon=True)` 直接调用任务主体函数（Celery task 对象可直接调用），并把 `executor_type` 记为 inline；同时让 celery 派发失败时自动回退 inline。用配置项（如 `TASK_EXECUTION_MODE=inline|celery|auto`）控制，改回 celery 只改配置。
代价要讲清：取消操作不能真正中止运行中的任务、多任务串行、重启丢执行中的任务。
_注意：这是改仓库源码，后续 pull 更新会冲突，先跟用户确认再动手。_

### 坑 8：只验证"服务活着"，漏了"业务动作能跑通"
现象：部署报告写"全部验证通过"，用户一用就"没反应"。
根因：验证清单只覆盖服务存活（/health、/docs、GET 列表），没跑真实写操作；异步任务/队列类依赖不在启动路径上，服务照起、功能静默失效。
解法：第 7 步第 7 项——必须挑一个真实写操作冒烟到终态。冒烟用真实链路（会真调一次模型/写一次库），**测试写入的数据要主动说清**：写到了哪张表/哪条记录、要不要清，别在用户真实数据里留痕还不吭声。

### 坑 9：配置项填了、"识别不出来"——先查应用的能力矩阵，别当部署故障
现象：用户在 UI 里给某供应商填了图像/视频模型或端点，但新建成该类别时**下拉为空 / 保存被拒 / 选项里根本没有**。
根因：这类"识别不出来"由**应用内置的能力白名单/枚举**决定，跟服务起没起无关。常见形态：供应商分类型，每类只声明支持若干"能力类别"（text/image/video），模型创建时按白名单过滤；白名单**硬编码在代码里**。
排查动作（按序）：
1. 查能力矩阵：调等价接口（如 `/api/v1/llm/providers/supported?category=image`）看哪些供应商被声明支持该类别；
2. 查代码实现：该类别是否真有分支实现（如 `image_capabilities` 里只有 `if provider=="openai" ... else volcengine`）——声明支持 ≠ 有实现；
3. 实测一次：直接 POST 建该类别的对象，**把返回的错误原文当结论**（如 400 `Provider 'X' does not support category=image`）；
4. 只填 URL 字段（`image_base_url`/`video_base_url`）**不改变能力归属**——那是地址，不是能力开关，别被表单里的这些框误导操作员；
5. 模型/端点名要用**供应商真实调用 ID**（常与 UI 展示名不同：如火山方舟要求全小写 + 短横 + 版本日期后缀，`doubao-seedream-5-0-pro-260628`），并确认**账户侧已开通**该模型（未开通报 `ModelNotOpen`）——这两件都会表现为"调用失败"，但都不是部署问题。
6. **判定"账户侧是否已开通"的标准做法**（云厂商通用）：
   - 先拉供应商的模型目录（火山：`GET https://ark.cn-beijing.volces.com/api/v3/models`，用库里的 key）——拿到**真实调用 ID** 与在售状态，UI 展示名（`Doubao-Seedream-5.0-pro`）一律不可直接填；
   - 再用最小真实请求探单模型，**按错误码分辨**：`ModelNotOpen` = ID 正确、账号未开通（该去开通）；`InvalidEndpointOrModel.NotFound` = 该 ID 不存在或已下线（**别让用户去开通一个已下线的 ID**，换在售版本）；
   - 开通入口与门槛一并交代（火山：控制台「开通管理 → 模型 → 视觉模型 → 开通服务」，弹窗勾「全选 + 自动开通新增模型」；**视频类有账户余额门槛**，以开通页实际提示为准）；
   - **开通需要用户的账号登录态（含实名/短信验证），Agent 无法代办**——不要含糊承诺"我帮你开"。给直达链接 + 界面操作路径（画一张控制台示意图最省用户力气），把"开通完回来我改库并端到端复验"作为明确交接点。
汇报写法：明确说"这不是部署故障，是应用设计的能力边界；要启用 X 类能力必须用/新增 Y 类型的供应商"，并给出新增供应商的步骤。若坚持用原供应商，那是改代码（且要补该类别在应用里的调用实现），工作量另算、先跟用户确认。

### 坑 10：生成类功能是**链式依赖**，错误被应用包装后要逐层剥

现象：任务 failed，UI 只给一句笼统错误（如 `Image generation task returned no result`），看不出卡在哪一层。

根因：生成链路是 3~4 个串联环节，任一环失败都被上层 `except` 统一包装成同一条消息；UI 通常只保留最后一层。

排查动作（逐层剥，每层拿到**原始错误**再进下一层）：

1. **看库不看 UI**：直接读任务表的 `error` 字段，它比 UI 详细得多（同一任务：UI 是"returned no result"，库里是 `ModelNotOpen` / `S3 未配置`）；
2. **把耗时当信号**：秒级挂（<1s）= 请求根本没发出去（本地校验 / 模型名解析阶段失败）；十几秒 = 真调用了远端，失败在**后段**（下载生成物、上传对象存储）；
3. 典型三层顺序：**模型名对不对** → **账户/模型是否开通** → **对象存储是否配好**（生成类应用几乎都把产物落到 S3，`s3_bucket_name` 为空时报 `S3 未配置`）；
4. 每剥一层给用户一个明确动作，**别把"链路太长"当结论抛回去**。

_备注：第 3 层常被忽略——"能生成"和"能保存"是两件事，很多应用没有本地落盘兜底，必须配 S3 兼容存储（云厂商对象存储或本地 MinIO）。_

**用户不想注册云服务时，给存储层加本地兜底**（工作量可控，做法可复用）：

1. **只改存储模块，不动调用方**：在存储模块顶部按配置开关（如 `storage_backend = s3 | local`）分派，**保持 upload / download / get_file_info / list_files / delete_file 五个公开函数的签名不变**——上层几十处调用一行都不用改；
2. 入口文件按开关挂载静态路由（`app.mount("/media", StaticFiles(directory=...))`），并在启动时建目录；
3. local 实现三个要点：key→路径映射**必须防目录穿越**（校验解析后的路径仍在根目录内）；返回的 URL 要用**绝对地址**（前端和后端不同端口，相对路径会打到前端开发服务器上）；忽略云特有的额外参数（如 `ACL`）；
4. 改成 `local` 后**必须重启后端**再复验，并实测"生成的产物 URL 能 HTTP 200 取回真文件"——只看到任务 succeeded 还不够，要确认文件真的落盘且能访问。

_注意：这属于改源码，先跟用户确认（用户若在意后续同步上游更新，就改走云对象存储）。_

### 坑 11：内联执行任务时，别把「为独立 worker 进程设计的执行器」搬进 API 进程

现象（三个信号同时出现，很容易误判成"部署没做好"）：

- 前端操作弹**"缺少任务 ID"**类提示——本质是**创建任务的接口没返回 id**，不是前端坏了；
- 所有**走数据库的接口全部 500**，且每个请求**卡满同一个整数秒**（如 8s）；
- 任务表里留一条 `status=pending`、`executor_type` / `started_at` 全空、`updated_at` 与 `created_at` **完全相同**的记录：任务建出来了，从没被派发。

根因：为了让异步任务在没有 broker（Redis）的机器上也能跑，把它改成「进程内执行」。但若直接复用 **Celery worker 那条执行链**，就会踩雷——这类执行器是按「独立进程、独占事件循环」设计的，内部通常做三件事：`reset_db_runtime()` **全局替换**数据库引擎 → `asyncio.run()` 在新事件循环里跑 → 结束后 `close_db()` **关掉**该引擎。把这条链放进 API 进程的工作线程里执行，等于替换并关闭主进程正在用的数据库 runtime：主事件循环已建的连接被遗弃、**写事务永不释放**。

取证动作：

1. 看 `db-journal` / `db-wal` **文件的时间戳**：若与故障起点（那条 pending 任务的 `created_at`）**完全一致**且几分钟不释放，说明就在那一刻开了一个永不提交的写事务；
2. 用 `curl -w "%{time_total}"` 打一个**纯读**接口，若每次固定卡满同一个整数秒 → 是**等锁超时**，不是慢查询；
3. 看那条 pending 任务：`executor_type` 为空 + `updated_at == created_at` → 派发根本没执行到。

正确接法：**内联执行要绕开 worker 专用执行器**——在**调用方所在的事件循环里**直接 `await` 它的 async 业务函数（自带状态流转与异常写库），共用同一套 engine 与连接池；**同步**执行器再单独 `asyncio.to_thread` 丢线程。判断依据是**执行器的类型**（是不是 async 委派型），不是"能不能跑起来"。

加固（SQLite 场景必做）：两个引擎（async / sync）都加 `PRAGMA journal_mode=WAL` + `busy_timeout=30000` 与连接参数 `timeout=30`——读写不再互斥、写**等待**而不是立刻报 `database is locked`。

验收标准：任务执行期间**并发打数据库接口**，原来 8 秒 500，修好后应为 200 且亚秒级；再**连续触发 2~3 个任务**确认不再死锁。

_备注：这条故障的迷惑性在于"服务是活的、健康检查也 200"——健康检查通常不碰数据库，所以看不出问题。凡是"健康检查正常、但所有业务接口都挂"的组合，先查数据库层。_

### 坑 12：多端点字段只改了一半 —— 以及「404 不等于路径错」

现象：同一家供应商下**图片能生成、视频不能**；视频任务 failed，错误是 `404 Not Found for url 'https://<厂商A域名>/.../tasks'`，看着像"接口路径写错了"、甚至像"这套应用不支持视频"。

根因（两层叠加，缺一层都定位不到）：

1. **供应商表按能力分了三列地址**（`base_url` 通用 / `image_base_url` / `video_base_url`）。填表时只改了其中一列，另一列还是默认值或上一家的地址——结果"图片走 A 家、视频走 B 家"，同一个 provider 的两种能力打到了两个不同域名。代码里的取值优先级是 **`类别地址 > 通用地址 > 内置默认`**，只要类别列被填过（哪怕是错的），它就赢，通用列填对了也没用。
2. 部分厂商**用 HTTP 404 表达业务错误**（火山方舟"模型未开通"返回 `ModelNotOpen`，状态码正是 404）。而多数 HTTP 客户端 / 框架的 `raise_for_status()` **只报状态码、丢掉响应正文**，于是"模型没开通"被显示成"路径不存在"。

排查动作：

1. **逐类别核对地址**：把 provider 的三列地址全部打出来并排看，别只看通用的那一列；确认每个类别指向的域名与该厂商一致（`ark.cn-beijing.volces.com` 与 `dashscope.aliyuncs.com` 这种一眼可辨）；
2. **看正文，不看状态码**：拿库里的 `run_args`（含 `provider` / `api_key` / `base_url` / `input`）**原样重放**到该厂商接口，打印状态码 **+ 原始响应体**。404 的正文里往往就是真正的原因；
3. 判"模型名 / 开通状态"类问题前，用供应商的**模型列表接口**（如 `GET /api/v3/models`）核对真实调用 ID 与在售状态，别信 UI 展示名。

加固（可选，但很值）：把厂商适配层的 `raise_for_status()` 换成**带响应正文的版本**（解析 `error.code` / `error.message` 拼进异常消息）——否则同类故障下次仍然会伪装成"404 找不到路径"，排查要重走一遍。

判据：**同一 provider 下，一个类别的能力通了、另一个类别不通 → 先怀疑多端点字段只改了一半，再怀疑功能不支持。**

### 坑 13：控制台显示「已开通」≠ API 能调用 —— 模型可能已进入退役流程

现象：平台控制台（如火山方舟「开通管理」）里目标模型状态明确是**「已开通」**、甚至还挂着**未消耗的免费额度**（如 200 万 tokens），但应用侧调用一律失败；把模型名换成控制台展示的那个之后仍然失败。界面与 API 各说各话。

根因：**平台侧的「服务开通状态」和「API 可调用状态」是两件事**。模型进入退役（deprecation）流程后：

1. 官方公告会给三个时间点：通知日 / **Deprecation Date** / 关停日（Deactivation Date）；
2. 过了 Deprecation Date，**基于该模型的新调用不再受理**，但控制台的「已开通」标记与免费额度**不会立刻消失**——那只是开通/计费层面的历史记录；
3. 结果就是「界面说已开通、API 说找不到」。

取证：列平台在售模型清单，看目标模型的 **status 字段**，与 API 返回的错误码交叉判断。

```python
# 火山方舟：列出账号可见模型及状态
# GET https://ark.cn-beijing.volces.com/api/v3/models
# Header: Authorization: Bearer <API_KEY>
# status 字段含义：
#   缺省 / "Active"  → 在售；账号未开通时调用报 ModelNotOpen
#   "Retiring"       → 退役流程中；调用报 InvalidEndpointOrModel.NotFound
#   "Shutdown"       → 已关停
```

火山方舟错误码对照：

| 返回 | 含义 | 处置 |
| --- | --- | --- |
| `ModelNotOpen` (404) | 模型在售、账号未开通 | 去控制台开通该模型 |
| `InvalidEndpointOrModel.NotFound` (404) | 模型 ID 错，**或**该版本已退役不再受理 | 查在售清单，按官方推荐换模型 |
| `AccessDenied` (403) | 模型未对账号开通 | 去控制台开通 |
| `AccountOverdueError` (403) | 账户余额低于零 | 充值 |

排查动作：

1. 看到 NotFound，**先查在售清单**（上面的接口）确认该版本是 `Retiring` / `Shutdown`，还是仅仅名字写错；
2. 确认退役 → 按官方公告给出的 **Recommended Replacement** 换模型 ID（不要自己猜一个"更新的"版本名）；
3. 换完原样重放：错误应从 `NotFound` 变成 `ModelNotOpen`（说明 ID 已落到一个在售模型上），剩下的就是让用户去开通。

判据：**控制台「已开通」+ API `NotFound` = 先怀疑模型退役，不要怀疑配置写错。**
定性要引官方公告的时间点（通知日/弃用日/关停日），不能只凭"我调用失败了"下结论。

## 汇报口径（对外输出，硬约束）

汇报面向业务人员，**只讲结果，固定四段，不得增删**：

1. **部署结果**：成功 / 部分可用；
2. **入口地址**：前端、后端、API 文档三个地址；
3. **能用什么 / 不能用什么**：不能用的逐项说缺什么（Redis？对象存储？API Key？）和补齐路径——**这一段的每一条都必须来自第 7 步冒烟的实际结论，不许凭依赖清单猜**；
4. **重启方式**：照日志哪两条命令。

**禁止输出**：部署原理、依赖判定过程、方法论叙述、坑位清单。判定依据最多一句话带过（"数据库用了项目自带的 SQLite 模式，所以不用装 MySQL"这个程度为止）。
