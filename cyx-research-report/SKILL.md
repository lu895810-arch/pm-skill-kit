# 数据溯源型市场调研报告（cyx-research-report）

## Purpose（目的）

提供一套**行业无关的通用市场论证方法论**，并配套暗色科技风单文件 HTML 模板。使用该 skill 生成的调研报告须满足：每个数据点可溯源、可信级分层标注、口径边界清晰、主次分明、去 AI 味、图文并茂。短视频工具报告只是它的一次落地实例，同一套链路可套用到任意行业与业务（消费品、B2B SaaS、制造、金融、医疗、本地生活等）。

区别于"堆数据的 PPT"：产物要求**每个数据点可溯源、可信级分层、口径边界清晰、主次分明**。

## When to use（何时触发该 skill）

- 用户要求撰写市场调研 / 行业研究 / 竞品分析 / 赛道评估 / 市场规模测算类中文研究报告。
- 用户强调「数据可溯源」「带来源标注」「可信级」「口径边界」「严谨可核验」。
- 用户明确要求「按我的调研报告模板 / 用 cyx 的调研模板 / 类似这种格式」生成报告。
- 交付对象是管理层 / 投资人、需要严谨与可信度背书的研究报告。

若用户仅需要简单的文字综述、不要求来源标注与可信级，可不触发本 skill。

## How to use（如何使用）

1. 复制 `assets/template.html` 作为报告起点（已含全部 CSS 与组件骨架，直接改内容即可）。
2. 按本 skill 的「通用市场论证链路（10 环）」与「数据可信级标签体系」组织内容与数据。
3. 严格遵循「五条红线」「脚注标注规范」「口径边界」「表达与写作要求」。
4. 用 `assets/template.html` 中的组件类（`.big` / `.grid3` / `.chips` / `table.t` / `.footnotes` 等）排版；SVG 内用 `<tspan>` 而非 `<sup>`/`<b>`；**装饰克制使用，遵守「八.6 避免 AI 塑料味」的纪律**。
5. 论证层遵守「八.3 逻辑闭环严谨、论证缜密不跳脱」；**Markdown 报告的骨架、层级标记与语言写法遵循 `cyx-md-style` skill**；视觉与通用语言约束遵循 `cyx-html-style` skill（去 AI 味、反塑料味、克制图文、论证不跳脱）；本 skill 只补报告场景的具体约束。
6. **模板纪律**：`assets/template.html` 中的示例文字仅为占位示范，**「一句话结论」「结论：」「内容模块标题」「数据表格示例」「徽章组示例」等空标签与占位词一律不得保留**，替换成具体内容后再交付。
7. 交付前逐项走「十五、交付前自查清单」。
8. **交付后把可复用的反馈沉淀回 skill**（三个 skill 一视同仁）：用户每提一次修改意见，按「十六、技能自我进化机制」判定是否具有跨报告通用性；通用则按 16.4「主责 skill」列回写到对应文件（`cyx-md-style` 六 / `cyx-html-style` 七 / 本文件十六），必要时同步 `assets/template.html` / `cyx-html-style/assets/cyx-html-style.css` / `scripts/check-template.py`，并在 `references/feedback-log.md` 留痕（含「归属 skill」列）。**不要只在当期报告上改完就结束。**

## 一、五条红线（任何时候不得违背）

1. **数据可信优先，绝不胡诌**：每个数据点必须有来源。来源不清楚、没把握的，**不得自信生成**；改为标注「推演 / 估算 / 抽样」并写明推导锚点。**「以事实为基础，宁可不写，不知道的请勿盲目自信生成」** 是这一红线的最高表述，凡与本条冲突的其他写法一律无效。**结论性内容（判断、定性、排名、趋势）同样适用：必须落到具体案例证据（主体 + 数字 / 时间 / 资料名），回查不到事实就整句删掉，不改成模糊表述保留（见八.20）。** 详见 cyx-html-style「数据可信强红线」。
2. **来源不同，必须拆开**：两个数字哪怕相邻，只要出处不同，就拆成两个脚注，绝不混在一条里含糊带过。
3. **口径边界要显式写清**：不同统计口径的数值不可直接加减对比，必须标出「统计口径不同」。
4. **从汇报视角写作，去 AI 味**：不用「读法 / 小结 / 上一版 / 划重点 / 简言之」等元语言；不出现「一句话结论 / 解读 / 总结 / 核心要点」及任何单字双字空标签；直给结论，不教读者"怎么读"。
5. **论证不跳脱**：任何判断都必须写出「前提 → 推断 → 结论」，不允许"数据后面直接跟结论"；结论范围不得超出数据范围。

## 二、通用市场论证链路（10 环，行业无关）

```
① 市场大盘 —— 目标市场总规模、增速、天花板（TAM 起点）
   ↓
② 需求侧 —— 谁在买 / 谁在用？按人群、场景、地域、行业切分
   ↓
③ 供给侧 / 品类 —— 市场里有哪些产品 / 服务形态？结构占比如何？
   ↓
④ 渠道与触达 —— 客户从哪获取信息、在哪成交 / 使用
   ↓
⑤ 生产与交付 —— 产品 / 服务怎么被生产出来、怎么交付（B2B 常是胜负手）
   ↓
⑥ 商业模式与钱 —— 钱从哪来、怎么分、谁赚最多
   ↓
⑦ 需求动机与痛点 —— 客户为什么买 / 不买？痛点多严重？
   ↓
⑧ 竞争格局 —— 现有玩家覆盖了哪些、缺口在哪
   ↓
⑨ 关键变量 —— 什么正在改变市场（技术 / 政策 / 宏观 / 渠道迁移）
   ↓
⑩ 机会与结论 —— 哪个细分增长快、我们该进哪块（综合前 9 环）
```

**关键认知**：①—⑩ 是通用骨架，不同行业的差异只在于**每环选什么指标**，取数逻辑一致。每环都要回答：**要回答什么 → 需要什么指标（含口径）→ 从哪个维度分析 → 去哪个链接取数 → 数据可信级**。

**行业适配示例**（同一链路，指标替换）：

| 环 | 短视频工具（原案例） | B2B SaaS | 消费品 |
|---|---|---|---|
| ① 大盘 | 短视频用户 / 工具市场规模 | 软件支出 / 细分赛道 TAM | 品类零售规模 / 增速 |
| ② 需求侧 | 五类创作者 | 企业决策者 / 使用部门 | 消费者人群画像 |
| ③ 品类 | 短剧 / 电商 / 广告视频 | 功能模块 / 部署形态 | 品类 SKU 结构 |
| ④ 渠道 | 抖音 / 快手 / 红果 | 直销 / 渠道 / 云市场 | 线上 / 线下 / 经销商 |
| ⑤ 生产交付 | 剧本→分镜→生成→剪辑 | 研发→销售→实施→交付 | 供应链→生产→分销 |
| ⑥ 商业 | 广告 / 电商 / 工具订阅 | 订阅 / License / 服务费 | 零售毛利 / 渠道分账 |
| ⑦ 动机痛点 | 效率 / 成本 / 爆款 | 降本 / 提效 / 合规 | 品质 / 价格 / 品牌 |
| ⑧ 竞争 | 底层生成器 / 工作流 | 头部 SaaS / 开源替代 | 头部品牌 / 白牌 |
| ⑨ 关键变量 | AI 模型能力 / 投流成本 | 云原生 / AI / 政策 | 消费分级 / 新渠道 |

## 三、数据可信级标签体系（①—⑤）

| 级别 | 名称 | 典型来源（行业无关的类型） |
|---|---|---|
| ① | 官方 | 政府 / 监管 / 统计局 / 行业协会 / 交易所公告 |
| ② | 第三方 | 咨询机构 / 数据监测 / 券商研报 / 行业协会报告 |
| ③ | 平台财报 | 上市公司财报 / 投资者关系（IR）披露 |
| ④ | 推演/问卷/行业估算 | 自采问卷、访谈、竞品定价、内部测算 |
| ⑤ | 媒体/媒体实测 | 行业媒体、产品评测、深度报道 |

**用法铁律：**
- 每个标签**必须显示类别名**（`① 官方`、`② 第三方`），不允许只写 `①`、`②③` 这种裸序号。
- **核心结论须有 ①/② 级来源支撑**；④/⑤ 级只用于「描述现象、提出假设」，不得单独下市场规模结论。
- 一条脚注可挂多个标签（如 `② 第三方` + `④ 行业估算`）。

## 四、脚注标注规范

**HTML 结构（正文角标 + 页底脚注）：**

```html
<!-- 正文内角标（紧跟数据点） -->
某平台 MAU &gt;7 亿<sup class="fn">1</sup>

<!-- 页底脚注区 -->
<div class="footnotes">
  <div class="fn-item"><span class="fn-n">1</span> 某平台 MAU/DAU，来自平台财报、第三方监测。<span class="tag l2">② 第三方</span><span class="tag l3">③ 平台财报</span></div>
</div>
```

**规则：**
- 每个引用数据点挂 `sup.fn` 角标；脚注写「来源机构 + 报告名称 + 可信级标签」。
- 脚注与角标**一一对应**，禁止「孤儿脚注」（有脚注无角标）。
- 具体来源在脚注里点名机构+报告名；**完整链接统一放进页脚「来源总索引」**，避免正文堆 URL。
- 逐条对应出处：当一组数据来自不同来源时，脚注里**逐条写明「数值 → 来源」**。
- **编号必须按正文首次出现顺序连续排列**（1、2、3…）。常见错误是编号按「来源加入时间」排——正文开头就出现 `[1][2][3][4][11][24][30]` 这种跳跃，读者无法顺着读。改稿补来源后务必重排一次：按首次出现位置重编号，并**把附录《来源链接》的整行条目一并按新顺序搬运**（不是只改首列编号，否则正文指向会整体错位）。重排后校验：正文首次出现序列 `== list(range(1,N+1))`，附录编号列亦为 `1..N`。
- **删来源时三处一起扫**：删一条来源，编号序号会整体前移，必须检查三处并同步 ① 正文角标 ② 附录《来源链接》条目（整行）③ 表格里的行内引用（如「企业联系方式」表的 `（来源 N）`）——第 ③ 处最易漏，漏了就指向错误来源。删完校验：被删主体的名称在全文残留为 0。
- 脚注编号用 `[a]``[b]` 字母时，与来源引用的 `[1]``[2]` 数字分开（见八.14）。

## 五、口径边界（高频陷阱，行业通用，必须显式标注）

以下"不可直接对比"的坑在任何行业都会出现。凡可能混淆处，在**该事实所在的章节就地写清**；属图表读法 / 评级依据 / 指标定义的口径，做成脚注（见八.14），不另起一段总述，也不单独设「证据边界」章节：

- **上游大盘 ≠ 目标细分市场**（如：网络视听规模 ≠ 短视频工具市场；行业总盘 ≠ 你的目标赛道）
- **流量/用户量 ≠ 收入/付费量**（如：MAU ≠ 付费用户；内容流水 GMV ≠ 上游工具收入）
- **单一环节成本 ≠ 全链路成本**（如：制作成本 ≠ 获客 / 投流成本；研发成本 ≠ 销售成本）
- **意愿 ≠ 行为**（付费意愿 ≠ 实际付费；渗透率[在用] ≠ 转化率[真掏钱]）
- **口径/年份/地域不一致不可直接对比**（不同统计机构、不同统计期、不同地域的数值）
- **机构估算 ≠ 官方普查**（媒体转述的估算 ≠ 机构官网原文 PDF；行业抽样 ≠ 全行业普查）
- **全量纳入数 ≠ 有效信息数**（如：共纳入 24 家 ≠ 已取得有效信息 22 家；分档、占比、汇总、横向归纳只对有效口径做，导语与标题必须写清用的是哪个口径，不能拿全量数当有效数用）
- **审阅免责语全文禁用**：「未经第三方核验」「正式引用前建议向厂商索取书面确认」「未附书面材料核验」「以上结论仅供参考」这类句子是写给审阅者的过程交代，不是写给读者的内容——正文、头部口径说明、页脚尾注都不出现。口径归属靠来源标签本身表达（「（**厂商自述**口径）」写到标签为止）；口径说明区只留**标签定义（图例）**；「向厂商索取报价」这类**行动项**归「待办」，不受此限。

## 六、推演/估算数据的标注法

当**没有权威普查**、只能推演或抽样时：

1. 明确定性：标注「行业抽样推演区间（**非全行业普查**）」「量级仅供参考」。
2. 写明推导锚点，用「推演逻辑」框逐条列出拆分依据（把原始基数、渗透率、折算系数写清楚）：
   ```
   A 类用户 X 万人 —— 某机构披露的用户基数（约 N 万），扣除 B 类与 C 类后推演。
   B 类用户 Y 万人 —— 全网总池约 M 万 × 渗透率 P%，剔除企业团队后推演。
   ```
3. 诚实提示：精确数字需「上线后自采问卷 + 后台画像回填」。
4. 若源头只是「媒体转述某机构估算、机构官网无原文 PDF」，脚注必须注明「媒体转述，非机构官方直接发布」。

## 七、竞品/玩家枚举的准确性

- **不低列**：用户说「不止这三家」时，核实数据源里实际有多少家，补齐被遗漏的。
- **不虚列**：数据源里只「被提及」、没有完整参数的玩家，**只补到「存在且各有侧重」层面，不伪造价格/能力等参数行**；需要参数则另找公开来源。
- 只引用有出处的玩家，每一个新补充都要能落到具体来源。

## 八、表达与写作要求

### 1. 通俗易懂且专业
- 专业术语首次出现时，用一句人话解释；面向非本行业读者（管理层 / 投资人）也要看得懂。
- 不堆术语、不炫技；把数据"翻译"成结论，不只罗列数字。

### 2. 简洁（一句话原则）
- 能用一句话说清的，绝不用两句话。
- 删冗余修饰、重复强调、废话连接词；每页只保留一个核心结论，一句话点透。

### 3. 逻辑闭环严谨、论证缜密不跳脱
- 每页 / 每板块：数据 → 结论 → 支撑，链条完整，不出现「结论无数据支撑」或「数据推不出结论」的断点。
- 前后口径一致：同一指标全文用一个口径，版本 / 年份差异显式标注，不自相矛盾。**同一口径在多张图 / 表里重复出现时（如企业分类家数、价格区间、样本数），数字必须逐一对齐**——改文字描述前先核对源数据，发现不一致要回改图表数值本身，不能只改文字，否则改完仍自相矛盾。
- **两套分档并存要显式区分**：同一批对象出现两套分类时（如第一节按「可落地性」分 A/B/C/D 档，后一节按「处理进度」分已了解 / 不匹配 / 待回访 / 未触达），在第二套的导语里点明**分档角度不同**，并给两套各自用不重名的档位名。只写「分成四档」，读者会以为是同一套分档前后矛盾。
- **链式论证**：每个判断由「前提（可核查数据）→ 推断（因果 / 换算，必须写出来）→ 结论（不超出前提支撑范围）」三步组成，缺一步即判为跳脱。
- **呈现方式：让三步在自然段落顺序中出现，不要为三步加标签。**
  - ❌ 左侧三行加粗「**前提**：…」「**推断**：…」「**结论**：…」三件套——这是元符号，教读者"怎么读"，与"一句话结论"是同一病灶。
  - ✅ 三个段落按"事实 → 因果 → 判断"自然展开，用句首承接词（"数据上看……""原因在于……""因此……""所以……"）过渡。
  - 检验：删掉所有可能为这三步添加的标签后，读者仍能从段落顺序看出"为什么这样判断"——能，则论证合格；不能，则论证本身缺环节。
- **反跳脱自检三问**（每写完一个判断过一遍）：
  1. 结论的依据在上文出现过吗？没有 → 补数据或删结论。
  2. 从依据到结论的推理过程写出来了吗？没有 → 补一句因果或换算。
  3. 结论适用范围超出数据范围了吗？超了 → 收窄表述或标注边界。
- **禁止的跳跃（报告高发）**：
  | 跳脱写法 | 问题 | 改成 |
  |---|---|---|
  | 「渗透率低，所以空间大」 | 缺推断：低渗透也可能是需求不成立 | 「渗透率 3%，且调研显示 71% 用户有未满足的 X 需求——需求存在但转化受阻，增量在 Y 场景」 |
  | 「A 增速快，所以 A 会赢」 | 增速不等于终局 | 「A 增速 40% 但基数仅为 B 的 1/5，按当前增速需 4 年追平」 |
  | 「数据显示……」直接跟结论 | 省略推断环节 | 「数据显示 X，因为 Y 机制，所以 Z」 |
  | 样本 128 人推出全行业结论 | 以偏概全 | 「在 N=128 样本中……；外推到全行业需谨慎，因为……」 |
  | 板块内换口径不说明 | 前后不可比 | 「此处改用 2025 年 12 月口径，原因是……，与上节差异为……」 |
- **衔接纪律**：相邻段落有显性承接（「因此」「但」「进一步」「反过来看」），不靠读者脑补；板块内未解矛盾显式写出，不略过。

### 4. 图文并茂
- 每页至少一种可视化（表格 / 卡片 / 徽章组 / SVG 图 / 大数字），避免纯文字堆砌。
- 关键结论用大数字卡片 `.big`；对比用表格 `table.t`；要点用徽章 `.chips`；结构用 `.grid3/.mini` 或 SVG。
- 图必配一句话解读，不裸放图。

### 5. 去 AI 味（强约束）
| 禁用 | 改用 |
|---|---|
| 「读法 / 小结 / 划重点 / 简言之」单独作标题或角标 | 直接删掉标签；正文需要时正常表达，不硬换词 |
| 上一版只作对比、仅供对比、不混用 | （直接删除，从汇报视角写结果） |
| 先看口径 / 口径红线 | 口径说明 / 口径边界 |

| **核心要点 / 核心观点 / 核心结论** | **用具体内容名** |
| **三步走 / 四个维度 / 五个关键 / 三大趋势** | **直接列"第一步做什么、做什么、做什么"**；如要结构列具体名称 |

| **保姆级 / 吐血整理 / 敲黑板 / 划重点** | **删**（营销词） |
| **可圈可点 / 不容错过 / 深度好文 / 长文慎入** | **删**（营销词） |
| **从图可见 / 如上图所示 / 数据告诉我们 / 一目了然** | **直接说图说明了什么**（元语言） |
| **「解读 / 看清 / 看懂 / 速读 / 速览 / 洞察 / 观察 / 拆解 / 解构」作小节 / 小标签（常带左侧装饰条）** | **删标签，直接写内容**（"读法"动词作标签 = 教读者"怎么读"） |
| **"X 解读 / X 看清 / X 速读 / X 洞察" 等 "X + 读法动词" 组合** | **改用具体内容名**（不说"市场解读"，说"市场盘子的三个口径差异"） |
| **单字 / 双字空标签单独作小节或段落标签**：**解读 / 小结 / 总结 / 要点 / 核心 / 提示 / 说明 / 结论 / 观点 / 看法 / 洞察 / 分析 / 拆解 / 速览 / 一览 / 概览** | **用具体内容名替换**（形式词单独作标题 = 零信息量；"结论"要写成"付费率 3% 是主要约束"） |
| **"值得注意 / 需要注意的是 / 显而易见 / 众所周知 / 不难看出"** | **删**（提示读者注意 = 元语言，直接陈述） |
| **"前提 / 推断 / 结论" 作为段落或小节的标签**（典型写法：左侧三行加粗「前提：…」「推断：…」「结论：…」三件套） | **删掉所有三件套标签**，三步在自然段落顺序中呈现，用句首承接词（数据上看 / 原因在于 / 因此 / 所以）让读者自然看到链条；给三步加显眼标签 = 教读者"怎么读"，与"一句话结论"是同一病灶 |
| **用修辞动作做标题或角标**：如「机制推演 / 路径推演 / 逻辑梳理 / 推导过程 / 框架搭建」 | **不要把写作动作放进标签**；改成内容名：机制推演 →「影响因素」或「形成原因」；路径推演 →「变化过程」；逻辑梳理 →「关系」；推导过程 →「计算依据」。若没有必要区分，直接删掉角标。 |
| **eyebrow 元描述 chip**：「cyx-research-report · 暗色科技风 · 整理自xx」「本文采用 xxx 风格」「整理自 xxx 文档」等描述本文格式 / 风格 / 来源的标签 | **删**（标签讲的是"这文档用了什么风格"，与读者要读的内容无关；只在确有信息价值时挂，如数据来源标注） |
| 赋能、抓手、闭环、颗粒度、组合拳等空话 | 具体动作与结果 |
| **callout / 小节标题用「对话口吻」包装主题**：「X，一句话说清」「X 怎么看」「X 值得注意的一点」「X 的『别人没有』」 | **直写该段在讲的事实**，如「两种产品结构的核心差别」「模型策略的差异」「LumenFlow 独有或领先的能力」；标题要能独立说明内容，不把段落主题说成聊天口吻 |
| **收束词「说到底 / 总而言之 / 一句话」** | **删**，直接落事实结论，不绕弯引导读者 |

写法原则：**直给内容，不教读者"怎么读"；用短句和数据说话，不用排比口号。**

**不要机械清洗词语：**「分析」「推演」「论证」「总结」等词在正文中有明确对象和动作关系时可以正常使用；只禁止它们脱离内容、单独充当小节标题、角标或装饰 chip。优先删除无信息的标签，不要为了避开某个词而硬换成另一套同样生硬的词。

**机检对齐**：本节「对话口吻标题」「收束词」两条已写入 `scripts/check-template.py` 第五节硬规则机检，生成或修订后跑脚本即可拦住。

### 6. 避免 AI 塑料味（视觉与表达克制）

报告里最容易出现"AI 塑料味"的，是以下几类"标签 + 装饰"组合。**遇到时直接删或换成具体内容**：

- **空标签当标题**：「一句话结论 / 解读 / 总结」「核心要点 / 观点 / 结论」「解读 / 小结 / 总结 / 要点 / 核心 / 提示 / 说明 / 结论 / 洞察 / 分析 / 速览 / 概览」等单字双字形式词单独作标题——一律删除标签，换成具体内容名（标题要能独立说明"这节讲什么"，而不是"这是一句结论"）。
- **「前提 / 推断 / 结论」三件套作段落标签**（常带左侧装饰条、套 `.define-box`）——删除标签，让三步在自然段落中呈现；这是"教读者怎么读"的元符号，与"一句话结论"同一病灶。
- **修辞动作标签**（「机制推演 / 路径推演 / 逻辑梳理 / 推导过程 / 框架搭建」）——删除或改成具体内容名；例如「机制推演」改为「形成原因」，「路径推演」改为「变化过程」，「推导过程」改为「计算依据」。
- **eyebrow 元描述 chip**（"cyx-research-report · 暗色科技风 · 整理自xx"、"本文采用 xxx 风格"、"整理自 xxx 文档"）——描述本文格式/来源的元标签，与读者要读的内容无关，删；只在确有信息价值时挂。
- **单独"解读 / 看清 / 看懂 / 速读 / 速览 / 洞察 / 观察" 作小标签**（常带左侧装饰条、套 `.define-box`）——删除标签，直接写内容；这是"读法"变种。
- **空洞数字模板**：「三步走 / 四个维度 / 五大关键 / 三大趋势」——列具体名称（"市场盘子的三个口径差异"，不是"三个口径"）。
- **emoji 装点**：「⚡ 干货」「📌 划重点」「💡 注意」——全删。
- **摘要页三件套**：「一句话结论」+ 三张大数字 `.big` + 板块编号——不要模板化套用，因内容而异。
- **装饰过载**：段落前大竖条 + 嵌套卡片 + 大数字 + 徽章堆叠——一个板块一种视觉，装饰只为信息不为"好看"。
- **元语言**：「从图可见」「如上图所示」「数据告诉我们」「一目了然」「值得注意」「不难看出」——直接说图说明了什么。

**装饰删除纪律**（仅在有信息价值时使用）：
- 左侧发光竖条：仅 `.define-box` 的"口径说明 / 边界 / 反直觉结论"框、`.info-title` 的小节分隔。**`.define-box` 严禁套读法标签（"解读 / 看清 / 洞察 / 观察 / 速读"等）。**
- 大数字 `.big`：仅数据有冲击时（如"市场规模 62.8 亿"），不当装饰。
- 徽章 `.chip`：仅短标签 / 分类时（如"① 官方""② 第三方"），不堆叠。
- 卡片 `.mini` / `.grid3`：仅多组并列信息时；不要"一段话也要装进卡片"。

**报告专属的克制建议**：
- 来源标注的脚注与可信级徽章**是该报告独有的必要组件**，不属于"塑料味装饰"，但仍遵守「组件只为信息」的纪律，不堆叠、不当标题用。
- 表格行高亮 `.hl` / `.hl2` 用作"重点行"提示，但不要全表都用，行高亮本身要稀缺。
- 公式 `.formula` 仅在解释口径换算或推导时用，不作普通强调手段。

视觉与语言风格的通用约束统一遵循 `cyx-html-style` skill（去 AI 味、反塑料味、克制图文）；本节只补报告场景下的具体落地约束。

### 7. 摘要页 / 顶栏 / 全文结构纪律

- **顶栏导航首位必须是「摘要」或「总览」**，即使全文只有 2 个板块也要有「摘要」置顶；它不与正文板块共享「1 2 3」编号体系，不编入 `1.x` / `2.x` 序列。
- **摘要页内容必须包含**：
  1. **核心结论 / 关键发现** block：2–3 条，每条用一段自然语言陈述「事实 → 推断 → 判断」，不写"核心结论"标签本身（直接以小标题为"关键发现 1 / 关键发现 2"等具体名，或用普通段落呈现）。
  2. 必要的总盘数据（如规模 / 增速 / 占比），但**不要"摘要页三张大数字 `.big` 卡片"的标准 AI 三件套**——大数字是稀缺品，有冲击时才有。
  3. 口径边界声明（如果全文口径多 / 易混）。
  4. 关联文档 / 上下文链接（如有）。
- **摘要不是"产品介绍"**：不要在摘要里只放定位标语、slogan、产品矩阵四件套（"知我 · 见心 · 观变 · 陪伴"那种），那不是摘要该做的事；摘要回答的是"这份报告的核心结论是什么、读者要带走什么判断"。
- **顶栏不要加 eyebrow 元描述 chip**：如「cyx-research-report · 暗色科技风 · 整理自产品方向讨论」「本文采用 xxx 风格」「整理自 xxx 文档」——描述本文格式/来源的元标签与读者无关，删。
- **章节顺序约束**：摘要 → 1 板块 1 → 2 板块 2 → …… → 来源。中间不要插入"目录""使用说明""致谢"等额外页面，除非报告对象明确要求。
- **每板块只解决一个核心问题**：板块标题要能独立说明"这节讲什么"；如一个板块里塞了多个问题，要么拆成多个板块，要么在小节中用 `1.1` `1.2` 明确分。

### 7.1 全文结构：层层递进链（强约束）

**报告不是「事实堆叠 + 附录清单」，而是一条从问题出发、逐层给出判断、每节都能在前面找到证据的推进链。**

写作前先问自己三个问题：

1. **这条报告要回答的核心问题是什么？**（如：「这个赛道值不值得进？能进哪一块？」）摘要就是这个问题的一两段答案。
3. **结论之前需要哪几层支撑？**（如：先校口径 → 再看大盘钱流 → 再点名 → 再归纳规律 → 再排除法得方向 → 再补缺口）。**从读者视角，每一节都要回答「看完这一节，我下一步能下什么判断」**。
3. **缺口和待采数据是不是「从论证里长出来」的？**——参见下一条「缺口不放附录」。

**结构递进四原则：**

1. **层层递进**：相邻板块之间必须有显性承接（「因此」「但」「进一步」「反过来看」），不靠读者脑补；板块末尾若有未解矛盾，显式写出而非略过。
2. **缺口不放附录**：当某节论证提到「某项数据拿不到」时，**不要把这一节独立成「5 缺口 / 5.1 缺口清单 / 5.2 回填 / 5.3 按缺口整理」三节**——那是「附录」而非「论证」。
   - **正确做法**：在论证末尾用一张「必须自采清单」框收尾，每条挂「问题 / 为什么前面没回答（指回主论证的哪个环节）/ 采集方式」三列，让「还要补什么」自然从主论证里长出来。
   - **错误做法**：单列「第 5 章 数据缺口与回填」，与前 4 章论证并列——会让读者感觉「这报告其实是 4 章 + 1 附录」。
3. **小节标题与子项命名按层级递进**——见下一条「三级标题」。
4. **不重复平铺页码**：章节内不再另加「第 1 节 / 第 2 节 / 一、二、三」等冗余序号；只保留 `1` / `1.1` / `1.1.1` 的层级编号。

**反例 → 正例：**

| 反例（章节并列、缺口独立） | 改成（层层递进、缺口融进论证） |
|---|---|
| 1 口径 / 2 大盘 / 3 逐家 / 4 规律 / **5 缺口（5.1 缺口清单 + 5.2 回填表 + 5.3 按缺口整理）** | 1 口径 / 2 大盘 / 3 逐家 / 4 规律（4.1 五条规律 + 4.2 排除后只剩一条 + **4.2 末尾一张「必须自采」表，每条指回 3.x / 4.x 哪个环节**） |
| 「5.1 缺口清单」独立成节 | 把缺口作为 4.2 的收尾表格，融进论证 |
| 「5.2 回填表」独立成节（Vidu / LibTV / Runway / Luma …） | 数据直接落到 3.2 / 3.3 / 3.4 对应表格的可信级列 + 脚注，不再单独列 |
| 「5.3 按缺口整理」独立成节 | 删，因为 4.2 末尾「必须自采」已经覆盖 |

**自检三问**（每写完一节问一遍）：
1. 看完这节，读者能往下下什么判断？还是只能再记一堆事实？
2. 这一节是不是从上一节「自然推出来」的？还是跳过去的？
3. 如果这一节提到「某数据没拿到」，它是作为缺口收尾在论证末尾，还是被拆成独立章节？

### 7.2 三级标题：`1.1.1` 命名规则

在子节（`1.1` / `2.1` / `3.1`）内若有 ≥ 3 个并列项需要编号，使用三级标题 `1.1.1` / `1.1.2` / `1.1.3` 等：

- **何时使用**：子节内并列项 ≥ 3 时使用，1–2 个并列项直接用 bullet 即可，不需要三级编号。
- **何时不要使用**：不要为三级标题另起新节（`<section>`）。三级标题是**子节内的并列项**，不是新的板块。
- **编号连续**：在父节 `1.1` 内从 `1.1.1` 开始连续编号；若改顺序，整段重排不要留空号。
- **示例**：「3.3 各家可信级说明」下有 5 项并列，分别为 `3.3.1 可灵 / 3.3.2 海螺 / 3.3.3 Runway / 3.3.4 Pika / 3.3.5 Vidu`——这是常见用法。
- **常见场景**：缺口整理、规则列表、案例分组、可信级分档等。

**反例**：把 `5.3.1 / 5.3.2 / 5.3.3` 当作独立章节写——那是 5.1 / 5.2 / 5.3 三节，不该用三级编号。

### 7.3 顶栏导航 / Brand 命名规则（详见 cyx-html-style「9. 导航 / Brand 命名规则」）

- **导航右侧**：保留章节原词（如「摘要 / 口径 / 大盘 / 逐家 / 规律 / 来源」），不要凝练为逻辑链。
- **导航左侧 brand**：放「一句话点全文」的对仗短语（5+5 字数对仗），不放文件名式 brand、不放 eyebrow 元描述 chip。
- **不要给 nav 项加序号**（不要「1 摘要 / 2 口径」），nav 是目录而非序号。
- **导航标签 = 正文大节标题的镜像**：正文大节叫「创作方式」，导航也叫「创作方式」，**不准各写各的**（如正文「创作方式」、导航「创作范式」不同步）。改正文大节标题时，**同步改导航**；导航项与正文 `h2` 逐字一致，改一处漏一处会留下断链式割裂。

### 8. 报告定位纪律：只陈述市场事实与结论，不作自证

调研报告的定位是「把这门生意/这个市场看清楚」，**不是替某一方的方案做证明**。凡把报告写成「先设定我方方案成立，再层层论证它合理」的，一律推翻重写。

- **不得预设自家方案最优**。禁止出现「我们的方案最优 / 差异化的立足点是…… / 对我们的启示 / 本项目的定位在于……」这类自指框架；如确实需要落到「对本项目的参考」，改为中性的「可供参照的要点」，且只陈述公开事实，不作优劣评判。
- **立项设想 ≠ 市场结论**。项目文件里的预期（如「某价格带尚无强势玩家」）只能作为「立项时的预计」引用，并紧跟核查结果；不得把它当行业共识写在结论段，也不得用无主语引语（「行业里常说」「有人说」）冒充来源。
- **判断句必须可追溯**。每个结论都要能指回附录里的具体条目；来源不足就删掉，不留「待补 / 待核」。
- **不设元叙述章节**。禁止单独成章的「论证链路」「事实复核与勘误」「修订记录」「证据缺口」；缺口、边界、修订结论全部写进它本来对应的那一章（如分项报价缺口写进价格分层节、课标映射缺口写进课程节）。改稿记录不入正文。
- **数据出现处就近标出处**。不只是脚注体系：摘要 KPI 卡、图表说明、价格区间等数字出现的地方都要紧跟 `[N]` 或「来源：……」，并写清是公开口径还是内部口径。
- **KPI 卡 `.tag` 只留实质口径**。标签写数量分层（「12 家核心，8 家相邻」）或样本性质（「2026 政采样本 [11]」），不写「来源：《项目需求说明书》第 N 节 ·」这类行政前缀，也不加「（公开渠道归档）」「（仅供参考）」式括号补语——出处由 `[N]` 与页脚统一承担。
- **结论章写法**：正文只写「结论一/二/三……」，每条是「依据 + 限定 + 一句判语」。**不要单设「证据边界」章节，也不要写「以上结论全部来自……未实测 / 未询价 / 未跑样课 / 未做课标映射 / 不对任何方案作优劣判断」这类段落**——这类审阅免责语全文禁用（见五），页脚尾注也不留；正文里同类的「上述判断全部来自公开页面，调研未登录试用任何产品」句尾、以及「前文梳理了……以下四条结论只依据公开来源」式章首元叙述，一并删掉。章节标题与导航随之简化为「结论」。

### 8.1 前置现状对照栏（唯一允许的自指栏目）

报告允许在正文前（摘要 / 结论之前）设一栏，把我方现状与调研结论逐条对照，回答「我们的做法是否合理」。这是 `八.8` 的唯一例外——**自指只允许出现在这一栏，且只允许做对照，不允许做自证**。

写法约束：

1. **现状事实**：把我方做法按可核查要素写明（合作对象、交付物、数量、工具、课程组织方式）。**正文不挂「我方口径」「我方目标」这类括注，也不写「未附书面材料 / 以现场清单为准」这类核验边界**——口径归属与核验边界放到报告头部的「文档说明」区，一句带过（如「另在正文前设『我们的现状与行业对照』一栏，该栏为内部口径」）。**说明性文字不进正文**是本栏第一位的语言纪律，详见第 11 条。
2. **判断标尺取自本报告**：对照必须用报告已有的分析框架（建设形态五类、合作模式六类、五件套等），并**指回小节号**（如「依据 2.1、2.3」）。禁止另造一套对照维度，也禁止用「行业领先 / 业内普遍做法」这类无来源断言充当标尺。
3. **只回答「哪几处一致、哪几处没有对应」**：逐项写「已经做到 / 还没做 / 这次没涉及」，不作优劣评判；「建议补齐 ××」这类行动项不进本栏，归「待办」章节。
4. **判断落在对照结果上**：判语写明「差距落在哪几个环节」，不写「我们的方案更优 / 差异化立足点」。
5. **不编入正文编号序列**：前置栏用独立编号（如 `0`）或独立名称，正文板块仍从 `1` 起；nav 首位挂它，正文 `1.x`–`N.x` 编号不动。
6. **标题同规格**：栏目名与小节标题按 `cyx-html-style`「8. 标题语言风格」写，不用「现状分析 / 自我评估」这类描述性前缀；板块副标题（`pdesc`）可放一句判断。
7. **三段式结构（固定）**：`现状 → 坐标 → 逐条对照+结论`，三段各自成页。
   - **0.1 现状**：先用一句**总结／目标性陈述**开头（在做什么事、朝哪个目标走），再用「事项 / 我们的做法」两列表把事实拆开（合作对象、硬件、课程、上课工具、下一步），**不写成一段流水句**。总述句后**直接接表**，不用口语化破题腔（「其实就一件」「说白了」「眼下做的事，其实就一件：……」），也不写「具体是这几项」「归结起来是一句话」这类引子；**表后不加任何注解句**（不挂口径括注、不注明哪项是打算）。
   - **0.2 坐标**：只放「对照内容 / 所用框架 / 出处」三列表，交代对照维度与来源。**表前表后都不写说明句**（不写「标准全部来自报告本身，不另设一套」「对照只看有没有对应，不评好坏」），标尺由表格自明。
   - **0.3 逐条对照**：每条按「行业通行做法（→ 指回小节号） → 我方现状 → 一句对照结论」写，条目标题只写「维度名：结论短语」（如「建设形态：最轻的一档」），**不加「其一／其二／其三」序号，不加「落在」「同属」等衬词**；末段收束用报告自身的「小结」体例，把「对得上的几处 + 有三处不同 + 差距落在哪」讲完。
   - **每块必须有骨架，不许写成整段（本栏第二高频问题）**：一块 = 一句定位句（这类形态 / 模式是什么、通行做法是什么）＋ 2–4 条要点列表，要点以「维度标签：内容」起句（如「代表厂商」「我方的情况」「上课方式」「同类做法」「行业路径」）；`（依据 2.x）` 挂在**该块最后一条**。凡是把「这一档是什么 + 我方落在哪 + 差别在什么 + 上课方式」塞进一句话的，一律拆开。
   - **小结不写整段，分点**（2026-09-15 用户圈两段整段后定）：小结用要点列表，标签统一三字对仗——「对得上的」「有差别的」「站得住的」「要补的」，一条只讲一件事；原两段的内容按此拆开（对照结果拆前两条、方向判断拆后两条）。
   - **表后要点不复述表**：0.3 的五件套表后若再加要点列表，要点按**件名**起句（「课程、教具硬件：有对应」「平台与工具：我方用的是公开互联网软件」），不再抄表格结论列的原词。
8. **对照表的结论列只用三档取值，措辞说人话**：「已经做到」（可带括注，如「工具不是自研的」「投入最轻」）、「还没做」（同行的「我们的做法」列写「还没有」）、「这次没涉及」。不用「占两件」「缺三项」这类概括词充当列值，也不用「有对应 / 现状未包含 / 本次调研未覆盖」这类公文腔充当列值；概括只出现在正文与 `pdesc`。**标题与 `pdesc` 里的计数概括，必须与「结论」列逐行数出来的结果一致——写完把列值数一遍再定标题**（2026-09-15 实测：标题写「占两件」，表里三行「已经做到」，被用户圈出）。
9. **语言**：事实与结论都写完整书面句，不用「提供电脑数十台」这类电报式短句，也不堆四字口号；`pdesc` 写「起步路径对得上，交付要件差三处」这类「一致项 ＋ 差异项」并列句。自称与表格语体见第 13 条。
10. **去 AI 腔（本节高发，重点查）**：禁用模板脚手架与自我解说——「归结起来是一句话」「只回答一个问题」「其一／其二／其三」「合起来看」「下面逐条比对」「因此每一条结论都能指回具体出处」「标尺不另立」；禁用口语化破题腔——「其实就一件」「说白了」。0.1 的总述句写总结／目标性陈述（如「……向打造有口碑的 AI 教室品牌迈出第一步」）。**小节主标题不用口语引导语**——「拿什么来比」「一条条比下来」这类读着随意，改用专业且对仗的短语：0.2「对照标尺：……」、0.3「对照结果：……」（2026-09-15 实测：口语标题被用户圈出，要求「通俗易懂且专业、对仗」）。
   - 条目标题直接写「维度名：结论短语」（如「建设形态：最轻的一档」「合作路径：单校样板校」「交付要件：五件套里占两件」），**不加序号，不加「落在」「同属」等衬词**；收束段用报告自身的「小结」体例。
   - **不设栏目说明框（`define-box`）**：0.1 / 0.2 的页顶与表后都不放定位说明、核验边界、免责声明。白话化解决不了这个问题——说明性文字一律不进正文，见第 11 条。
   - 段内用「区别在 A：……」这类直陈，不用「区别在于，这一档……用的是……，我方用的是……」的对称排比。
11. **说明性文字一律不进正文（本栏最高频问题，重点查）**：凡「交代这一栏怎么写的、数据可不可信、哪项还没发生」的句子，都属于说明性文字，正文里一条不留，只留在报告头部的口径区。
   - 五类禁用：① **栏目定位说明**（「本栏的行业侧依据取自……」「这一栏不评判……只回答一个问题」）；② **口径括注与免责声明**（「（**我方口径 / 我方目标**）」「以上为我方内部信息，没有配套书面材料」「设备台数以现场配置清单为准」「未经第三方核验」「正式引用前建议向厂商索取书面确认」）；③ **状态与时态注解**（「『下一步』是打算，还不是已经发生的事」）；④ **方法论自述**（「标准全部来自报告本身，不另设一套」「因此每一条结论都能指回具体出处」）；⑤ **表格导语与收尾**（「具体是这几项」「逐件对照如下」「对照只看有没有对应，不评好坏」）。
   - 判断标准：**删掉这句，读者还能不能看懂？** 能看懂就删。事实与判断照写（现状要素、对照结论、依据小节号），只是不再解释「我是怎么做的、可信度多高」。
   - 口径信息不丢失：栏目的口径归属移到头部「文档说明」一句（「……另在正文前设『我们的现状与行业对照』一栏，该栏为内部口径」），与「口径说明」区并列，正文不再重复。

12. **叙述主体是人（我们），不是文档，也不是「本次调研」这个活动（本栏另一处高发机器腔）**：本栏视角是「做这次调研的人」，不是「报告」这个载体，也不是「调研」这件活动。禁用两类主语——
   - ① 把文档／章节当主语：「报告把……归成五类」「报告里称……」「2.2 的结论是……」，标题里也不出现「报告」（如「用报告已有的三组框架」）。
   - ② 拿「本次调研」当主语：它是活动名，不是人。「AI 教室的落地形态，本次调研归成五类」应写成「AI 教室怎么落地，我们这次归成五类」；「本次调研未覆盖」写成「这次调研没涉及」。
   - 判断标准一句话：**这句里的动作是谁做的？** 是我们在调研过程中做的，主语就写「我们」；是厂商做的，主语写厂商名。文档与活动都不会「归成」「认定」「得出」，它们只记录、只发生。
   - 同类一起查：`（依据 2.x）` 保留（出处标记），但**不要**用「2.x 的结论是……」「本节认为……」去领起句子——结论归我们，小节号只作出处。

13. **汇报者语体：自称「我们」，表格说人话（本节第三处高发机器腔）**：把这一栏当成「我在向人汇报」来说，不是填规格书。
   - **自称统一用「我们」，整栏不出现「我方」**——「我方」是合同／公文语（「我方与××合作」「要求我方先提交方案」），汇报时说的是「我们」。
   - **表格行值写白话完整句，不用分号并列的规格书句**：不写「配置电脑数十台；不含教具与课堂采集设备」，写「配了数十台电脑，没有教具和课堂采集设备」；不写「自行配套的一套 AI 课程，以一个个项目实战为单元组织」，写「课程是我们自己配的，一课一个项目实战」。
   - **列头用人话，不用表结构语**：「要素」→「事项」，「我方现状」→「我们的做法」，「用哪组框架」→「所用框架」（0.2 表首列「比什么」→「对照内容」），「对照结论」→「结论」。
   - **条目标签同步**：「我方的情况」→「我们的做法」。
   - 判断标准一句话：**这句话像是「我在跟人汇报」时说出口的吗？**「我方」「配置电脑数十台；不含……」都不会出现在对话里。
   - 适用范围：本栏专用。其余正文仍按第 10 节用「本次调研」作主语，不出现「我们」。

14. **行业术语要给白话定义，不能拿同义改写当解释（本栏第三类读者障碍）**：块标题或定位句里出现行业说法时（如「单校样板校」「SaaS 云平台型」），定位句要把这个词**拆开讲清楚**——是什么、为什么叫这个名字、谁在做、怎么起作用；**不能只给一句同义改写**（「我们走的是『先在一所学校做试点，做出样板再复制』这一类，调研里叫单校样板校」——把词换了种说法，非本行业读者仍不知道它指什么）。做法：定位句讲「是什么」，再补一条 **为什么叫「××」** 讲命名由来与作用，主体名单、放大路径照旧。判据：**非本行业的人读完，能不能用自己的话把这个词复述一遍？**
15. **我方现状的主语是我们自己，不用观察动词（本栏第四类机器腔）**：写我方现状只写「我们做了什么 / 还没做什么」，**不写「（我们）没看到某种材料」**——「没看到跟 2025 版指南的对标说明」是审阅材料时的观察动作（AI 扫文件的口径），不是汇报自家情况的说法，应写成「还没按 2025 版指南逐条对标」。同类禁用：没看到 / 未见 / 未发现 / 材料里没有。判据：**这句话的主语是我们，还是「材料」？**

16. **术语要给标识，让读者一眼看出「这个词有解释」**（第 14 条术语白话定义的配套做法）：写出白话定义的那个词，后面紧跟一个标识——HTML 侧 `<span class="tag term">术语</span>`（青底虚线小徽章），Markdown 侧写 `〔术语〕`。
   - **默认不启用，用户明确要求才加**（2026-09-14 同日实测：本报告加上徽章后用户要求撤下，回到无徽章版本；白话解释本身承担全部职责，标识属可选项而非标配）。
   - **只标非本行业读者猜不出意思的词**（如「SaaS 云平台型」「单校样板校」）；本行已自明的词（「五件套」「师资培训」「课程」）不标。
   - 标识是「这里有解释」的路标，不是强调装饰；一页标满等于没标。标在**词**后面（标题里的词标在标题里，段落里的词标在该词后），不标在段落末尾。

| 「第二部分把厂商交付的东西归成五件套——……，各家只在配比上不同。逐件对照如下。」 | 表格导语 | 「……各家只在配比上不同。」（去掉「逐件对照如下」） |
| 0.3 每块写成一大段（一句话里塞进「这一档是什么 ＋ 我方落在哪 ＋ 差别在什么 ＋ 上课方式」四件事） | 整段流水句，页面上一堵字墙，读不出层次 | 拆成「一句定位句 ＋ 2–4 条要点列表」，要点按「维度标签：内容」起句，依据标注挂最后一条（见第 7 条） |
| 「报告把 AI 教室的落地形态归成五类」 | 把文档当主语（机器腔）；AI 教室不是报告归的，是我们调研归的 | 「AI 教室怎么落地，我们这次归成五类。」 |
| 「交付要件：五件套里占两件」（同一页表格里三行写着「已经做到」） | 标题计数与「结论」列的列值口径矛盾，读者一数就穿帮 | 「交付要件：三件已经做到，两件还没有」（写完把列值逐行数一遍再定标题，见第 8 条） |
| 「报告把厂商与学校的合作归成六类……报告里称**单校样板校**」 | 同一句里「报告」出现两次当主语 | 「厂商和学校怎么合作，我们这次归成六类。……调研里叫**单校样板校**。」 |
| 「2.2 的结论是自下而上的放大路径」 | 把章节当主语 | 「这一类厂商走的是一条从下往上放大的路（依据 2.2）」 |
| 「0.2 对照的坐标：用报告已有的三组框架」 | 标题里出现「报告」，文档视角 | 「0.2 对照标尺：调研归纳的三组框架」 |
| 「厂商自述数据未经第三方核验，正式引用前建议向厂商索取书面确认。」（口径说明区尾句） | 审阅免责语——写给审阅者的过程交代，AI 视角 | 整句删除；口径说明只留标签定义（图例），审阅提示全文不出现（见五） |
| 「0.2 拿什么来比：调研归出的三组框架」「0.3 一条条比下来：两处对得上，一处有差距」 | 口语引导语当标题，随意不庄重 | 「0.2 对照标尺：调研归纳的三组框架」「0.3 对照结果：两处对得上，一处有差距」（标尺／结果对仗成套） |
| 小结写成两段整段（一段塞对照结果四件事、一段塞方向判断两件事） | 整段黏连，读着费劲 | 分四条要点，标签三字对仗：「对得上的／有差别的／站得住的／要补的」，一条一件事 |
| 「我方与龙高北中学合作，在该校建一间 AI 教室」 | 「我方」是合同／公文语；汇报者说的是「我们」 | 「跟龙高北中学合作，教室建在他们学校」 |
| 「配置电脑数十台；不含教具与课堂采集设备」 | 分号并列的规格书句 | 「配了数十台电脑，没有教具和课堂采集设备」 |
| 列头「要素 / 我方现状 / 对照结论」 | 表结构语，不是人话 | 列头「事项 / 我们的做法 / 比下来」 |
| 结论列「有对应 / 现状未包含 / 本次调研未覆盖」 | 三档划分本身没错，措辞是公文腔 | 「已经做到 / 还没做（做法列写「还没有」）/ 这次没涉及」 |
| 「有配套课程，按项目实战组织；没看到跟 2025 版指南的对标说明」 | 「没看到」是审阅材料的观察动词（AI 口径）；我方现状要写我们自己的动作 | 「有配套课程，按项目实战组织，还没按 2025 版指南逐条对标」 |
| 「我们走的是『先在一所学校做试点，做出样板再复制』这一类，调研里叫**单校样板校**」 | 拿同义改写当术语解释，非本行业读者仍不知道这个词指什么 | 「我们走的是其中一类——**单校样板校**：先集中做好一所学校，把 AI 课真正开起来，课程怎么排、设备怎么用、课时怎么安排，都在这一所里跑通。」＋ 一条「**为什么叫「样板」**」讲命名由来 |
| 「单校样板校」「SaaS 云平台型」直接出现，词后无任何标识 | 读者不知道这是术语，也不知道后面有解释（看不懂就直接跳过） | 词后加标识：「最轻的一档是 **SaaS 云平台型**`〔术语〕`：……」 |
| 满页「术语」徽章，连「课程」「师资培训」也标 | 徽章泛滥，反而看不出哪个词真需要解释 | 只标本行业外猜不出意思的词；自明词不加 |

内容侧的骨架与标记（栏目在 md 里的部位、三段式骨架与表格形式、头部「文档说明」里的口径归属）同步 `cyx-md-style`「一、骨架纪律」的对应约定。

### 10. 叙述人称：站在调研视角，不写「正在干活的 AI」

报告主体是「调研」，不是执行核查的 AI。凡把写作 / 核查动作本身写进正文的，改为事实与调研结论表述：

| 禁用（过程自述 / AI 视角） | 改用 |
|---|---|
| 本轮 / 本次核查「显示……」 | 调研显示 / 公开信息显示 / 直接陈述结论 |
| 本轮没有登录试用 / 本轮未拨打 | 调研中未登录或试用 / 未拨打，未建立联系 |
| 已核实 / 补充核实 / 当日重新核实 | 已公开 / 新增 / 发布当日归档 |
| 需要说明：/ 需要记录的是： | 上述判断…… / 需要注意的约束是： |
| 我们 / 笔者 / 我认为 | 主语改为「调研」「公开资料」「企业公开披露」（**唯一例外见本节末**） |

- 「本报告 / 前文 / 下文」可作文档自称，保留。**「本轮」一律不用**，全文统一改成「本次调研」（作名词主语，如「本次调研纳入 24 家厂商」）；而「本次 + 动作」这类过程自述（本次核查 / 本次拨打 / 本次检索）仍要去掉。同一个意思在全篇只用一种表述，不要「本轮 / 本次调研 / 这次调研」混用。
- 过程留痕（何时检索、归档、补录、走访）只写在页脚或来源附录，不进正文论述。
- **唯一例外**：「第零部分　我们的现状与行业对照」——那一栏是我方现状的归纳与对照，按要求用「我们」的汇报者语体（见 8.1 第 13 条），不受本节限制；其余正文仍以「本次调研」为主语。**「我方」全文不用**。

### 11. 不写「提示词式」规则串，术语要白话

报告是给人读的，不是给 AI 下的约束清单。

| 禁用（提示词式 / 工程术语） | 改用 |
|---|---|
| 「口径纪律三条：访问日 ≠ 发布日；官网自述 ≠ 第三方验收」 | 拆成叙述句：分别说明每种材料的性质与边界（访问时间不等于发布时间；官网自述未经第三方验收） |
| 学段覆盖表述 | 只说「覆盖小学到高中」的表述 |
| 社区署名课例 | 教师署名的个别课例 |
| 课标逐课映射未见公开依据 | 与课程标准逐课对应的材料未见公开依据 |
| 硬约束 / 强约束 | 明确限制 / 现实限制 |
| 只当线索，不当事实证据 | 只作线索使用，不作为事实证据 |

**判断标准**：一句话念出来像不像人在介绍研究，而不是像在给模型下指令；出现 `≠`、`A；B；C` 规则串、括号式标签，基本都要改。

### 12. 密排内容分观点展示

一段话里并置多个事实（价格带 / 免费供给 / 中间档位三类数字），读者抓不住重点。凡一段里含 **≥2 个并列事实**，就拆成带小标题的要点列表。

**适用范围要放宽到正文段**：不只是卡片。`info-title` 标题下那种「一段话罗列多种供给 / 多家企业 / 多份材料」的段落（如「平台/中台类」「AI 通识/入门」「编程/机器人」），以及 `define-box` 提示框里的长段（如「课堂使用的现实限制」），同样要拆。第 4、5 章这类「地图」章节往往整节都是这种段落，须整节统一处理，不能只改用户指到的那一段。`define-box` 里拆点时保留一行 `.db-title` 作框标题，再接 `ul.pts`。

```html
<div class="mini yel">
  <h4>价格口径</h4>
  <ul class="pts">
    <li><b>主流价格带</b>：50–160 万，指带硬件的 AI 实验室；2026 年政采单校样本集中在 56–97 万。</li>
    <li><b>免费供给</b>：国家中小学智慧教育平台 AI 专区免费，人教、北大也提供官方通识内容。</li>
```


### 13. 不写章节过渡框与免责式说明段

两类别「看起来专业、其实没信息」的文案，删掉，不要靠它们撑结构。

**（1）阅读导引 / 过渡框**——`→ 以上为……；下文从……展开。` 这类箭头框，通篇重复出现（每章末尾一个）时尤其像模板。章与章的承接靠内容本身与标题，不靠一句「下文将……」；确需过渡时，用一句带事实的承接写进正文。

```html
<!-- 删 -->
<div class="bridge"><span class="arr">→</span><div>以上为范围与口径界定；第二章从<b>需求来源、市场格局与价格分层</b>三方面展开。</div></div>
```

**（2）免责式说明段**——`这些材料的性质并不相同：A≠B；C≠D。在取得 X、Y 之前，不对「……」「……」作出结论，本报告只作方向性判断。` 这类自述研究立场的段落，读者不关心，位置应让给事实。口径与边界**只在两个地方**写：① 该事实所在章节里就地写清（如 D 级来源「只作线索使用，不作为事实证据」）；② 页脚说明（含 `.footnotes` 脚注区）。不要在第 1 章另起一段总述，也不要在结论章单设「证据边界」段落。

**（3）前置性元描述**——段首先交待「本节要干什么」的话。典型写法：

- `本部分不逐家罗列，只做横向归纳，把……四件事讲清楚。`
- `本节将从需求来源、市场格局、价格分层三方面展开。`
- `下面我们来分析各家厂商的合作模式。`

删掉前置语，直接进入内容。**必要的覆盖范围限定要写进事实句里，不要另起一句交待**：

> 覆盖 24 家厂商中有实质 AI 教育业务的部分（重点为 A 类 7 家加 B 类 2 家），讲清「怎么建教室、怎么跟学校合作、课程长什么样、钱怎么收」四件事。

一句话同时交代范围与内容，没有「本部分要……」的空转。

- 判据：删掉这句后，读者对内容的认知有没有损失？没有 → 它就是前置话术。
- 例外：**文档信息块**（整理时间 / 数据来源 / 分组说明 / 覆盖厂商 / 文档说明 / 口径说明）属元数据区，保留；但**修订流水不进**——不出现「最近修订：××。本日 N 件事——（1）……（4）……」（见十五「修订记录不入报告」）。

**保留判断**：承载分析框架、且被下方图表/卡片直接使用的句子（如「全篇主线五段：企业 → 业务 → 软件 → 课程 → 课程内容」）属于正文骨架，不是说明性文案，保留。

**判断标准**：这句话删掉后，读者对市场的认知有没有任何损失？没有 → 就是说明性文案。

### 14. 补充说明降级为注，不占正文权重

解释「为什么这样分层 / 口径怎么理解 / 数据怎么读」的话，别用 `.info-title` + 正文段这种一级权重写——那是给结论用的。降级成注释：小字、弱色、左侧一根细线，紧跟它所解释的图表或段落。

```html
<p class="note">注：平台型以账号形式打包软件与课程，对硬件要求低，进校门槛较低；硬件加课程型的成本主要在实验箱等设备，单价相应较高。区分这两类交付形态，是判断各价格带供给情况的基础。</p>
```

```css
.note{font-size:12.5px; line-height:1.72; color:var(--text-faint); margin:10px 0 0;
  padding:2px 0 2px 12px; border-left:2px solid rgba(0,245,212,.22)}
```

权重层级从高到低：`.part-banner h1` > `.page-title` > `.info-title` > 正文 `p` > `.note` / `.fn-note` / `.viz-cap`。一段话如果只是「解释前面的内容」，就往下压一级，不要跟结论抢同一层级。

**口径类说明直接做成脚注**：表格 / 图表下方那种「指标怎么看、评级依据是什么」的口径说明（如「『初中可用度』依据公开材料判断，不代表供应商承诺……」），不要当正文段落平铺——降为脚注：正文位置只留一个小字号 `[a]` 标记，完整说明收进页脚 `.footnotes` 区。

```html
<!-- 表格末尾 -->
<div class="fn-note"><span class="mk">[a]</span><span>「初中可用度」依据公开材料判断，不代表供应商承诺……</span></div>

<!-- 页脚 -->
<div class="footnotes">
  <div><span class="mk">[a]</span>「初中可用度」依据公开材料判断，不代表供应商承诺……</div>
  <div><span class="mk">[b]</span>第 2 章价格区间「50–160 万」来自……正文价格均为公开口径，不含内部定价。</div>
</div>
```

```css
.fn-note{font-size:11.5px; line-height:1.7; color:var(--text-faint); margin:12px 0 0;
  display:flex; gap:6px; align-items:flex-start}
.fn-note .mk{color:var(--cyan); font-weight:700; flex:0 0 auto}
footer .footnotes{margin-top:10px; padding-top:10px; border-top:1px solid var(--border);
  font-size:12px; line-height:1.8; color:var(--text-faint)}
footer .footnotes div{margin:3px 0}
footer .footnotes .mk{color:var(--cyan); font-weight:700; margin-right:5px}
```

- 编号用 `[a]` `[b]`…（与来源引用的 `[1]` `[2]` 阿拉伯数字**分开**，避免混淆）；正文标记与页脚条目一一对应。
- `.footnotes` 与来源总索引并列放在页脚；页脚只放**事实性口径**（研究范围 / 价格口径）与脚注，**免责与审阅声明不放**（「未实测声明」这类审阅免责语全文禁用，见五）。
- 适合下沉的典型内容：指标定义与评级依据、口径换算说明（含 / 不含某项、公开口径 vs 内部口径）、对图表读法的必要限定。

### 15. 实体级小标题：逐家 / 逐项的详情块

一个章节里如果要对**同一层级的多个对象**（厂商 / 城市 / 产品 / 学校 / 渠道）逐个给一段详情，不要用加粗行内文字冒充标题（`**帕拉卡详情**`），要立成统一的子标题层级。

- **HTML**：`<h4 class="co-sub">帕拉卡 · 厂商详情</h4>`——青色左竖线，字号介于 `.info-title` 与正文之间。
- **Word（HTML→DOCX）**：`h4` 会映射成 `Heading 4`，进导航窗格、可生成目录；若用 `<p><b>…</b></p>` 冒充，这一层结构在 Word 里完全丢失。
- **命名统一**：同一层级共用一套命名模板（`{对象} · 详情`），不要把「xxx详情」「关于 xxx」「xxx（简介）」混着用。
- **对象齐全**：同类对象要逐个都有小节。出现「只有重点对象有详情、其余对象整段混在正文里」，就是没拆干净——把缺的对象按同一模板补齐，内容从上方速览表取，不臆造。
- **顺序一致**：本节对象的排列顺序与上方速览表 / 汇总表对齐，否则读者来回找。
- **每组收尾统一**：各组末尾的收尾判断（「本组……」）体例要一致；有的组有、有的组没有，读者会以为漏了。

**反例 → 正例：**

| 反例 | 改成 |
|---|---|
| `**帕拉卡详情**`（加粗行内文字，无层级） | `<h4 class="co-sub">帕拉卡 · 厂商详情</h4>` |
| 12 家里只有 3 家重点有详情，其余 9 家在正文里连成一团 | 12 家都立 `h4.co-sub`，缺的内容从上方速览表逐家补齐 |
| 详情顺序与上方表格顺序不一致（按沟通先后排） | 按表格顺序重排，重点对象在前 |
| 有的组末尾有「本组投入最大、资料最全……」收尾，有的组没有 | 六组统一补收尾判断，体例对齐 |

### 16. 多行块与编号列表：逐行独立，不许粘成一坨

从 Markdown / 结构化数据生成 HTML、Word 时，最常见的毛病不是缺内容，而是**多行内容被 join 成一段**。三类高发场景：

| 高发场景 | 症状 | 正确做法 |
|---|---|---|
| 连续引用行（`>` 元信息块：整理时间 / 数据来源 / 覆盖范围 / 文档说明） | 4–5 行粘成一大坨，读者分不清哪句是哪条 | 每一行渲染成**独立元素**（独立 `<p>` / 独立段落），不做 `" ".join(...)` |
| 编号列表（`（1）（2）（3）`） | 相邻条目被合并成一段 | 编号行**之间保留空行**；转换层按行切段，不做段落合并 |
| 缩进的子项列表 | 子项被当成正文段落，缩进也丢了 | 转换层必须支持**两级列表**；缩进 ≥2 空格即判为二级 |

**自查**：渲染完成后按行检索，确认多行块里每一条都能单独定位。若几条在结果里连续出现、中间没有块级边界，就是粘连。

**只用两级列表**。第三级在正文里已经读不出层次，应改为拆小节或用表格。

### 17. 先总后分：章节先给总结，再落分项

分档 / 分类类章节，顺序永远是 **总结 → 速览表 → 逐项依据**。直接把 20 条平铺列表摆上来 = 「散」，一定会被打回。

| 层级 | 写什么 | 形式 |
|---|---|---|
| 总结 | 分了几档、各几档多少家、真正可推进的是谁、其余为何不必投入 | 2–3 个短段落（不列表、不铺长句） |
| 速览 | 档位 / 对象 / 一句话判断 | 一张 4–6 行表（家数写进档位名，如 `A 类 · 能马上落地（7 家）`） |
| 依据 | 逐档展开 | 每档**先一句总述**，再列对象；档标题用独立加粗行 |

**同类对象合并成条**：结论相同的多家合成一条——「明确无方案：新东方、学而思、鸿合、Makeblock、作业帮」「主业错位或已退出：越疆、华为、大疆教育」，不要一家一条撑行数。只有**主推对象**才逐家单列。

**机检**：正文段落 >115 字 = 0；**超长单条 bullet 也要查**（单查段落会漏掉 100+ 字的单条）。

**实体详情 ≥12 条时改用分组小标题**（见八.15），其余保持平铺。

### 18. 同题重复只留一处：结论区与横向归纳区不重写同一张表

报告常同时有「结论（总体）」与「横向归纳」两部分，最容易犯的错是**同一批内容写两遍**——合作模式六类、教室形态五类、运营要点五点，各在一部分出现一次，标题不同、实质重叠，读者读到第二遍会以为换了内容。

**分工**：结论部分只留三样——**结论（分档）＋分档依据＋完成度**；所有横向归纳（怎么建、怎么合作、课程什么样、钱怎么收）只在横向归纳部分出现一次。

**合并前先逐条比对两侧**，因为各有一半信息：

| 位置 | 独有信息 | 处理 |
|---|---|---|
| 结论区「五类形态」 | 希沃 70 亿参数端侧模型与标准版/专业版差异、帕拉卡 3D 创作平台与 36 主题互动墙、盛思 17 个模块化案例 | 改为「逐类落地细节」列表，并入横向归纳区的形态表下方 |
| 横向归纳区「形态表」 | 投入分级、适合谁 | 保留表；原「按投入从轻到重」四条列表与表内「投入」列重复，删除 |
| 结论区「六类合作模式」 | 各类「特点」（「规模最大、最稳」「易试点、低风险」） | 并入横向归纳区表的「怎么运作」列 |
| 结论区「运营四点」 | 逐家展开的详情（师训 / 赛事 / 合规 / 解耦） | 直接替换横向归纳区的压缩版，并补上后者独有的「对齐政策」，成五点 |

**两条附加纪律**：
- **同一约束不写两遍**：某条前提（如「渠道商模式的交付依赖本地集成商」）只放在机制描述处（讲该模式那一节），不再在选型对照处重复。
- **完成度汇总不铺资料清单**：「掌握最扎实的 N 家及依据」这类资料明细属于附录的资料完备度，不进完成度汇总——完成度只报**进度与缺口**（几档、几家、缺哪几项报价）。

**机检**：合并后取两部分的 h3 标题比对，不应出现同义标题；关键短语（「五种形态」「六类」）计数应只落在保留侧。

### 19. 段落分层与框架：每段都有骨架，全节结构对称

`八.12` 管「要不要分点」，`八.17` 管「章节的先后顺序」；本条管**分完之后，每一段内部有没有骨架**。一段话读起来「黏、平、抓不住」，通常不是内容不够，而是段落没有分层——读者只能顺着字面读一遍，才发现重点在哪。

**（1）每段一个主题，判语只出现一次。**

- 一段只讲一件事。并列事实 ≥2 个即拆点（见八.12），不写成一句串到底的长句。
- 判语（结论 / 判断）只在**段首**或**段尾**出现，不埋在中间。标准骨架两种：
  - 叙述段：**领起句 → 依据（分点）→ 收束判语**。
  - 纯结论段：**依据分点 → 一句判语**（`.pts-tail` 收尾），判语不混进最后一条。
- 一段里既有事实又有解释又有判断、且次序不分，就是「有内容、没章法」。

**（2）全节结构对称：同层段落用同一种结构。**

| 层级 | 应一致 | 违反即返工 |
|---|---|---|
| 同一节各段 | 都分点，或都是整段 | 一段分点、一段长段；一段有判语收尾、一段没有 |
| 同一档逐项 | 同一命名模板 + 同一顺序 | 「重点对象有详情、其余连成一团」（见八.15） |
| 同排 `grid2` 卡片 | 分点方式一致、长度量级相当 | 一高一矮（见八.12） |

**（3）凝练：一句一个信息点。**

- 长句拆短；单句 >55 字、正文段 >115 字即判超长（与八.17 机检同口径）。
- 删「的」字堆叠与套话连接词；删掉不说也不损失信息的话。
- **通俗门槛**：非本行业读者**只读每段首句，也能复述该段要点**。做不到，说明首句不是主题句，或该段混了多个主题。

**章法三查（每写完一节过一遍）**：

1. **首句查**——每段首句是不是主题句？不是 → 改成主题句或把主题句提到句首。
2. **对称查**——同层段落是不是同一种结构？长度量级是否相当？
3. **复述查**——只看小标题 + 各段首句，能否读出本节骨架？不能 → 骨架没立起来。

**反例 → 正例：**

| 反例（黏 / 无骨架） | 正例（有分层 / 有框架） |
|---|---|
| 一整段把「合作模式、交付方式、收费口径、风险」串成一串 | 领起句一句 → `ul.pts` 四条（各 3–5 字小标题）→ 收束判语一句 |
| 第一节整段铺陈、第二节密集分点，同层不等重 | 同一节各段统一「总述 + 分点」骨架 |
| 判语埋在第三句中间，读完才知道结论 | 判语前置为领起句，或后置为 `.pts-tail` |
| 每段首句都是「随着……」「值得注意的是……」式铺垫 | 首句直接给主题（如「平台端钱厚，工具层利薄。」） |
| 「总结／小结」块写成三四段整段，段段塞多件事（2026-09-15 用户圈 1.1 总结块与 0.3 小结） | 默认分点：`ul` 要素列表，标签统一对仗短语——1.1 总结用「总体／第一梯队 7 家／其余 15 家／尚未触达 2 家」（数字进标签），小结用「对得上的／有差别的／站得住的／要补的」（三字对仗），一条一件事 |

**判断标准**：把每段首句单独抽出来连读，如果连不成一条通顺的提纲，这一节就没有章法。

### 20. 结论要有案例证据：以事实为基础，宁缺毋造

`八.3` 管单句的三步论证，`八.19` 管段落骨架；本条管**结论有没有事实垫底**——结论性内容（判断、定性、排名、趋势）不是「表达观点」，而是**对已核查事实的概括**。一条结论句如果回查不到具体案例或数据，它就不是结论，是印象。

**（1）每条结论都要能回查：主体 + 数字 + 来源三件套。**

- 结论句里必须出现**具体对象**（哪家厂商 / 哪个产品 / 哪份资料）与**具体量级或时间**；只写「不少厂商已有布局」「业内普遍认为」「行业领先」这类无主体断言，一律不合格。
- 反例：「多家厂商已具备完整课程体系」→ 正例：「帕拉卡、人教已有完整课程（**访谈确认**口径）」。
- 同一主体在**厂商详情、分档依据、速览表**三处必须同名同口径，不出现「表里规范、正文写成某厂商」。

**（2）先事实后判断，判断不越出事实范围。**

- 写作顺序固定为**可核查事实（案例 / 数据 / 方案名 / 公开动作）→ 判断**；判断只做事实范围内的概括，不给事实加戏。
- 一个判断若找不到对应事实，**整句删掉**——不要改写成更模糊的表述保留下来，模糊保留等于把印象伪装成结论。

**（3）不知道就不写：空白优于错误（强约束）。**

- 查不到出处、访谈没覆盖、资料没给的，**宁可不写**，也不用推测性表述填空（「据悉」「预计」「有望」「大概是」）。
- 确需保留的，改标「推演 / 估算 / 抽样（非普查）」并写明推导锚点；缺口显式列出（「未提供报价 4 家：××、××」），不拿相邻数据补齐。
- 这条与第一条红线同源，凡冲突写法一律无效。

**（4）避免假大空：无对象、无度量的话一律删。**

- 禁「赋能教育行业」「大幅提升效率」「具有重要意义」「前景广阔」这类**既没对象也没度量**的句子；换成对象 + 量级 + 来源三样齐备的事实句。
- 同理禁无依据的排名与趋势（「行业第一」「未来三年将爆发」）：排名要给出比较维度与数据，趋势要给出预测来源，给不出就不写。

**（5）叙事严谨、逻辑缜密：全篇是一条闭合链。**

- 全链条自检：**每条结论 → 有依据；每条依据 → 有来源；每个来源 → 标可信级**。任一环断掉，结论就悬空。
- 章节之间要有叙事承接（「因此」「相比之下」「进一步看」），不出现上一节讲 A、下一节忽然讲 C 的断裂；相邻结论若有矛盾，显式写出而非略过。
- 分档类结论另需满足：**结论家数 → 速览表 → 逐档依据**三处数字逐一对齐。

**反例 → 正例：**

| 反例（假大空 / 无证据） | 正例（案例 + 事实） |
|---|---|
| 「绝大多数厂商已布局 AI 教育」 | 「24 家中 15 家有实质 AI 教育业务（本次调研访谈口径）」 |
| 「该产品性能行业领先」 | 「该产品支持 70 亿参数模型本地部署（**公开资料**）；同档其余 6 家未公开参数量」 |
| 「未来市场空间广阔」 | 「不预测——无 P0/P1 级预测来源，缺口列入待补」 |
| 「价格方面较为灵活」 | 「9800 元/年/学段（**厂商自述**口径）；未报价 4 家另列」 |
| 「厂商普遍重视课程建设」 | 「7 家中有 5 家提供完整课程清单（**访谈确认**），2 家仅提供大纲」 |

**自检三问（每写完一条结论问一遍）**：① 这条结论能回查到具体厂商 / 数字 / 资料吗？② 回查不到，我是不是该把它删掉？③ 链条「结论 → 依据 → 来源 → 可信级」有没有断点？

## 九、HTML 结构与样式（暗色科技风）

**CSS 变量（:root）：**
```css
--bg-deep:#04071a; --bg-night:#0A0E27; --bg-card:#0F1638;
--cyan:#00F5D4; --magenta:#FF2E97; --yellow:#FFE74C; --purple:#B14AED;
--orange:#FF6B35; --blue:#3A86FF; --green:#5CE082;
--text:#E8ECFF; --text-dim:#8E96C9; --text-faint:#5A6094;
--border:rgba(0,245,212,.28); --grid:rgba(0,245,212,.07);
--wrap:1360px; --gut:64px;   /* 版心与左右留白 */
```

**版心**：`.hero` / `main` / `footer` 统一 `max-width:var(--wrap)`、左右 `padding:0 var(--gut)`。**`.part-banner` 是唯一例外：它在 `<main>` 内部，不得再自带左右 gutter**——main 已经提供一份 `--gut`，横幅自己再加一份就是**双重缩进**，板块标题会比下面的 `.page` 卡片多缩进一个 `--gut`，用户看到的就是「章节标题与正文割裂」。对应地，`.part-banner::after` 装饰线用 `left:0;right:0`（与卡片同宽），断点里也不要给 `.part-banner` 加 padding。默认 `--wrap:1360px`、`--gut:64px`。上限必须**低于常见窗口宽度**才有意义：视口约 1550px 时，1600px 的上限等于失效——容器直接顶满窗口，两侧只剩 gutter，观感压抑；1360px 则两侧各留约 95px 呼吸位。**关键：当视口窄于 `--wrap`（例如 1050px 左右的内嵌预览面板）时，上限同样失效，两边留白完全由 `--gut` 决定**——此时只调 `--wrap` 毫无效果，必须调 `--gut`。用户反馈「两侧窄」时，先由截图反推视口宽度：视口 < `--wrap` 就加大 `--gut`，视口 > `--wrap` 才收 `--wrap`。超宽屏靠 `--wrap` 上限兜住行宽，不随视口无限拉长。

**组件类速查（完整 CSS 见 `assets/template.html`）：**
- 导航：`.topnav` / `.brand` / `.nav-links`

## 十、SVG 渲染规则（关键坑）

SVG `<text>` 内 **HTML 的 `<sup>`、`<b>` 不生效**，必须用 `<tspan>`：

```xml
<!-- ❌ 错误 -->
<text>... 0–300 元/年<sup>1</sup> <b>扩大边界</b></text>

<!-- ✅ 正确 -->
<text>... 0–300 元/年<tspan baseline-shift="super" font-size="9" fill="#00F5D4">1</tspan></text>
<text><tspan fill="#00F5D4" font-weight="700">扩大边界</tspan><tspan dx="4" baseline-shift="super" font-size="9" fill="#00F5D4">2</tspan></text>
```
- 用 `fill` 不用 `color`；上标用 `baseline-shift="super"`；加粗用 `font-weight`；间距用 `dx`。

## 十三、工作流程（执行顺序）

1. **明确行业与业务**：先确认调研的行业/业务，再按「行业适配示例」把 10 环映射到具体指标。
2. **建证据库**：每条数据登记「指标 / 数值 / 口径 / 来源链接 / 可信级 / 采集日期」。
3. **按 10 环链路逐环取数**，①→⑩；每环先回答"要回答什么、要什么指标"。
4. **交叉验证**：核心结论至少 ①/② 级来源；④/⑤ 级只描述现象。
5. **新资料到达即全文复核**：任何阶段拿到新资料（新方案 PDF、新访谈记录），不要只改该主体那一节——先判断它对**分档结论**有没有影响（例：商汤资料让「场景错位」独立成档），再同步改分档表、速览表、结论段、完成度四处；改完检索旧提法残留是否为 0。

## 十四、多格式交付（HTML → Word / Markdown）

本 skill 的主产物是单文件 HTML。当交付对象还要 `.docx`（便于批注、盖章、归档）或 `.md`（便于二次编辑）时，按下面这条链路走，不要另起一套内容。

**链路（单一事实源）：**

```
内容源（Markdown，唯一事实源）
   ├─→ 暗色 HTML（本 skill 主产物，assets/template.html）
   └─→ 浅色 HTML（排版中间件：A4、正文 11pt、无暗底，供转 Word）
            └─→ .docx（html4docx 转换）
```

**Markdown 源怎么写**：内容侧的骨架、层级标记、语言与口径规范见 `cyx-md-style`；本节只管三种格式的同源链路与转换映射，不重复 md 侧写法。

**硬性要求：**

1. **三种格式同源**。内容只改 Markdown，HTML 与 DOCX 都由脚本重新生成；禁止在不同产物上分别手改——三处分别改必然口径不一致。
2. **浅色中间件要真的浅**。暗色 HTML 直接转 Word 会得到满页深蓝底加白字反色，打印和批注都不能用。转 Word 前先出一版浅色 HTML（白底、正文 11pt、A4 边距、标题分级字体）。
3. **改前留备份**。批量改写脚本落盘前先存 `_bakN` 或 `历史版本/` 快照；脚本写成可重放（含 `expected` 计数校验 + 禁词 / 标签平衡 / 引用区间终检，全通过才落盘）。
4. **写回被占用就等一下**。目标文件被 WPS / Office 打开时会报「文件被占用」——让用户先关闭再重跑，不要反复重试，也不要另存临时文件顶替。

**HTML → DOCX 的映射约定：**

| HTML | Word 样式 | 说明 |
|---|---|---|
| `h1`–`h4` | `Heading 1`–`Heading 4` | 进导航窗格、可生成目录；**不要**用 `<p><b>…</b></p>` 冒充标题 |
| `ul` / `ul ul` | `List Bullet` / `List Bullet 2` | 自动得到两级项目符号 |
| `table.t` | 表格 + 表头行 | 保留列宽与边框 |
| `sup.fn` / `.footnotes` | 上标 + 段末脚注 | 转换后需抽查是否保留 |

**转换调用（Python，html4docx）：**

```python
from docx import Document
from html4docx import HtmlToDocx

html = open(src, encoding="utf-8").read()
doc = Document()                       # 页脚、页码在此模板上补
HtmlToDocx().add_html_to_document(html, doc)
doc.save(dst)
```

**已知坑：**

- `python -m html4docx` **没有 `__main__`**，会直接报错；必须走上面的 API 调用。
- 转换器自带的 `setup-html-to-docx.sh` 按 `$VENV_DIR/bin/python` 判断解释器路径，在 **Windows / Git Bash 下必然失败**（Windows venv 是 `Scripts/` 而非 `bin/`）。直接用托管 Python 自建 venv 调转换 API，不要跟这个脚本较劲。
- 转换只保证结构（标题层级、列表、表格）。**封面、目录、页脚、页码要额外补**——转换后用 `python-docx` 补 `section.footer` 与页码字段，再核对目录页。
- **转换后必查三项**：标题样式数量（`Heading 4` 条数应等于实体详情块数）、列表标签配对（`<ul>`↔`</ul>`、`<li>`↔`</li>` 计数相等）、段落总数与表格总数是否与源相符。
- **改日期要扫三处，不能只改源文件**：`.md` 头部与正文的日期只是其中一个来源；构建脚本里通常把**封面标题 / 副标题 / 组织 / 日期**写成硬编码常量（`DATE = "…"`、`REQUEST_ID = "…"`）。只改 `.md` 会漏掉 Word 封面那一处。转换后必查：剥掉标签后搜旧日期，**残留必须为 0**。同理，副标题里的家数（如「24 家厂商的落地能力」）也是硬编码，厂商数量变化时要一起改。
- **同一份 `.md` 禁止在同一轮并行发多个编辑**：并行 Edit 各按初始快照写回，**后写覆盖前写，只有最后一个生效**，其余静默丢失（不报错）。表现是「编辑都提示成功，但文件里旧词仍在」，而构建脚本接着按这半改的源生成了 `.html` / `.docx`，交付出「源已改、产物未改」的不一致版本。**必须串行逐个改**，改完先机检「旧词残留 = 0」，再跑构建链路。
- **`**独立加粗行**` 绝不能用 `startswith("*") and endswith("*")` 判定为斜体脚注**——`**加粗小标题**` 同时满足首尾是 `*`，会被脚注逻辑吞掉：暗色 HTML 里小标题**凭空消失**（页面看着「一片散、没有分组」），Word 里则被**堆到文末**成一串垃圾段。判定必须用 `re.fullmatch(r"\*[^*].*\*", s)`（单星号才认），并让独立加粗行输出 `<h4 class="co-sub">`，与 Word 的 `Heading 4` 对齐。交付前用「独立加粗行数 = HTML `h4.co-sub` 数 = DOCX `Heading 4` 数」三者相等来自检。

## 十五、交付前自查清单

- [ ] 每个数据点都有脚注角标，且脚注里写明了「来源机构 + 报告名 + 可信级标签」
- [ ] 可信级标签都带类别名（无裸 `①` / `②③`）
- [ ] 无「孤儿脚注」（有脚注无角标）
- [ ] 来源不同的数据已拆成不同脚注，未混用
- [ ] 推演/估算/抽样数据已标注「非普查」+ 推导锚点
- [ ] 口径边界已显式点破（大盘≠细分、流量≠收入、意愿≠行为等）
- [ ] 竞品/玩家枚举既没低列也没虚列，每个都有出处
- [ ] **分类名不用弱化字眼**：不写「观察型 / 观察对象 / 相邻观察」这类 hedge 标签，直接用实质分类名（如「相邻型」）；同一类别在全篇（卡片标题、图表标签、chip、图注）必须用同一个名字
- [ ] **不用判断式收尾**：不写「补齐即入列」「补全即可纳入」这类**把对象直接归位**的短语，也不用「需补 ××」式的要求口吻；改为中性陈述缺项本身（如「教师资格验证与报价两项未明确」）。同一缺项在正文、速览表、分档依据三处必须用同一措辞
- [ ] **报告不下行动决策**：调研报告只交事实、性质与比较维度，不替读者做决定。禁止「可直接进商务」「进入商务评估」「优先选择 ××」「落地建议：选 1 所试点校做 POC」「当前不必投入」这类表述。替代写法——分档**维度**用调研口径（「按与本次需求的匹配度分档」而非「按可落地性分档」）；分档**结果**用程序语言（「未纳入第一梯队」而非「不必投入」）；选型对照表写成「需求取向 ↔ 产品形态与代表厂商」映射，不写「若想 ×× → 优先选择 ××」；比较项写成维度清单（「7 家 A 类的横向比较维度：…」）。行动项只允许出现在「待办」章节，且用「列入后续对接」而非「进入商务评估」
- [ ] **不写状态迁移与台账式说明**：厂商「已触达 / 已获方案 / 由 X 档转入 Y 档」这类**归属变动**不入正文——它已经在本档名单里，就不要再解释它从哪来、到哪去（禁「本轮已由『未触达』转为『已获方案』——故从本档移出，归入上述……」）。档位随修订产生的增减**一律不入报告**——既不散落到各节，也不单列「最近修订」流水行（报告是给读者看结论的，不是给作者记工时的）；修订记录放版本管理 / 交付说明，不进文档信息块；厂商详情也不以「2026-09-14 新增」「本轮新增一份完整方案，但不改变 A 类排序」开头，只留来源与判断（「资料为《××方案》（30 页），未经访谈」＋结论），缺口另列
- [ ] **全文不出现「轮次」语言**：汇报性文档里，叙事主体是「本次调研」这一件事，不是产出的迭代过程。禁「本轮 / 本期 / 此次 / 下一轮 / 这一轮」等字眼（含「它是本轮唯一现成选项」「本期不推进」「列入下一轮对接」）。替代——限定范围时直接用「本次调研」或干脆省略（「本次调研 24 家厂商」「无实质回复，未推进」）；行动项写「列入后续对接」而非「下一轮」。报告任何位置（含页眉与文档信息块）都不出现修订流水；自检命令：`grep -n "轮\|本期\|此次\|最近修订" 报告.md` 应无命中
- [ ] **图表口径一致**：同一分类 / 指标在多张图、表、卡片里重复出现时（如企业分类家数、价格区间、样本数）数字逐一对齐；改文字前先核对源数据，发现不一致要回改图表数值本身，不能只改文字
- [ ] 标题编号层级正确（1 / 1.1 / 1.2），无重复页码
- [ ] SVG 内用了 `<tspan>` 而非 `<sup>`/`<b>`

**技能不是一次写死的——本技能包下的三个 skill 都不是。** 每轮用户反馈里都藏着一条可能适用于所有后续报告的规则；把它挑出来写回**对应 skill**，才是「越用越好用」的唯一途径。本会话反馈的归类与落点已存于 `references/feedback-log.md`。

### 16.1 触发时机

- 用户针对已交付报告提出任何修改意见（措辞 / 结构 / 命名 / 版式 / 删内容 / 补数据）。
- **同一类意见在同一会话里反复出现**——这是最强信号：说明不是当期报告的问题，而是 skill 的**默认值或默认写法错了**。例：用户连提 4 次「边距窄」，真实原因不是这一份报告要宽，而是默认留白偏窄、且前三次调错了变量（动了 `--wrap`，而视口窄于上限时只有 `--gut` 生效）。

### 16.2 三步判定

| 步骤 | 做什么 |

| ① 归类 | 把反馈归到 A–F 六类（见 16.4） |

### 16.3 落盘纪律（三不写）

1. **不与已有规则重复**：同类规则已在 → 就地强化表述或补一条机检，不新起一节。
2. **不写死具体数值**：用户说「边距再宽一点」，写「偏好宽留白 + 判定方法（视口 < `--wrap` 时只有 `--gut` 生效）」，不写「边距 = 64px」——数值只是当前默认，会再变。
3. **不写无法机检的模糊直觉**：写不成判据或检查项的，不进 skill。

### 16.6 留痕：每轮追加反馈日志

在 `references/feedback-log.md` 追加一行：`日期 / 用户原话（节选）/ 类别 / 归属 skill / 落点 / 处置（新增·强化·高频）`。

- **「归属 skill」列必填**（A–F 与 skill 的对应见 16.4 的「主责 skill」列）；一条反馈跨两个 skill 时填两个（如 `cyx-html-style + cyx-md-style`），不合并成一行含糊表述。
- 同一类别出现 ≥2 次并标注「高频」的，回本文件把该条从「建议」升级为「强约束」（加粗、加机检、或在自查清单里前置）。
- 个案不入日志。

### 16.7 沉淀完成前必跑

```bash
python scripts/check-template.py
```

全过才算沉淀完成（它同时校验本文件提到的类与资产是否对齐，**第 9 组专门校验三个 skill 是否都具备进化条款**——任何一处缺失都会 FAIL）。

**Windows 下跑机检的编码坑（已复发 2 次，务必先设）**：PowerShell 捕获 Python 输出时默认走 GBK，脚本 print 到 `↔`、`→` 这类字符即抛 `UnicodeEncodeError`，表现为「输出为空 / 中途报错」，容易误判成脚本挂了。**先设 `$env:PYTHONIOENCODING = "utf-8"` 再跑**；要把结果落盘比对时用 `[System.IO.File]::WriteAllText(路径, 文本, [System.Text.Encoding]::UTF8)`，不要依赖 shell 重定向。

### 16.8 向用户报告

沉淀后用一句话告知：「这条我记进 skill 了，以后默认这样做。」——让用户知道规则在累积，也方便他当场纠正（「这条只是一次性的，别记」）。

### 16.9 规则也会过时：允许回退

后续报告里若用户推翻某条已沉淀的规则（「这条不要再这样」），做三件事：① 改本文件对应条目——**不是删掉，而是标注适用边界**（「仅当 ×× 时」）；② 在 feedback-log 追加一条「规则回退」；③ 检查有无其他规则与它冲突。

### 16.10 子 skill 的进化责任（三个 skill 一视同仁）

两个子 skill 各自带一份与本节同构的进化条款（`cyx-md-style` 第六节、`cyx-html-style` 第七节）。四条硬要求：

1. **自带触发与落点表**——被单独调用时按自己的落点表回写自己，**不要求先加载本文件**；用户只写 Markdown、或只改视觉时，沉淀照样发生。
2. **越界即路由**——反馈超出本 skill 管辖时（如正在用 `cyx-md-style`，用户却抱怨「看着像 AI 生成的」），按 16.4 的「主责 skill」列定位到真正该改的文件，**能改就当场改**（同属一个技能包，路径可达），改不了的用一句话写进交付说明。
3. **共享一本账**——三个 skill 的留痕都写进 `references/feedback-log.md`，用「归属 skill」列区分；各 skill 内不另建日志，避免两处对不上。
4. **共用一次校验**——`scripts/check-template.py` 第 9 组即校验「三个 skill 是否都具备进化条款」，任一处缺失会 FAIL；改完任何一份文件都跑同一支脚本。

**一条反馈进来的完整路径**：识别 → 归类（A–F / 组织）→ 判通用性 → 按 16.4 找主责 skill → 写进该 skill 的本地条款 → 同步自查清单与机检 → 追加 feedback-log（含归属）→ 跑 `check-template.py` → 一句话告知用户。

### 16.11 管辖范围与「当轮必沉淀」纪律

1. **本 skill 管辖两类产物**：① 行业 / 市场调研报告；② **厂商 / 产品对比图谱类 HTML**（如 A 家对 B 家的功能、计费、成熟度横向对比）。第二类常被误当成「独立视觉产物」而漏走沉淀——**它本质是市场论证的视觉化，同样受本机制约束**，润色反馈一律落账。
2. **当轮交付前必过第十六节自检**：任何一轮产出（含对比图谱）定稿前，先把用户这轮的润色意见逐条判通用性，通用项写进对应章节 + feedback-log，**不得把反馈只留在当期产物里**。本次（2026-09-28 LibTV vs LumenFlow 对比 HTML）多轮去 AI 味润色此前未走沉淀，本轮补记并归口，已暴露的漏项（callout 对话口吻标题、「说到底」、导航与正文不同步）已写入八.5 / 八.9 / 七.3。
3. **现状说明**：共享账本 `references/feedback-log.md` 当前由本 skill 持有；`cyx-md-style` 与 `cyx-html-style` 是规划中的子 skill（第十六节早期版本曾引用其「六 / 七」进化条款），目录尚未建立前，**本 skill 第十六节即为唯一进化条款载体**，所有语言 / 视觉去 AI 味规则都先落本文件，待子 skill 建立再分流。
