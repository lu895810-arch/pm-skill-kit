# 项目宏观对比（cyx-compare-macro-demand）

## Purpose（目的）

把「对比两个项目」从并列罗列变成可复现的方法论：**对比的每个维度都来自两份代码级分析的
证据、结论落在「互补关系」或「按目标分流」而非谁好谁坏、图只画承载对比结构的图**，
产出一份能直接点开看的单文件暗色 HTML 报告。

首例是 Huobao Drama × Jellyfish 对比，方法论项目类型无关，任何两个已有单项分析的
项目 / 产品可套。

**与既有 cyx 技能的分工（不重复造）**：

| 事项 | 归谁 |
|---|---|
| 单个项目的代码级分析（六步分析法、取材清单） | `cyx-github-analysis` / `cyx-folder-analysis` |
| 本技能的八节对比框架、用户→场景→问题三层法、选型决策 | **本 skill** |
| 语言纪律（去 AI 味、术语白话定义、口语禁用） | `~/.workbuddy/MEMORY.md`「语言总纲」+ `cyx-md-style` |
| 视觉纪律（暗色配色、SVG 精致度基线、禁 emoji） | `cyx-html-style` + 本文件第四节 |
| 成品归档、文件命名 | `cyx-doc-separate` |

---

## 一、输入约定（先读这段再动手）

| 输入 | 说明 | 缺失时怎么办 |
|---|---|---|
| 两份单项分析报告 | HTML / MD 均可，最好已过 `cyx-github-analysis` 流程 | 没有就先对各项目跑单项分析（本地有仓库副本直接读，没有先 clone），**不要跳过单项分析直接对比**——对比的深度上限就是单项分析的深度 |
| 对比侧重点（可选） | 用户点名想重点看的维度 | 未点名按第二节默认八节走全 |
| 输出文件名 | 默认 `{a}-vs-{b}-compare.html` 放工作区根目录 | 用户指定则从其指定 |

**红线：对比报告里不允许出现两份单项分析里都没有的新事实。** 对比阶段只做提炼、对齐、
归一；发现两份材料口径冲突（如版本号、日期对不上），回源码或原报告核实后再写，不凭感觉取其一。

## 二、八节对比框架（默认结构，按需增删）

编号顺延（01–08 + 来源索引），左侧目录锚点同步。每节的产出与证据要求：

### 01 核心结论
- 开篇给整体判断：两者是**互补关系**（强项与弱项正好错开）、**同位竞争**（同一位置一强一弱）、还是**上下游关系**（产出一个接得住另一个的输出）。互补是常见形态，判断依据要落到具体维度。
- 配一张**双列对照 SVG**：左右各列对方 ✓ / ✗ / △ 项，中间标注互补关系。每条 ✓/✗ 都能回溯到单项分析的成熟度或风险章节。

### 02 用户人群与使用场景（本技能的「需求」核心，不可省略）
- **三层因果链**：目标用户群体 → 典型使用场景 → 要解决的问题。左右两栏各三条链，配 SVG（纵向箭头串联三个节点框）。
- 每一层都从单项分析的用户定位、部署形态、主流程章节提炼，不新编用户画像。
- 配一张三行对照表（用户 / 场景 / 问题），行值写白话完整句，便于用户后续逐项补全。
- 判断依据：部署形态（桌面单机 vs Web 自托管）、许可证（个人 vs 商用）、协作模型（单人 vs 多人）直接决定用户群，把这些证据写进表格。

### 03 基本信息对比
- 一张逐行对照表：核心定位、开源协议、版本 / 时间、后端栈、前端栈、部署形态、AI 编排方式、模型接入、成片导出、语言 / 分发、自动化测试。
- 行的选择标准：**两份单项分析都提过的维度才进表**；只有一方有的信息不硬凑。

### 04 主流程对比
- 两条流水线并排的 SVG 管道图，节点宽度一致、行对齐；**分歧点高亮**：一方的末环绿色（已完成），另一方末环黄色虚进（进行中或缺失）。
- 图后必有一段文字点破产物形态差异（成片 vs 素材这类），并核对 README 宣称与 roadmap 实现的差距。

### 05 架构对比
- 左右两列分层栈 SVG（前端 / 后端 / 运行层 / 基础设施），中间分隔线标注范式差异（如「轻量 / 桌面 / 内嵌 ↔ 企业级 / Web / 外部化」）。
- 图后一段文字写清两种范式各自的代价——不写「各有优劣」这种空话，写具体换来了什么、牺牲了什么。

### 06 能力成熟度雷达
- 八维左右合并归一（从两份单项分析的成熟度评估取维度，对齐口径后合并），0–5 相对评分。
- **口径声明必须写在导语**：「相对自估用于横向比较，非基准测试」。评分为谁高谁低服务，不为绝对值服务。
- 图后 callout 逐项列举双方高分、低分维度，并点出唯一重叠的高分轴（如有）。

### 07 工程纪律与风险对比
- 一张逐行对照表：工程纪律、任务系统、商用风险（许可证）、供应锁定、多用户、主要短板。
- 每条风险标注来源（哪份分析、哪个文件证据），禁止凭印象写「可能存在性能问题」。

### 08 选型建议
- 一张决策 SVG：起点「使用目标？」，按目标分流到左右两个选项卡，每张卡列 3–4 条适用条件 + 1 条前提 / 代价。
- 导语固定写「选型取决于使用目标，而非项目优劣」。
- **若两者单独使用都不完整（如一个可商用但无成片、一个能成片但禁商用），必须给组合思路**：哪个当底座、借鉴另一个的哪块设计，并核清组合下的许可证边界（可借鉴设计 ≠ 可复制代码）。

### 来源索引
- 列两份单项分析覆盖的仓库文件路径、版本与日期，以及评分口径说明。

## 三、证据与语言红线

1. **结论锚定来源**：每张图 / 表后跟 `来源：…` 行，指向两份单项分析的对应章节。
2. **雷达口径显式声明**：0–5 是合并归一的相对自估，不是基准测试；写在导语和来源索引。
3. **宣传与实现分开**：README 宣称但 roadmap 未实现的，在对应对比节单列，不消化掉。
4. **AI 味词对照表**（本轮实战确认，写入报告时逐个替换）：

| 不写 | 写 |
|---|---|
| 一句话定位 | 核心定位 |
| 按目标挑 | 按使用目标选择 |
| 首页强推 | 首页引导用户使用 |
| 最长短板 | 主要短板 |
| 唯一真相源 | 唯一可信数据源 |
| 你的核心目标 | 使用目标 |
| 开箱即用 | 安装后可直接使用 |
| 短板互为对方长板 | 强项与弱项正好错开 |
| 互补的镜像（比喻） | 强项与弱项正好互补 |
| 闭环 / 拉满 / 贴近圆心 / 错开半圈 | 平实表述（如「贯通至成片」「得分高 / 低」） |

5. **章节标题用名词短语**，不带论述腔；正文叙述主体用「本次调研 / 我们」，不用「报告」。
6. 其余语言纪律（口语禁用对照表、术语白话定义）按 `cyx-github-analysis` 三.6 / 三.7 与
   `~/.workbuddy/MEMORY.md` 语言总纲执行，两份是同一套标准。

## 四、交付物规格（单文件暗色 HTML）

**视觉风格：黑色高对比，默认直接做，不再询问。**（2026-09-29 三轮确认：商务蓝灰浅色、
暖色纸感均被否，用户最终指定黑色。同类报告未来直接走暗色。）

| 项 | 规格 |
|---|---|
| 底色 | 页面 #0e1116，面板 #151a22，面板内表格头 #1c232d，边框 #2a323e |
| 文字 | 正文 #dde3ea（对黑底对比度约 12:1），标题 #f0f4f8，次级 #a6b0bd，弱化 #77828f |
| 双方标识色 | 各选一个暗底可读的亮色变体并全局统一（如暖橙 #e8925a / 青绿 #54c7b4）；✓ 绿 #7dd694、✗ 红 #ef8a80、△ 黄 #e5c376 |
| 布局 | 左侧固定目录 216px（IntersectionObserver 滚动高亮，≤1080px 隐藏）；版心 1180px |
| SVG | viewBox 宽 900 上下；节点深色渐变（如 #221a14→#1a1510 / #122020→#0f1a1a）+ feDropShadow（flood-color 纯黑）+ 暗边框；渐变与 marker 的 id 每张图独立前缀防冲突 |
| 表格 | `table.t`：边框 #2a323e、表头底 #1c232d、行 hover #1c232d |
| Callout | 左边框 3px：黄 #221d12 / 红 #251614 / 绿 #14201a 暗色底 |
| 禁用 | emoji、说明性文字、免责语、页脚方法论自述 |

骨架与组件（CSS 变量、`.toc` / `.panel` / `table.t` / `.callout`、SVG 渐变与投影写法、
八节完整实例）直接参考 `assets/report-sample.html`（Huobao × Jellyfish 最终黑色版全文），
改内容不改骨架。

**SVG 文字溢出检查（硬性，逐张做）**：每张 SVG 写完后，核对每段文字最右端的估算位置
（x 起点 + 字数 × 字号 ≈ 最右端）是否越过 viewBox 宽度与卡片右边界。曾实际踩坑：
x=850 处的注释（字号 11）最右到约 954，越过 900 边界被裁。解法：画布加宽（900→980）
并把注释移入安全区。检查不通过的图交付前必改。

- [ ] 每张图 / 表后有 `来源：…`？末尾来源索引齐？
- [ ] 雷达评分口径声明写了吗（相对自估、非基准）？
- [ ] 宣传与实现差距点出来了吗？组合思路的许可证边界核清了吗？

**框架完整性**
- [ ] 02 节「用户→场景→问题」三层因果链在？每层有证据支撑？
- [ ] 主流程分歧点高亮了？产物形态差异写成文字了？
- [ ] 选型节按目标分流 + 给了组合思路（若两者单独都不完整）？

**语言与视觉**
- [ ] AI 味词对照表（三.4）逐个扫过？章节标题是名词短语？
- [ ] 全文暗色，无浅色残留（grep 旧色值验证）？无 emoji、无说明性文字？
- [ ] 每张 SVG 文字溢出检查通过？最右端留了 ≥30px 安全边距？

**结构**
- [ ] 章节编号与左侧目录锚点全部对齐？SVG 闭合？
- [ ] 交付用 present_files 单文件呈现？

## 六、自我进化机制（遵循 cyx-skill-evolution 通用条款）

**本技能不是一次写死的。** 用户就对比报告提的修改意见，按三步判定：**通用**（换一对
项目仍成立）→ 回写本文件；**个案**（只对这一份成立）→ 只改当期产物。

| 反馈类型 | 典型原话 | 改本文件哪一节 |
|---|---|---|
| 对比框架 | 「缺了 X 维度」「这块该多讲讲」 | 二（八节框架） |
| 证据口径 | 「评分哪来的」「结论哪来的」 | 一 / 三（红线） |
| 遣词命名 | 「换个词」「标题别这么说」 | 三（AI 味词表） |
| 排版视觉 | 「换风格」「图太挤」「文字被裁」 | 四（交付物规格） |
| 流程命令 | 「先做 X 再做 Y」 | 一（输入约定） |

**沉淀后必做**：① 规则与「交付前自查清单」两处同步；② 在 `references/feedback-log.md`
追加一行；③ 一句话告知用户「这条记进本技能了」。

## 边界

- 本技能只管「两个已分析对象的横向对比」。单个项目还没分析 → 先走
  `cyx-github-analysis`（GitHub 仓库）或 `cyx-folder-analysis`（本地文件夹 / 桌面软件）；
  要部署运行 → `cyx-github-deploy`；要市场 / 行业调研 → `cyx-research-report`；
  需求条目分级 → `cyx-priority-need`。
- 三方及以上对比：先按本技能做两两对比提炼维度，再扩展为多列对照；雷达维度合并口径
  在报告导语声明。
