01核心定位

Jellyfish 不做模型，只做流水线：它把「剧本 → 分镜 → 一致性管理 → 图/视频生成 → 任务追踪」串成一条生产线，属于 AI 视频赛道里的工作流编排层——类比影视制作：大模型是摄像机，Jellyfish 是把摄像机、灯光、场记、后期组织起来的剧组管理系统。

它不与模型厂商直接竞争，模型可替换；代价是产品能力上限取决于所接入模型的能力。

02解决什么问题

生成单条视频并不困难，困难的是完成一部剧：上百个镜头必须保持同一套视觉设定。Jellyfish 的每个核心设计都对应一个生产级痛点，对应关系如下：

痛点Jellyfish 的设计落在代码哪里
一致性漂移：同一个角色在上一镜黑发、下一镜金发（AI 逐镜生成时互不知道对方画了什么） 把角色、场景、道具、服装做成实体库，镜头只做「关联」而非「重新描述」；生成时携带实体参考图 services/studio/entity_*.py 共 7 个模块，是整个 services 目录里最大的一簇
流程割裂：剧本用 ChatGPT、出图用即梦、出视频用 Kling，环节之间依赖人工复制粘贴，结果散落各处无法复用 以「章节」为单位的一条龙工作流：AI 提取结果先沉淀为分镜、候选资产、对白、提示词，确认后进入生成，产物全部回流入库 前端 pages/aiStudio/ 按项目→章节→分镜组织；后端以 GenerationTask 统一记录
长任务黑盒：视频生成耗时数分钟，是否失败、停滞于哪一步、能否取消，用户无从得知 统一任务中心：文本/图片/视频任务共用一套任务模型，状态、耗时、取消、跳回来源页面全部可见 models/task.py + core/tasks/ + 前端悬浮 TaskCenter

03产品视角

主流程：一条带门禁的生产线

来源：README.md「主工作流」、AGENTS.md「分镜主流程约定」

这条线的共同逻辑：AI 只负责生成候选，人负责最终确认——拆分和提取的结果一律先落为「候选」，人工确认后才生效。这类设计在 AI 内容生产产品中较少见，其价值在于产物质量可控、出错可回退。

三个产品亮点

亮点说明
状态三分离大多数同类产品把「镜头是否已确认」「是否正在生成」「能否立即生成视频」混为一谈。Jellyfish 在 AGENTS.md 里明文规定这是三个独立状态：信息确认状态（shot.status）、运行时任务状态（来自任务系统）、视频准备度（单独一套检查）。状态语义清晰，是交互不混乱的基础。
页面职责硬边界分镜编辑页仅负责「准备」，工作室仅负责「生成」，任务中心只展示通用任务信息、不承担业务详情页职责——该边界写入协作约定，要求修改代码时同步遵守，防止职责随功能迭代扩散。
任务中心的轻量化取舍悬浮面板默认每页只放 3 条、可拖动吸边、按需筛选；业务细节（提示词调试、图文映射）留在业务面板。这条边界同样是明文约定。

宣传与实现的差距：README 首页写的是「剧本输入 → … → 后期剪辑 → 一键导出成片」，但 roadmap 自己承认「补强时间线和成片导出体验」仍在待办，前端目录中也没有剪辑相关页面。结论是：该流水线的末段尚未实现，当前实际产物停在「镜头级视频素材」而非「成片」。
目标用户判断：五类场景中（短剧创作者 / AI 工作室 / 个人创作者 / 教育视频 / 电商剧情短片），当前形态最贴合的是个人创作者与技术型小团队——自托管部署、无多租户权限、依赖容器化运维能力，短期内难以覆盖大型工作室与非技术用户。

04技术视角

系统架构

来源：deploy/compose/docker-compose.yml、backend/README.md、site/content/docs/architecture/task-execution.md

任务系统：技术含金量最高的子系统

来源：site/content/docs/architecture/task-execution.md

三处工程决策的取舍依据：

  • GenerationTask 是唯一真相源：前端不直接查询 Celery 的任务状态，只读取 MySQL 中自维护的任务记录；更换 Celery 不影响任务数据完整性。
  • 取消语义表述克制：文档明说「不承诺模型 SDK 层面的绝对强终止，只保证业务状态立即收敛」——进行中的模型调用无法立即中断，但用户侧的任务状态即时更新。多数同类项目对此要么不处理，要么承诺无法兑现的强终止。
  • 双运行时切分：Web 进程使用异步 SQLAlchemy，Worker 进程使用同步 SQLAlchemy，两者隔离、不混用——该约束源于曾出现的循环导入问题，故障后固化为规则。

工程纪律：该仓库最具特色、长期价值最高的特征

开源项目中罕见的做法是维护一份 AGENTS.md，把「什么算完成」写成验收标准：修改 API 后必须重新生成 OpenAPI 客户端、文档分三区（architecture 记录现状、plans 记录计划、guide 说明用法，不得混写）、架构落地而文档未更新视为未完成、release note 采用固定章节结构。后端测试覆盖响应结构、任务取消、缓存等关键分支。

这套纪律的另一面是为 AI 协作开发而设计：状态语义、页面职责、依赖方向都写成机器可执行的约定，适合由 AI Agent 参与迭代。它既是工程优势，也是理解该项目设计成因的关键。

技术风险

风险说明
接入的模型服务少README 宣称对接 OpenAI / Kling / Runway / Luma 等，但代码中图/视频适配器只有两个目录：integrations/openai/ 与 integrations/volcengine/（火山引擎，即豆包/即梦所属平台）。「模型无关」是架构能力，实际接入清单仍短。
依赖轮询而非推送任务进度依赖前端轮询接口，任务与页面数量增多时请求量线性增长；单机自托管场景可以满足，规模化后需引入 WebSocket/SSE（服务端主动推送）。
双运行时的心智成本async/sync 两套 DB runtime 并存是务实解，但新贡献者容易误放代码位置；依赖约定而非类型系统约束。
单机部署形态Compose 完整组件集（MySQL+Redis+RustFS+Worker+前后端）适合个人与小团队，无水平扩展、无权限体系，与「工作室多人协作」尚有差距。

05综合判断

维度判断
竞争位置开源同类（MoneyPrinter、ShortGPT 等）多停留在「输入一句话、输出一条成片」的演示级自动化；Jellyfish 选择的是相反方向——把 AI 生成候选、人工最终确认、可复用、一致性这些生产级细节做深入。方向判断合理：短剧是连续剧内容，一致性与流程管理正是这类内容的核心瓶颈。
最大优势工程纪律与任务系统。状态语义、页面边界、依赖方向全部成文，代码分层清晰，这是它能长期演进的基础。
最大短板生产链路止步于素材，未延伸到成片：时间线、剪辑、成片导出均未实现，用户最后仍需携带素材到剪映完成后期；加上宣传承诺超出已实现范围，试用者的预期落差风险高。
下一步关键完成导出链路、扩充模型服务接入。两者完成后，它才能从「分镜生产工具」成为完整的「短剧生产线」。
