# GitHub 项目分析 · 产品 × 技术双视角（cyx-github-analysis）

## Purpose（目的）

把「分析一个开源项目」从随手聊变成可复现的方法论：**每个结论都有仓库证据、宣传与实现分开核、
图只画承载结构的图**，产出一份能直接点开看的单文件暗色 HTML 报告。
首例是 Jellyfish（Forget-C/Jellyfish）分析，方法论行业无关，任何 repo 可套。

## How to use（如何使用）

1. 按「二、六步分析法」走完全程，先取材后动笔。
2. 交付物按「四、交付物规格」排版；骨架与组件可直接参考 `assets/report-sample.html`（Jellyfish 完整实例）。
3. 语言遵循 `~/.workbuddy/MEMORY.md` 的语言总纲（通俗 + 严谨 + 逻辑闭环 + 去 AI 味）与 `cyx-html-style` 的禁词纪律。
4. 交付前逐项走「五、交付前自查清单」。
5. 交付后按「六、自我进化机制」回扫本轮反馈，可复用的写回本文件并记账。

## 一、取材清单（动笔前读什么）

有本地副本直接读，没有先 clone（浅克隆即可：`git clone --depth 1`）。按顺序：

| 优先级 | 读什么 | 回答什么 |
|---|---|---|
| 1 | `README.md`（含中文版） | 项目对自己的定位与承诺——这是**宣传口径**，不是事实 |
| 2 | 目录结构（`ls` 顶层 + 核心源码目录） | **实现口径**：真实模块分布、规模、分层 |
| 3 | `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md` | 工程纪律与协作约定，判断项目能否长期演进 |
| 4 | 架构 / 设计文档（docs、site/content/docs 等） | 状态语义、核心链路、技术取舍的自述 |
| 5 | release notes / changelog / 最近提交日期 | 成熟度与活跃度：最新版本在做什么、多久没动 |
| 6 | 关键子系统源码（挑 1-2 个最有含金量的） | 深挖取舍：真相近于读文档，差相近于读代码 |

**红线：宣传 ≠ 实现。** README 宣称的每个能力（对接了哪些模型/平台、有哪些功能）必须到
代码目录里数一遍再写；对不上的差距**单列一节**，不消化掉、不替作者圆场。

## 二、六步分析法

### 1. 核心定位
- 一句话句式：**「不做 X，只做 Y」+ 一个生活化类比**（例：大模型是摄像机，它是剧组管理系统）。
- 判断项目站在赛道哪一层（模型层 / 编排层 / 应用层），并写清这一定位的两面：换来什么、代价是什么。

### 2. 痛点 → 设计映射
- 用三列表：**痛点（说人话描述）→ 设计 → 落在代码哪里**。
- 每个核心设计必须对应一个真实痛点；对不上痛点的功能是装饰，降级处理或不写。
- 痛点描述要让外行看懂（例：「一致性漂移：同一个角色上一镜黑发下一镜金发」）。

### 3. 产品视角
- **主流程图**（SVG 管道图）：从输入到产出的主干，标出状态门禁与贯穿性组件。
- **亮点表**：挑 2-3 个真正差异化的设计，说明它防了什么乱象；不堆功能清单。
- **成熟度条**：三档——已落地 / 主体完成 / 缺口，逐项依据 roadmap、前端页面目录、release note 核对，不凭印象打分。
- **宣传与实现差距**：单列一个红色 callout，写清「宣传说了什么、实际做到哪」。

### 4. 技术视角
- **架构分层图**（SVG）：前端 / 后端 / 基础设施三块 + 关键数据流箭头，每块标技术选型。
- **核心机制深挖**：挑全项目最有含金量的一个子系统画链路图、讲透取舍（好的取舍和诚实的语义约定都值得写）。
- **工程纪律**：分层约束、契约生成、文档分区、验收标准——这类「反常的规矩」往往是最值钱的特征。
- **风险表**：每条风险必须有代码证据（目录、文件、缺失的模块），禁止「可能存在性能问题」这类无锚点猜测。

### 5. 综合判断
- 固定四行：**竞争位置 / 最大优势 / 最大短板 / 下一步关键**。
- 竞争位置要放到同类开源项目坐标系里说（同类多停在什么水平、它押注的反方向是什么），不说空话。

### 6. 来源索引
- 报告末尾列全部依据文件路径 + 判断依据（如「基于 YYYY-MM-DD 最后提交」），读者可回查。

## 三、证据与语言红线

1. **每个结论锚定仓库文件路径**，写成 `来源：路径` 跟在图/表后面；报告末尾来源索引收口。
2. **未实现的能力不得写成已有**；「宣称」与「实现」两个词分开用。
3. **图必有信息量，不为图而图**：流程、架构、核心链路才配 SVG；对照关系、风险清单用表；
   成熟度用色条。纯装饰性插图一张都不要。
4. **一句话原则**：能用一句说完不用两句；每节一个核心判断，先判断后展开。
5. **去 AI 味**：不写「生态」「闭环」「赋能」「体现了…的诚实」这类空词与论述腔；
   「链路没闭环」改「生产链路到 X 这段断了」，「Provider 生态薄」改「接入的模型服务少」。
6. **口语表达禁用，统一换书面表述**（2026-09-28 反馈新增）：报告语言要「通俗」但不「口语」。
   判据：读出来像聊天就不行。高频对照例——
   「好比→以…类比」「拍板→最终确认」「两眼一抹黑→无从得知」「搅成一锅粥→混为一谈」
   「人肉复制粘贴→人工复制粘贴」「挂没挂、卡在哪→是否失败、停滞于哪一步」「不吹牛→表述克制」
   「踩过坑→曾暴露缺陷后固化」「全家桶→完整组件集」「玩具级→演示级」「吐一条片→输出一条成片」
   「长歪→偏离既定职责」「小白→非技术用户」「够用→可以满足需求」「跑在实现前面→宣传承诺超出已实现范围」。
   SVG 图内文字、表格单元格同样适用（图里的字也是文档的字）。
7. **术语白话定义**：Celery（把耗时活儿搬到后台进程排队干的任务队列）、OpenAPI（前后端之间的
   接口合同，前端代码从它自动生成）——第一次出现必须给「是什么 + 为什么叫这个名」。
8. 叙述主体用「我们」，不写「本报告」「本文将」。

## 四、交付物规格（单文件暗色 HTML）

| 项 | 规格 |
|---|---|
| 布局 | **左侧固定目录**（约 212px：「目录」标题 + 章节锚点，滚动 IntersectionObserver 高亮，≤1080px 隐藏）；正文 `margin-left` 让开目录 |
| 版心 | 加宽到约 1180px，左右留白收窄，让图表撑满 |
| 图 | 内联 SVG，`viewBox` 宽 900 上下，文字用 `<text>`/`<tspan>`，箭头用 `marker`；深色底上每个形状显式填色。精致度基线（2026-09-28 反馈新增）：节点用纵向渐变填充 + 投影（feDropShadow）+ 顶部 3px 色条标类别；节点上方加等宽字体编号眉标（01/02…）；连线上有信息的加胶囊标签（如 OpenAPI / 读写）；同类图共用一套视觉语言（同一渐变、同一投影、同一箭头样式），渐变与 marker 的 id 每张图独立前缀防冲突 |
| 成熟度 | CSS 三色条（绿=已落地 / 青=主体完成 / 红=缺口）+ 图例，不用打分表格 |
| Callout | 红=差距与风险、黄=取舍与边界、绿=优势确认，左边框 3px |
| 目录命名 | 章节标题用「核心定位」（不用「一句话定位」）、「解决什么问题」（不用「它解决什么问题」）——名词短语，不带论述腔 |
| 禁用 | emoji、说明性文字（口径声明、方法论自述）、单字双字空标签、页脚免责语 |

CSS 变量、组件类（`.panel` / `table.t` / `.callout` / `.bar-row` / `.toc`）直接从
`assets/report-sample.html` 抄，改内容不改骨架。

## 五、交付前自查清单

- [ ] README 宣称的每项能力都到代码里核过？差距是否单列？
- [ ] 每个结论后面有 `来源：路径`？末尾来源索引齐吗？最后提交日期写了吗？
- [ ] 每张 SVG 都承载结构信息？删掉任何一张，报告是否缺一块？（缺才该留）
- [ ] 空词扫过一遍：生态 / 闭环 / 赋能 / 克制 / 底蕴 / 论述腔开头？
- [ ] 口语扫过一遍：好比 / 拍板 / 抹黑 / 一锅粥 / 人肉 / 小白 / 吹牛 / 玩具级 / 够用？（对照表见三.6）
- [ ] 痛点描述外行能复述吗？术语第一次出现给了白话定义吗？
- [ ] 风险表每条都有代码证据？
- [ ] 左侧目录滚动高亮正常？窄屏隐藏？版心 ≥1100px？
- [ ] 章节标题是名词短语、无 AI 味？

## 六、自我进化机制（遵循 cyx-skill-evolution 通用条款）

**本技能不是一次写死的。** 用户使用本技能时提的修改意见，按 `cyx-skill-evolution` 的三步判定处理：
**通用**（换个项目仍成立）→ 回写本文件对应章节；**个案**（只对这一份产物成立）→ 只改当期产物。

| 反馈类型 | 典型原话 | 改本文件哪一节 |
|---|---|---|
| 证据与口径 | 「这个结论哪来的」「宣传和实际不符」 | 一（取材清单）/ 三（红线） |
| 分析框架 | 「这块该多讲讲 X」「视角缺了」 | 二（六步分析法） |
| 遣词命名 | 「换个词」「标题别这么说」 | 三（红线）/ 四（目录命名） |
| 排版视觉 | 「加目录」「间距小点」「图多点/少点」 | 四（交付物规格） |
| 流程命令 | 「这步顺序不对」「命令跑不通」 | 一（取材清单） |

**沉淀后必做**：① 规则与「交付前自查清单」两处同步；② 在 `references/feedback-log.md` 追加一行；
③ 一句话告知用户「这条记进本技能了」。
规则回退、落盘纪律（三不写）、分权处理、账本格式见 `cyx-skill-evolution`。

## 边界

- 本技能只管「分析并产出报告」。要部署运行项目 → `cyx-github-deploy`；
  要市场规模、竞品格局、商业模式调研 → `cyx-research-report`。
- 分析过程中发现的可部署性、启动坑，不属于本技能产出；用户需要时转交 `cyx-github-deploy`。
