# cyx 技能自我进化通用条款（cyx-skill-evolution）

## Purpose（目的）

**技能不是一次写死的。** 用户用一个 skill 干活，干的过程中提的每一条修改、补充、纠偏，都可能是适用于**所有后续同类任务**的规则；把它挑出来写回那个 skill，技能才会越用越准。丢掉的部分，下次还会重犯。

本文件是这份机制的**母版**。各 `cyx-*` 技能文末那一节「自我进化机制」只写三件事——本节引用、触发时机、本技能的落点表——其余共性条款一律指向本文件。这样以后要改机制，改一处就够。

机制的三根支柱：

| 支柱 | 干什么 | 没有它会怎样 |
|---|---|---|
| **判定** | 把反馈分成「通用 / 个案 / 模糊」 | 把一次性意见写成永久规则，或者把通用规则当个案放过 |
| **回写** | 通用项落到 skill 的具体章节 | 反馈只落在当期产物，下次重犯 |
| **留痕** | 反馈记进账本，规则与自查同步 | 半年后没人知道这条规则从哪来、还成不成立 |

---

## 一、触发时机

以下任一条成立，就要启动本机制：

- 用户针对**已交付产物**提出修改意见——措辞、结构、命名、版式、删内容、补内容、口径。
- 用户**推翻了上一轮**的做法（「还是改成原来那样」「这条不用这样」）——回退同样是进化，要记账。
- **同一类意见反复出现（≥2 次）**——最强信号：不是当期产物的问题，而是 skill 的**默认值或默认写法错了**，必须从「建议」升为强约束。
- **我主动发现**技能里有错命令、缺步骤、名不副实、过时信息、前后矛盾——不等指令，当场修。
- **每次交付收尾**（用户一句意见都没提也算）——主动回扫本轮交互，逐条问「这条只对当期产物成立，还是对以后同类任务也成立」。**这一条是把机制从「被动响应」变成「自主进化」的关键**：只在用户不满时才长规则，等于把教训留在当期产物里，下次重犯。没有可沉淀的就明说没有，别硬凑。
- **用户明确要求「把改动沉淀进技能 / 技能要有自我进化机制」时**——立即启动全量回扫：把本轮（含此前漏走的）所有可复用反馈写进技能并落账，**不得只口头答应「已沉淀」**。这是把「进化」从默认动作显式升级为强制动作；若发现某产物多轮反馈都没走沉淀（如对比图谱类 HTML 被当成独立视觉产物绕过），要补记归口并写清教训。

## 二、三步判定

| 步骤 | 做什么 | 判据 |
|---|---|---|
| ① **归类** | 把反馈归类（用本节下方的通用分档，或该技能自带的分类表） | 一条反馈只归一个主类；跨界拆两行，不合并成含糊一行 |
| ② **判通用性** | 通用 / 个案 / 模糊三选一 | **通用**：换一个项目、换一个对象仍成立 → 回写 skill。**个案**：只对这一份产物的某个结论/某个数字成立 → 只改当期产物。**模糊**：按通用处理，但写成「判据」而非「硬值」 |
| ③ **定落点** | 找到应改的**文件 + 章节** | 优先就地改已有条目，不新起一节 |

**通用反馈的通用分档**（技能自带分类表时以技能为准）：

| 代号 | 类别 | 典型反馈 |
|---|---|---|
| A | 事实与依据 | 「结论要有依据」「点出是哪家」「这个数不对」 |
| B | 遣词与命名 | 「换个词」「不要弱化字眼」「用行业口径」 |
| C | 视角与元信息 | 「不要写 AI 干了什么」「删掉说明性文字」「不要修订流水」 |
| D | 结构与层次 | 「不要大段黏在一起」「先总后分」「分清主次」 |
| E | 术语与可读性 | 「这个词解释一下」「看不懂」 |
| F | 排版与视觉 | 「边距宽一点」「配色太刺眼」「组件太重」 |
| G | 流程与命令 | 「这一步顺序不对」「这个命令跑不通」 |
| 组织 | skill 自身的拆分/改名/机制 | 「这个该独立成技能」「进化机制要统一」 |

**判通用的一个动作**：把这条意见套到一个**不同项目**上问——还成立吗？成立就是通用。
反例：「LumenFlow 主打短视频」不是通用；「产品定位段先讲清服务谁、解决什么，再讲机制」是通用。

## 三、回写规则

### 3.1 落到哪

- **优先就地强化**：同类规则已在 → 把表述改准、加粗升为强约束、补一条机检，**不新起一节**。
- **规则与自查两处同步**：改了正文条款，必须同步该技能的「交付前自查清单」。只改前者，下次交付仍会漏。
- **能机检的落成机检**：有检查脚本的技能（如 `check_course.py`、`check-template.py`、`check-prd.py`），把硬规则落成一项断言。
- **教学/口诀类**：若这条反馈更适合作为「正面例子 vs 反面例子」存在，优先落成对照表一行，而不是写一段说明。

### 3.2 落盘纪律（三不写）

1. **不与已有条目重复** —— 同类已在，就地强化。
2. **不写死具体数值** —— 写「判据 + 判定方法」，不写具体像素 / 数字（数值只是当前默认，还会再变）。
3. **不写无法检验的模糊直觉** —— 写不成判据、落不成对照表一行的，不进 skill。

### 3.3 分权处理（谁能改）

| 技能归属 | 怎么改 |
|---|---|
| 我自建的技能（frontmatter 有 `agent_created: true`） | 直接用 SkillManage 或文件编辑改，改完报告 |
| 用户自建的 `cyx-*` 技能 | 小幅精准修改可在文件层直接做并明确报告；涉及方法论口径的**较大调整先说方案** |
| 第三方技能（`deck-*` / `pdf` / `pptx` 等模板库） | 本体不动（改了会被覆盖，且不归我们）。若反馈对其成立，记进对应 cyx 技能或全局记忆，并点明「需要改插件/模板的哪一处」 |
| 插件（connector / plugin）本体不可写 | 把修正记进对应 skill 或 `~/.workbuddy/MEMORY.md`，并写明「需要改插件的哪一处」 |

### 3.4 技能改名的收口清单（组织类反馈）

用户说「把这个技能命名为 X」「改名成 X」时，**只改目录名不算完成**。旧名通常散在五处，漏一处就留下断链——选择器指向已删路径、别的技能写着旧名找不到目标。一次收干净：

| # | 落点 | 怎么改 |
|---|---|---|
| 1 | 技能目录 | `~/.workbuddy/skills/<旧名>/` 改为 `<新名>/`；目录名与 frontmatter `name` 必须一致 |
| 2 | 本技能文件 | `SKILL.md` 的 `name`、触发词、H1、正文自称；`references/*.md` 的标题与自指 |
| 3 | 交叉引用 | 全 `~/.workbuddy/skills/` 内其他技能的 `SKILL.md` **与各自账本**——账本里的「归属技能」列、「下游指向」行最容易漏 |
| 4 | 全局记忆 | `~/.workbuddy/MEMORY.md` 里列技能清单的句子。**注意裸词**：不带 `cyx-` 前缀的写法（如 `brief-need`）不会被「搜 `cyx-<旧名>`」命中 |
| 5 | 应用缓存 | `~/.workbuddy/storage/user-*/scoped/*/skill-picker.json` 的 `recentlyUsedSkills` 键与 `recentSkillSnapshots` 条目（`id / name / slug / displayName / filePath / description` 一并换，**时间戳保留**，别新建条目）。**这个文件常被运行中的应用占用**：首次改报 `EBUSY: resource busy or locked` 属正常，隔一步再试通常就过；始终写不进时不要强写，在回复里点明「选择器缓存待应用刷新」即可。另有一处由应用自动重建的缓存 `~/.workbuddy/.skill-list-cache.json`——改完目录名后应用会自行刷新，**不需手工改**，但值得 `Grep` 一遍确认新名已进、旧名已出 |
| 6 | 技能路由表 | `~/.workbuddy/skills/SKILL-ROUTES.md` 里该技能的条目与交叉引用（见本文件「八」）。**新增、改名、降级触发等级后必改** |

**刻意不改的两处**：历史账本「用户原话」列、历史工作日志里的旧名——那是当时的原话与事实，替换等于篡改记录。

**配套动作**：① 在 `SKILL.md` H1 下加一行更名注——「本 skill 原名 `<旧名>`，YYYY-MM-DD 更名为 `<新名>`；能力、骨架与产出不变」；② 在账本追加一行，处置列写「重命名」。

**做法**：先 `Grep` 旧名列出全部落点（**带前缀与裸词两种写法都搜**）→ 备份 → 批量替换（多文件多处用脚本，比反复单点编辑可靠）→ 复查残留并逐条判定「刻意保留 / 漏改」→ 最后**按新名调用一次**，工具能返回新目录才算通过。

**一个边界**：技能名换了，正文里作为**文体标签**的词（如「轻量 brief 版」）不必跟着换——它描述的是产出物类型，不是技能标识。要不要一起换属于方法论口径，先问用户，别顺手改掉。

## 四、留痕与校验

1. **追加账本一行**：`日期 / 用户原话（节选）/ 类别 / 归属 skill / 落点 / 处置`。
   账本位置：技能自带 `references/feedback-log.md` 的，写那里；没有的，写本技能目录下的 `feedback-log.md`（首次使用时创建）。
2. **同类 ≥2 次** → 对应条目加粗升为强约束，并同步自查清单。
3. **跑一次该技能的机检脚本**（有的话），确认没改坏。
4. **一句话告知用户**：「这条我记进 `<skill 名>` 了，以后默认这样做。」——方便当场纠正（「这条是一次性的，别记」）。
5. **报告三件事**：改了**哪个 skill**、改了**哪几处**、**为什么**。

---

## 五、规则也会过时：允许回退

用户后续推翻某条（「这条不用这样」）时：

1. 改对应条目，**标注适用边界**而不是直接删除——删掉就丢了「为什么当初这么定」的线索。
2. 在账本追加一行，处置列写「规则回退」，并记明被谁推翻。
3. 查有无其他条目与它冲突（尤其结构条款与自查清单之间、同一技能的两节之间）。
4. 若回退影响多个技能，同步改，不留半套。

## 六、交付后自检（每次用完某个 skill 都要过一遍）

- [ ] 本轮反馈是否逐条判过通用性？
- [ ] 通用项是否已落到对应 skill 的**具体章节**（不是"记下了"，是文件里真改了）？
- [ ] 是否有同类意见重复出现，需要从「建议」升为「强约束」？
- [ ] 新规则是否同步进该技能的**交付前自查清单**？
- [ ] 能机检的是否已落成检查项，脚本是否跑过？
- [ ] 账本是否已追加一行（含归属 skill）？
- [ ] 是否已用一句话告知用户？
- [ ] 越界项（属于别的 skill 或插件）是否已转出去并点明落点？
- [ ] 「每次交付收尾」的主动回扫做了吗——**哪怕用户一句意见都没提**？（没有可沉淀的就明说）

## 七、各 skill 如何引用本文件

在该技能文末加一节，模板如下（把 `X.Y` 换成实际编号）：

```markdown
## X.Y 自我进化机制（遵循 cyx-skill-evolution 通用条款）

**本技能不是一次写死的。** 用户使用本技能时提的修改意见，按 `cyx-skill-evolution` 的三步判定处理：
**通用**（换个项目仍成立）→ 回写本文件对应章节；**个案**（只对这一份产物成立）→ 只改当期产物。

| 反馈类型 | 典型原话 | 改本文件哪一节 |
|---|---|---|
| （按本技能实际结构填） | | |

**沉淀后必做**：① 规则与「交付前自查清单」两处同步；② 能机检的落成脚本检查项；
③ 在 `references/feedback-log.md` 追加一行；④ 一句话告知用户「这条记进本技能了」。

规则回退、落盘纪律、分权处理、账本格式见 `cyx-skill-evolution`。
```

## 八、技能路由表（家族清单与分流）

`cyx-*` 已超过 26 个，其中需求类 8 个、分析类 2 个、部署类 2 个，名称相似度高（多个叫 `*-need` / `*-demand`），光看目录名分不出该走哪个。家族的分流清单落在：

**`~/.workbuddy/skills/SKILL-ROUTES.md`**

内容分九节：需求与产品规划（含八兄弟边界对照与「最容易选错的三对」）、分析类、运行与部署类、课件类、短剧创作链、调研与写作类、文档治理与工程杂项、邻居技能（非 `cyx-` 前缀）、待治理问题。

**什么时候必须改它**：

- **新增技能** → 按「你要产出什么 / 走哪个 / 判据」补一行，判据要写清与相邻技能的分界，不能只抄 `description`。
- **改名** → 见 3.4 收口清单第 6 处。
- **降级触发等级**（自动 → 点名才上，或反之）→ 在对应行标注档位，否则路由表会把用户引到一个已经不自动触发的技能上。
- **发现两个技能在实盘里被选错** → 立刻回写判据，别只当场纠正一次。

**路由表与 `description` 的分工**：`description` 是模型选技能的第一依据，路由表是**人**查「这个活该走哪个」的对照表，也是判据写不准时的兜底。两者冲突时以 `description` 的实际触发行为为准，并回头修路由表。

## 边界

- 本技能**不负责**具体某个技能的内容规则——它只管「反馈怎么变成规则」这套流程。
- 本技能**不替代**各技能自带的自足条款（如 `cyx-research-report` 十六、`cyx-md-style` 六、`cyx-html-style` 七）。
  那几节内容更细、有专属账本与机检，**优先执行它们**；本文件是它们的共同上游，处理其余没有专属条款的技能。
- 与全局记忆的分工：**跨技能、跨项目的公约**（如语言总纲）写 `~/.workbuddy/MEMORY.md`；
  **某一技能的写法与流程**写该技能文件。两者冲突时，记忆里的纲领优先，并回头修技能。
