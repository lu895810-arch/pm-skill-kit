# 产品功能需求速览（cyx-summary-need）

> 本 skill 原名 `cyx-brief-need`，2026-09-23 更名为 `cyx-summary-need`；能力、骨架与产出不变。

## Purpose（目的）

把「一份产品资料 / 一堆素材 / 一份旧稿」整理成一份**结构化、可直看、可填数据**的功能需求文档。

这份需求文档的产出是一份**单文件暗色科技风 HTML**：评审者打开就能看、产品能照着讲、研发能照着补数据。它来自一份真实跑通过的短剧 AI 平台需求文档（LumenFlow，V1.0），它做对的三件事，也是本 skill 的交付标准：

1. **审阅层先行**——评审者不读正文也能在 3 分钟内对完核心定位、范围、风险与待确认项。
2. **功能需求有组织**——按模块分组，每条带「模块编号 / 功能点 / 说明 / 优先级 / 验收要点」，缺一项都不算写完。
3. **交付物能活过第一版**——待确认显式挂 B 编号、风险带等级与对策、来源有出处，半年后的人还能看懂当初怎么定的。

**与 cyx-ears-need 的分工（不重复造）**：

| 事项 | 归谁 |
|---|---|
| 单文件暗色科技风 HTML 模板、组件类、徽章自动着色、进度条 | **本 skill** |
| 功能需求的「九段骨架」、模块字母、编号、优先级、待确认公约 | **本 skill** |
| 语言纪律（去 AI 味、通俗、逻辑闭环、衔接流畅、跨格式语言总纲） | `cyx-md-style` + `~/.workbuddy/MEMORY.md`「语言总纲」 |
| 视觉纪律（暗色科技风配色、组件类、反塑料味、去 emoji） | `cyx-html-style` |
| 数据可信红线（每数有出处、宁缺毋造） | `cyx-research-report` |
| 十章重型 PRD / EARS 六段式 / 工程级派工粒度 | `cyx-ears-need`（**用户点名才加载**，不自动触发） |
| 素材分区、成品归档、文件命名 | `cyx-doc-separate` |

---

## When to use（何时触发）

**触发**：

- 用户要整理「某产品的功能需求 / 功能清单 / 需求文档」，并希望产出一份能直接打开看的单文件 HTML。
- 用户说「帮我整理需求文档」「把功能点提炼一下」「列个功能清单」「像 LumenFlow 那份需求文档那样」。
- 用户手里有产品白皮书、官网、截图、旧版方案、教程文档，要把它们收敛成一份结构化需求文档。
- 用户要的是「能看、能讲、能补数据」的轻量需求稿，不要求 EARS 工程粒度。

**不触发**：

- 用户点名要十章重型 PRD（EARS 六段式、派工粒度）→ 用 `cyx-ears-need`；只是要「一份需求文档」→ 就用本 skill，不升级。
- 只做市场调研、不涉需求定义 → 用 `cyx-research-report`。
- 纯界面原型稿、不涉需求组织 → 另说。

## 一、结构骨架（九段 + 可选扩展组 + 附录）

文档顺序固定，是一条从「评审者要看什么」到「怎么验收」的推进链，**段不要少、不要乱序**。

```
【审阅层】（评审者只看这一层即可开会）
  0. 评审速览     核心定位 · 模式/范围 · 核心价值 · 模块数 · P0 范围 · 商业模式 · 运行环境 · 待确认数 · 风险 Top3
  0. 文档信息     文档名 / 版本 / 日期 / 内容基线 / 状态 / 关联文档
────────────────────────────────────────────
  1. 产品概述     定位与核心价值 · 解决的问题 · 目标用户 · 运行环境与语言
  2. 名词术语表   先定义后使用，非本行业读者也能读懂
  3. 功能需求     按模块分组（3.1–3.N），每条：编号/功能点/说明/优先级/验收要点
  4. 业务流程     主流程 / 子流程 / 独立模式（ASCII 流程图）+ 规则注
  5. 定价与计费   计费项 / 口径 / 来源（可选但产品常需）
  6. 非功能需求   数据安全 / 稳定性 / 性能 / 提示约束 / 可扩展
  7. 约束与风险   编号 · 约束/风险 · 等级 · 对策
  8. 验收冒烟清单 端到端场景，不写单元测试
────────────────────────────────────────────
【可选扩展组】素材里有对应内容才写；不写就连 nav 链接一起不加
  9. 后续迭代需求池 演进 / 现状分析归纳出的缺口，明确标「不在当前范围」
【附录】
  A 待确认清单        编号 / 问题 / 建议责任方 / 状态
  B 参考来源          来源 / 用途
  C 文档口径与变更记录 口径与边界 · 变更记录（分条分点；变更流水全文档只此一处）
```

**逐段写什么、必填什么——见 `references/structure-playbook.md`。每写一段前先翻对应小节。**

**骨架里有两类「可选」——判据是「手上有没有对应材料」，没有就整块不写，别硬凑：**

| 可选块 | 什么时候写 | 位置 |
|---|---|---|
| 产品演进背景 · 入口架构 · 核心需求主线 | 素材里有演进分析、现状梳理、竞品或阶段材料 | 第 1 章末尾（各自 `info-title` + 表 / `ul.pts`） |
| 用户旅程视角的需求流转 | 产品有多个入口，需要说清「什么阶段该用哪个」 | 第 4 章最后一条（`4.x`，ASCII 图） |
| 后续迭代需求池 | 演进 / 现状材料归纳出了「现在没做、以后可能做」的缺口 | 第 9 章（验收之后、附录之前） |

可选块的通用纪律：**写明它不在当前主需求范围内**（如「不在本文档主需求范围（模块 A–H）内，是否纳入需产品确认」）；**优先级是推断值时必须标「（待确认）」**——主需求的 P0/P1/P2 是定论，迭代池的 P2/P3 是推断，两套别混着说。

**附录 C 不属可选项，每个文档都要有**：「口径与边界」是必答项（这份文档凭什么、冲突怎么处理、推断怎么标、条款到什么程度），「变更记录」第二版起累积、首版写「首版」。两块都用 `ul.pts` **分条分点**。**变更流水全文档只允许这一处**——头部 `.kick` 与「文档信息 · 版本」都不再展开，只留版本号 + 「见附录 C」。

## 二、模块与编号公约

功能需求（第 3 章）按**模块**分组，每模块一个大写字母前缀，需求编号 `{字母}{序号}`。

**模块字母按 3.x 章节顺序从 A 开始连续编排，不跳序、不倒序、不混用语义字母**：3.1 → A，3.2 → B，3.3 → C，依此类推。这样模块编号天然与文档顺序一致，审阅时不会乱。

| 示例位置 | 字母 | 通用要回答的问题 |
|---|---|---|
| 3.1 输入与结构化 | **A** | 外部素材怎么进来？格式与容量边界？怎么变成系统可用的结构化数据？ |
| 3.2 资产与复用 | **B** | 哪些对象要被反复引用？一致性怎么锚定？跨范围怎么复用？ |
| 3.3 核心生产与编辑 | **C** | 核心能力（生成/计算/生产）怎么执行？参数与规格？局部怎么改？ |
| 3.4 生成与模型 | **D** | 接哪些模型/引擎？单价与消耗？风险标注？ |
| 3.5 协作与多用户 | **E** | 账号模型？角色权限？分工？积分/消耗归属？ |
| 3.6 计量与计费 | **F** | 用量怎么算？成本归集到谁？计费还是配额？何时启用？ |
| 3.7 辅助与扩展 | **G** | 教程/FAQ/素材库/多语言/独立业务模式？ |
| 3.8 转绘/其他独立模式 | **H** | 独立业务入口、配置、解析、进度与导出？ |

**挑选原则**：数一遍产品真正需要的模块——通常 5–8 个。太少说明漏了横切能力（协作 E、计量 F、治理最常被漏），太多说明颗粒度太细要合并。

**其他编号**：

| 对象 | 格式 | 备注 |
|---|---|---|
| 需求 | `{模块字母}{序号}`，如 `A1`、`B4`、`H7` | 拆分用后缀：`B4` → `B4a`（P0）/ `B4b`（P1），注明「自 B4 拆分」 |
| 优先级 | `P0` / `P1` / `P2` / `P3` | P0 = 主链路闭环必须；P1 = 阶段二；P2 = 观望；P3 = 远景。**排序纪律：每个模块内需求行必须按 P0→P1→P2→P3 单调降序排列，优先级列不得逆序混排。**增量补行时新条目要插进对应优先级段，别顺手加到表尾（表尾挂一个 `P0` 是最常见的破坏方式）。编号用「重排」还是「不重排」都可以，但**选重排就必须同步更新「P0 范围」行与正文/附录里的所有引用**；本项目实测取「按优先级排行、编号不重排」（见 G 模块 `G3,G1,G2`、C 模块 `C1–C4,C6,C5`），跨引用最安全。补完抽一遍 `(编号, 优先级)` 序列验单调 |
| 风险 | `R1` | 含等级（高/中/低）+ 对策 |
| 待确认 | `B-1` | 编号连续，状态三档：`待确认` / `部分确认` / `已确认` |
| 迭代池缺口 | `G-1`（**带连字符**） | 第 9 章后续迭代需求池专用，与模块字母 `G1` 靠连字符区分——`G1` 是模块 G（辅助与扩展）的需求条目，`G-1` 是缺口条目，同文档并存时别混用 |
| 正文引用 | `见 B-2` / `见 B-9、B-10` | 正文、表格、流程注里凡涉及未定口径，直接写「见 B-x」指到附录 A；跨章节引用写「见 4.3」「见第 3 章第 5 步」。**别让读者自己去附录里找**，也别只写「待确认」不给编号 |

**优先级判据**：一条需求删掉后，「从输入到产出」的主链路还走得通吗？走得通 → 不是 P0。

**数字必须闭合**：头部 KPI（模块数 / 创作模式数 / P0 主链路状态 / 待确认数）↔ 正文实际计数 ↔ 附录条目数，四处对得上。

## 二·五、事实来源分级与标注

同一份需求文档里的「事实」不等重：**来源级别不同，能进的章节不同，标注方式也不同**。动笔前先给每条事实归级。

| 级别 | 来源 | 能进哪些章节 | 怎么标 |
|---|---|---|---|
| 一级 · 原始材料 | 白皮书、业务介绍、官网、教程 / 知识库、模板 | 全部章节，含计费、模型、参数、合规 | 表格「来源」列写明材料名 + 小节；同一材料内部口径冲突分别列出并挂 B 编号 |
| 二级 · 界面观察 | 用户提供的产品实际界面截图 | 功能需求、业务流程、术语；**也可用来核对材料口径** | 表格内或句末写「（界面观察：……）」，段末用 `.note` 收一句「据当前产品界面观察，……」 |
| 三级 · 用户口述 | 需求方 / 产品口头说明 | 功能需求、业务流程、范围边界 | 写「据需求方口述」；涉及价格、法律、对外承诺的**一律降为「待确认」**，不拿口述值填正文 |

**界面观察与材料口径不是替代关系**：截图看到的是「当前实现」，材料写的是「约定与承诺」。二者冲突就两条都留——材料口径进正文并标来源，界面观察作为核对线索写进对应 B 编号的问题描述里（例：「界面显示单价 × 时长 = 扣费积分，可作兑换比核对参考」）。

**判据**：这条事实如果被质疑，我能指向哪份材料、哪张截图、哪句口述？指不出来 → 不进正文，降级为「待确认」。

**演进 / 现状类文档的位置**：由原始材料二次归纳出的「演进分析 / 现状梳理 / 缺口清单」类文档，**可以**作为「演进背景、入口架构、需求主线、后续迭代池」的来源（这是它的本职），但**不得**作为产品事实（价格、能力、参数、合规要求）的来源。附录 B 里给它单独一行、用途写明「仅支撑演进与缺口章节」，与原始材料区分开。

## 三、模板用法（执行顺序）

### Phase 0 — 定调（先问，别猜）

缺信息就问，一次问清：**行业与产品形态（Web/App/硬件/服务）· 客户形态（B/C/双端）· 首发场景（只做一个）· 核心问题（用户现在用什么替代、代价是什么）· 谁买单、怎么收钱 · 能力边界（自研 vs 接入第三方）· 硬约束 · 交付形态（只要 HTML，还是也要 MD/Word）**。

**若用户提供的素材里同时出现「公司多条业务线」与「自助平台功能」，必须先定边界**：本文档的产品对象是哪一条？其他业务线（如定制服务、企业解决方案）在概述中显式列为背景能力，不写入平台功能需求模块，也不写入平台计费/权限/验收。

**不要默认把自助平台称为「MVP」「试点」或「实验」。** 若原始材料（如业务介绍、官网、白皮书）已明确将该平台列为公司核心业务模块/业务线，概述措辞必须与之一致：写「核心业务方向之一」「三大业务模块之一」等，不写「平台 MVP」「自助平台 MVP 阶段」。

用户只有素材、答不上来时，**先按常识给一版假设并显式标注「假设待确认」**，进入 Phase 1，不要卡住不动。

### Phase 1 — 复制模板

```bash
cp {baseDir}/assets/template.html <你的产出路径>.html
```

模板已内联全部 CSS 与 JS，改内容即可，无需外链。

### Phase 2 — 填审阅层与概述

先写第 1 章（定位/问题/用户/环境）与审阅层（速览+文档信息），确定全篇基调。

### Phase 3 — 建模块地图

按 第 2 章 挑模块、起名（字母 + 主题），画一张「模块 → 需求条目」草表。字母必须按 3.1→A、3.2→B、3.3→C 的顺序连续编排，不跳序不倒序。先给用户过一眼再往下写。

同一轮里把**可选扩展块写不写**也定下来（演进背景 / 入口架构 / 需求主线 / 用户旅程 / 迭代需求池）——依据是素材里有没有对应内容，没有就整块不写、nav 也不加链接。

### Phase 4 — 逐条写需求

按模块写，每条给「编号 / 功能点 / 说明 / 优先级 / 验收要点」。**每条 P0 需求必须有可测的验收要点**，说明里避免「支持 / 优化 / 提升」式空话（见 第 5 章语言纪律）。

### Phase 5 — 业务流程 / 定价 / 非功能 / 风险 / 验收

顺序收口：流程图（ASCII）+ 规则注 → 计费表 → 非功能表 → 风险表（等级+对策）→ 验收冒烟清单（端到端场景）。

### Phase 6 — 附录台账

待确认清单（**从正文把所有「待确认」抓出来汇总，一条不落**）→ 参考来源（每条来源写明「用途」）。

**附录 B 参考来源红线**：只列用户提供的**原始材料**（白皮书、官网、教程、模板、截图等）。同空间其他衍生文档（如 PRD、旧版 brief、汇总表）不得作为事实来源，避免循环引用；若用户要求「以某份材料为准」，该材料本身必须是原始材料，否则追问原始来源。

**一条例外**：「演进分析 / 现状梳理 / 缺口清单」类归纳型文档可以列入附录 B，用途写明「仅支撑演进背景与后续迭代需求池」，**不得**作为价格、能力、参数、合规这些产品事实的来源。分级判据见 第 2·5 章。

### Phase 7 — 机检与交付

- 用浏览器打开模板自测：进度条随滚动、顶部导航锚点可达、优先级单元格自动变徽章、返回顶部按钮出现。
- 点一遍 nav 的**每个**链接，确认锚点都存在——尤其 nav 指向小节（如「演进」）时，正文里要有对应的空 `<div id="...">`。
- 数字闭合自检：头部 KPI ↔ 正文计数 ↔ 附录条目。
- 过 第 6 章自查清单。
- 交付物按 `cyx-doc-separate` 命名与分区。

## 四、模板组件速查（已在 template.html 实现）

| 用途 | 类 / 结构 |
|---|---|
| 顶部导航（目录 + 进度） | `.topnav` / `.brand` / `.nav-links`。**nav 项与文档实际章节一一对应**：增删章节同步增删 nav；可选块写了才加链接，不写别留空链接 |

## 五、语言与视觉纪律（遵循全局设定）

本 skill 的模板只管「结构骨架 + 渲染长什么样」，文字怎么写遵循全局 cyx 设定，**不在此重复维护**：

- **跨格式语言总纲**（`~/.workbuddy/MEMORY.md`「语言总纲」，最高优先级）：一切文字产出都要满足**通俗易懂、专业严谨、叙事逻辑闭环、段落衔接流畅、去 AI 味**五条。
- **内容侧写法**：`cyx-md-style` 的「语言规范 / 逻辑与口径」（先事实后判断、结论有证据、术语给白话定义、宁缺毋造、无 AI 过渡填充）。
- **视觉侧写法**：`cyx-html-style` 的「色彩与视觉风格 / 反塑料味」（暗底为主、高饱和色只作点缀、标题用总结性对仗短语、不写读法标签与 eyebrow 元描述 chip、不堆科技感符号）。
- **数据可信红线**：`cyx-research-report` 的「数据可信强红线」——每个数据点必须有出处，拿不准就标「待补 / 推演」，**绝不自信生成看似权威但无来源的数**。

**落到本模板的硬约束（摘要，具体以全局 skill 为准）**：

1. 标题写实体名词（「功能需求」「解决的问题」），不写「一句话结论 / 核心要点 / 机制推演」这类空标签与修辞动作。
2. **原始材料口径冲突处理**：同一份或多份原始材料对同一事实（价格、时限、模型名、活动规则等）表述不一致时，**不在正文中硬凑统一口径**；应在表格/正文中分别标注来源与差异，并新增 B 编号待确认。宁可多一条待确认，也不自信生成一个看似统一的数。
3. 不用 emoji 装点，不写「赋能 / 抓手 / 闭环 / 干货」等空话；不用「首先/其次/最后」「综上所述」「值得注意的是」过渡填充。
4. 术语首次出现给一句人话解释（是什么 + 为什么叫这个名），不拿同义词当解释。
5. 每个判断有依据、每个风险有对策、每个待确认有责任人——不写悬空待定。
6. **核心业务线措辞与源材料一致**：源材料称「核心业务模块之一」「三大业务线之一」的，文档不写「MVP」「试点」；源材料称「试点/MVP/早期探索」的，才可用对应表述，并标来源。
7. **文档自称指向明确**：正文一律用「本文档」或「本需求文档」指代当前产出，不用「本 brief」；文件名、文档名称中的「Brief 版」仅作为文档类型标签保留，不作为正文自称。
8. 导航项用原章节名（不编号、不编逻辑链）；brand 用一句话对仗短语点全文。
9. **头部只写产品摘要，口径与变更进附录**：`.kick` 写产品核心摘要（≤60 字）；来源范围、口径归属、推断怎么标 → 「附录 C 口径与边界」；版本沿革 → 「附录 C 变更记录」，分条分点。「文档信息 · 版本」只写版本号 + 「版本沿革见附录 C」。**变更流水全文档只允许一处。**【2026-09-23 修订】本条此前写的是「`kick` 写口径与范围、版本流水写在文档信息表」——用户推翻：那两处都在正文头部，流水一长就把摘要挤没了，读者第一眼看不到产品是什么。
10. **证据链不留白**：判断后面跟依据（材料 / 界面观察 / 口述），风险后面跟对策，待确认后面跟责任方与编号。

## 七、自我进化机制（本 skill 同步更新规则）

> **上游通用条款**：判定、留痕、回退的共性规则见 `cyx-skill-evolution`；本节是它在 brief 需求文档场景的落地。

**技能不是一次写死的。** 用户就 brief 需求文档提的每一条修改意见，都可能适用于所有后续同类文档；把它挑出来写回本文件与模板，本 skill 才会越用越准。与 `cyx-html-style`「七」、`cyx-md-style`「六」同构，共用 `references/feedback-log.md`。

### 7.1 触发时机

- 用户对**结构 / 骨架 / 编号 / 视觉**提意见（「少一段」「边距太窄」「徽章不对」「这个模块该单独成章」）。
- **同一类意见反复出现（≥2 次）**——最强信号：不是当期文档的问题，而是默认写法错了，要升为强约束。
- **每完成一次交付就过一遍**（哪怕用户一句意见都没提）——按 7.6 回扫本轮交互。只在用户不满时才长规则，等于把教训留在当期产物里，下次还得重犯。

### 7.2 落点映射

代号取 `cyx-skill-evolution`「二、三步判定」的通用分档，账本按「代号 + 落点」记，跨技能才好统计。

| 代号 | 反馈类型 | 典型原话 | 落点 |
|---|---|---|---|
| C 视角与元信息 | 文档头、口径说明、变更流水、自称 | 「这些内容放附录」「这个地方写核心摘要」「不要修订流水」「本 brief」 | 第 1 章骨架（附录 C）+ 第 5 章语言纪律 + 第 6 章自查 + **`assets/template.html` 的头部与附录 C** |
| D 结构与层次 | 章节结构 | 「缺一章」「章的顺序不对」 | 第 1 章骨架 + `references/structure-playbook.md` |
| D 结构与层次 | 编号、优先级与台账 | 「编号乱了」「P0 排到 P1 后面」「待确认漏了」 | 第 2 章公约 + 第 6 章自查 + **`assets/template.html` 的示例编号与排序** |
| F 排版与视觉 | 呈现 | 「太像 AI 生成的」「边距」「徽章」 | `assets/template.html` 的 CSS/JS + 第 5 章（视觉纪律指向 cyx-html-style） |
| B 遣词与命名 / E 术语与可读性 | 语言与措辞 | 「太啰嗦」「看不懂」「逻辑跳」 | 第 5 章（指向 cyx-md-style / 语言总纲） |
| A 事实与依据 | 来源与口径冲突 | 「以这五份资料为依据」「不知道的宁可不写」 | 第 2·5 章来源分级 + Phase 0 / Phase 6 + 第 6 章自查 |
| G 流程与命令 | 工具与执行 | 「这个命令跑不通」「Edit 没落盘」 | Phase 7 机检 + `references/structure-playbook.md` 末尾执行提示 |

### 7.3 落盘纪律（三不写）

1. **不与已有规则重复**：同类已在 → 就地强化，不新起一节。
2. **不写死具体数值**：写「判据 + 判定方法」，不写具体像素/数字（数值只是当前默认，会再变）。
3. **写不成判据的模糊直觉不进文件**：要么落成模板 CSS/JS 改动，要么落成自查清单一项。

### 7.4 沉淀后必做

1. 在 `references/feedback-log.md` 追加一行：`日期 / 原话节选 / 类别 / 落点 / 处置`。
2. 同类 ≥2 次 → 对应条目加粗升为强约束，并同步第 6 章自查清单。
3. 一句话告知用户：「这条我记进 cyx-summary-need 了，以后默认这么做。」——方便他当场纠正（「这条是一次性的，别记」）。
4. **回扫落点清单**：同一条规则一般有四处落点——`SKILL.md` 正文、`references/structure-playbook.md`、`assets/template.html` 的示例代码、第 6 章自查清单。改一处必须核其余三处，否则规则变了、模板还留着旧写法。（实例：模块字母规则已于 09-22 改为 A–H，但 template 的示例字母长期仍是旧的 S/A/D/V/C/H/G/T，属于「规则改了、落点没扫」的存量漂移。）

### 7.5 规则也会过时：允许回退

用户推翻某条 → ① 改对应条目，**标注适用边界**而非删除；② 在 feedback-log 追加「规则回退」；③ 查有无其他条目与之冲突。

### 7.6 每轮交付的自动回扫（不等用户开口）

**这是本机制从「被动响应」变成「自主进化」的那一步：交付收尾时自己过一遍，别等用户不满。**

1. **回扫本轮交互**：把用户从提需求到定稿说的话逐条过一遍，**尤其中途改口、推翻、补充的地方**——那里通常藏着一条默认写法错了。
2. **逐条判通用性**：只对当前这份文档成立（个案，只改当期产物），还是换个产品、换份材料仍成立（通用，回写本技能）？
3. **归类**：按 7.2 表取一个主类代号，跨界就拆两行。
4. **定落点并回扫四处**：`SKILL.md` 正文 / `references/structure-playbook.md` / `assets/template.html` / 第 6 章自查清单。**四处是同一件事的四个投影**——规则改了模板没跟，就会继续按旧写法生成新文档，比不改更坏。
5. **落盘 + 告知**：账本追加一行；一句话告知用户「这条我记进 cyx-summary-need 了，以后默认这么做」。
6. **没有可沉淀的就明说**：告诉用户「本轮没有需要写回技能的规则」。走完流程但不硬凑规则，也是这一步的一部分。
